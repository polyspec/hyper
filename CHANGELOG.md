## Unreleased

### Added

- A page requests only the resources that it uses, each once (H6, HY-76). The asset build writes code that the client entry imports with `import()` only into chunk files `public/assets/hyper-chunk-<hash>.js`, which the browser loads by their absolute URL when that code first runs, also from the entry that the static shell inlines; the entry is `public/assets/hyper-<hash>.js`, named by the hash of esbuild. It wrote all client code into one file, so an application could not load code that only some pages use when such a page needs it. `public/assets/manifest.json` holds only the entry URL `hyper`; it held `css` and `reader`, the stylesheet names of the board example, which another application does not have, and the board layout now links `/assets/app.css` and, on a post page, `/assets/reader.css` itself. The static shell contains no stylesheet; it inlined `app.css`, which the rendered layout links too, so a client-rendered page held that stylesheet twice. The build no longer requires `public/assets/app.css`. `tests/scripts/build-assets.test.mjs` failed before the change with `ENOENT` for `public/assets/app.css`, and the CSR stylesheet flow of `make e2e` failed with one `style` element. The header comments of `scripts/build-assets.mjs` and `scripts/build-templates.mjs` and item 2 of the asset build in `docs/operations/development.md` described the index with referenced templates, which H5 removed and did not update. The CSR shell limit falls from 34,000 to 33,200 gzip bytes, because the shell no longer inlines `app.css` and measures 32,782 gzip bytes.
- The browser loads a template when rendering reaches it (H5, HY-35). It renders, loads the templates that the rendering requested and did not hold, by their index URLs, and renders again. The index maps a name only to its URL (HY-34). A server-rendered page loads no template when it opens. The browser loaded every template that the templates of a route reference by path, transitively, before rendering, so a route whose template selects one of many views loaded every view. A template of a branch that the data does not select is now not loaded. The Node server reads every template of the index when it opens. Three cases of `hyper.test.ts` failed before the change: a region response and a client-side rendering of `/pick` loaded both `pick-a.tpl` and `pick-b.tpl`, and opening a server-rendered page loaded six templates. HY-30 now states that a change of a route region sends no request to the application and may load the template files that it renders; `make e2e` checks that the first changes of a server-rendered board load only `board-notice` and `board-rows` and that a client-rendered board loads none. The Node server fails to open when an entry template of a route is not in the index. `templateReferences` and its test are removed.
- A route region loader may return `null`, which makes the region absent from that response (H4, HY-75): it has no entry in `regions`, in the embedded data or in `kept`, and the page region receives no definition for it, so a template places a region that may be absent inside `{?# name}…{/}`. A route region may be placed in a template that the route template includes or places by path, and `make templates-check` follows those templates. The browser holds only present route regions, refuses `data`, `render`, `set` and `hy-set` for an absent one, and marks the body with `hy-error="0"` when a present route region has not exactly one element or an absent one has an element. A page that places views at request time under one route, such as a page that an administrator composes, can now declare a route region for a view that only some pages place. Every route region was rendered for every request of its route. The board example shows the notice on the first page only, and `make server-parity` compares `/board?page=2` after eleven posts. `AppTest`, `app.test.ts`, `hyper.test.ts`, `response.test.ts` and `check-templates.test.mjs` failed before the change.
- `make check` runs `make analyse-php`, which runs PHPStan 2.2 at level `max` on the source and the tests of `packages/hyper-php` without a baseline and without ignored errors (H3.3). The first run on "Fail a PHP request on a warning, notice or deprecation" reported 285 errors: 83 in `src` (`Manifest` 26, `Reads` 14, `Kept` 11, `App` 10, `Renderer` 5, `Csrf` 5, `Session` 4, `Request` 4, `Container` 2, `JsonEncoder` 2) and 202 in `tests` (`AppTest` 79, `ClientTest` 36, `RouterTest` 30, `FieldsTest` 18, `RunTest` 11, `KeptTest` 10, `ReadsTest` 8, `CsrfTest` 7, `Support/warnings.php` 2, `JsonTest` 1). The source now checks every decoded value before it uses it: the manifest, `reads.json` and `program.json`, the flash data of the session and the result of a service factory. The renderer holds a `Polyspec\Template\Program` or the native `Engine`. The data maps that loaders return have the type `array<array-key, mixed>`, because PHP stores a decimal key as an integer. A client rendering selection is a `\Closure(Request): mixed` whose result the server checks (HY-62). The tests read fixtures and responses through `tests/Support/Json.php`, which fails a test on a value of another type or a missing key.
- While the PHP server answers a request, a warning, notice or deprecation, such as an undefined variable or array key, becomes an exception and the request fails with the plain 500 of HY-43 (H3, HY-74). PHP continued with `null` and sent a wrong page with status 200, while the message reached only the log. An error that `@` silences stays silent, and the handler is removed after the request. PHPUnit lowers `error_reporting()` while a test runs, so `RunTest` runs `tests/Support/warnings.php` in a separate PHP process; it answered 200 with `"id":null` before the change.
- The server sends only the data that the templates of a route read (H2, HY-73). The browser package computes the read paths of every route from the template ASTs: variables, members, literal indexes, loops, assignments, includes and blocks follow paths, and an output, a test, an operand or an argument reads its value whole. `scripts/build-server.mjs` writes them to `reads.json` of the server program, which `App::open` of PHP now requires (HY-48), and the Node server computes them when the application opens. Before rendering or encoding a page, both servers keep only those paths of the shared data and of every region's data; a list keeps its length and an emptied map stays a map. Every loader value was sent, so a value that the page did not show, such as an internal identifier or a whole message catalog, reached the browser in every JSON response. The data model check of HY-44 now runs on every value that the handlers return before the removal, so an unread value outside the data model still fails. `conformance/reads.json` holds 21 cases that the browser package computes and renders and that `ReadsTest` keeps; `ReadsTest`, `RendererTest`, `AppTest` and the Node `app.test.ts` failed before the change. The `add` route of the test fixtures renders `add.tpl` with the CSRF field, and the token of the tests comes from `/list`, whose route region keeps a value on the server.
- The CSRF protection no longer depends on the application (H1). Every response carries `csrf` as a masked value of the session token: 32 random bytes drawn for that response followed by those bytes XOR the token, as 128 hexadecimal digits, and an action or a save of a kept value is accepted only with a masked value of the token (HY-24); `conformance/csrf.json` holds the cases that both servers pass. The token was the same in every response of a session, so the compressed size of a response that also contained request input, such as the path in `params`, could reveal it. The session cookie is `__Host-hy-session` on HTTPS and `hy-session` otherwise, with `Path=/` and no `Domain`, and the application no longer names it: PHP sets the name in `NativeSession`, and `FileSessions` of Node has no `name` option (HY-45). A cookie without the `__Host-` prefix could be set by a sibling subdomain, which then knew the token of the session that it gave the visitor. An action calls `renewSession()` of its reply at sign-in and sign-out; the server moves the session to a new identifier, deletes the old one and creates a new token, and a loader that calls it fails with 500 (HY-72). `Reply::cacheControl` and `reply.cacheControl` refuse a value without `private` or `no-store` or with `public` or `s-maxage`, because a shared cache would give the token of one visitor to another (HY-52). The `ETag` of a JSON response is weak and hashes the body with the masked token replaced by the session token, so the mask does not prevent a 304 and a renewed session has another tag (HY-53). A stored token that is not 64 lowercase hexadecimal digits is replaced. `CsrfTest`, `ReplyTest`, `NativeSessionTest`, `AppTest`, `csrf.test.ts`, `sessions.test.ts` and `app.test.ts` failed before the change; `make server-parity` compares the masked tokens with the weak tags.
- Embed only the data that the browser can change. A document embeds `env`, `route`, `params`, `shared`, the data of the route regions of its route and their kept entries; a route without route regions embeds no `#hy-data` (HY-31). Before, every document embedded the whole document JSON, so the source of every page showed the data of every region and all shared data, although the browser changes only route regions (HY-30). `data`, `render`, `set` and `hy-set` work only on the route regions of the held route (HY-33, HY-36), the browser holds only their data (HY-32), and the manifest check rejects `keep` on a manifest region (HY-37). JSON responses keep every region. The new rule HY-71 states that every value the server sends reaches the browser, so loaders return only values that the visitor may see. PHP, Node and browser tests and an e2e test check the embedded data.
- The response hook also receives the failure of a 500 of HY-43 or HY-66 as its fifth argument, `?string $failure` in PHP and `failure: string | null` in Node (HY-60): the message of the error, or `the response to <method> <path> has <size> bytes, more than the response limit of <limit> bytes`; it receives null for every other response. The server wrote the cause only to its own log, so an application could not write it on its own line of the request. `AppTest` and `app.test.ts` failed before the change.

They resolved `@polyspec/template` from the dependencies of this repository, which link the template checkout next to it, so a rebuild of that checkout removed the package while a build of an application read it, and an application could not build with another template package. `tests/scripts/template-dir.test.mjs` failed before the change.
- A loader or an action gives the page of its request the status 403 with `Reply::status(403)` in PHP and `reply.status(403)` in Node (HY-69), so that an application shows a sign-in form in place of a page that needs a session, at the URL of that page. The page renders as it does with 200, as JSON or as a document, with `Cache-Control: no-store` and without `ETag`; a page with 409 or 422, a redirect and a stop keep their own status, and another status fails with 500. A loader could only stop the request with the plain text 403 of HY-51 or render the page with 200, which states that the response is the page. `AppTest` and `app.test.ts` failed before the change.
- The application can declare a disconnect hook, `App::open(onDisconnect:)` in PHP and the `onDisconnect` option of `App.open` in Node, which the server calls once with the request, the elapsed milliseconds and the reply of a request whose client closed the connection (HY-67). The Node server learns of the close from `node:http` and then runs no further loader, action or rendering of the request, writes no response and does not call the response hook. PHP reports a closed connection only when a write to it fails, so `App::run` turns `ignore_user_abort` off, PHP ends the script at the first failed write of the response, and a shutdown function calls the hook; the PHP server renders the complete response before it can detect the close. The servers ran every loader and rendered the response for a client that had gone, and reported nothing. `RunTest` and `http.test.ts` failed before the change.
- Every response with a status of 400 or more has `Cache-Control: no-store` (HY-65): the plain text responses that hyper answers itself, the 400 and 431 responses of the Node server to requests that `node:http` cannot parse, and the pages with status 409 or 422. The plain text responses had no `Cache-Control`, so a cache could store a 404 or 405 response by its heuristic freshness (RFC 9111). `AppTest`, `ClientTest` and the Node tests `app.test.ts`, `http.test.ts` and `client.test.ts` failed before the change; the 12 failure cases of `conformance/client.json` now state the header.

A response whose body is larger is not sent: the server logs the method, the path, the size and the limit, answers a plain 500 that no cache stores and reports it to the response hook. A limit that is not a positive integer fails when the application opens. The servers sent a body of any size, which a slow client keeps in the memory of the server process and of a web server that buffers the response. `AppTest` and `app.test.ts` failed before the change.

It keeps a present link whose key, the `href` resolved against the page URL, the source has, inserts the missing links in the order of the source, waits until they load and only then shows the content, and afterwards removes the links that the source does not have. A link that fails to load keeps the page and marks the region, or the body, with `hy-error="0"` (HY-47). The application declares client rendering with `App::open(clientRendering: new ClientRendering(shell, basePath, selects))` in PHP and the `clientRendering` option of `App.open` in Node: the absolute path of the static shell, a data base path such as `/_props`, and a selection that chooses the requests of client-rendered pages, for example by the `Host` header. A chosen HTML `GET` of a page receives the shell with `Cache-Control: no-cache` and `Vary: Accept`, without a session or a loader; its JSON requests and actions run under the data base path and redirect within it; an HTML request under the data base path and a JSON request outside it receive 406. - The response hook also receives the reply of the request, and a loader or an action records a value of the request for the hook with `Reply::note(name, value)` (`reply.note(name, value)` in Node), which the hook reads with `notes()` (HY-60). The Node server gave the hook the request as received and its loaders and actions a copy, so the hook could not read a value that they decided, such as the kind of a refusal; a PHP application used the state of its process. The reply is the one that the loaders and actions received, also after a stop or an error, and an empty reply when the server answered before routing. The notes are not part of the response. The tests of both servers failed before the change.
- The application can declare a response hook, `App::open(onResponse:)` in PHP and the `onResponse` option of `App.open` in Node, which the server calls once for every response with the request, the response and the elapsed milliseconds, including the 400, 403, 404, 405, 413, 415 and 500 responses that hyper answers itself (HY-60). An application logs refusals through it. `App::run` counts from `REQUEST_TIME_FLOAT`; the Node server counts from the time when `node:http` gives the request, and also reports the 400 and 431 responses to requests that `node:http` cannot parse.
- The application declares a body limit (8 MiB by default) and the form types that its actions and `/_hyper/keep` accept (`application/x-www-form-urlencoded` by default, and `multipart/form-data`): `App::open(bodyLimit:, formTypes:)` in PHP and the `bodyLimit` and `formTypes` options of `App.open` in Node (HY-59). Both servers answer 413 for a larger body, then 415 for another media type, then 403 for a wrong CSRF token, before any loader or action runs. The Node server option `bodyLimit` of `app.server` is removed; the server reads no more of a body than the limit of the application. PHP takes the size from `Content-Length` as well, because it leaves a body larger than `post_max_size` empty, and `App::run` fails when `post_max_size` is smaller than the limit or when multipart bodies are accepted while `enable_post_data_reading` is on. `make server-parity` now compares the 413, 415 and 403 responses of both servers: 49 responses were equal.
- A loader or an action can stop a request with `BadRequest`, which answers 400 with the text `Bad Request`, and an action can return `Result::page(status, data)` (`Result.page` in Node), which renders the route page with the status 200, 409 or 422 (HY-58). `Result::invalid(data)` is the page with 422. Only a `GET` request now receives 304 for a matching `If-None-Match`, so an action that renders a page with 200 always runs (HY-53).
- `Request` provides every form value of the body in order without nesting, as the query values are provided: `roles[]` stays the name `roles[]` with all its values (HY-57). PHP read `$_POST`, which nests bracketed names, and the Node server kept only the last value of a name; both servers now read the raw body, an `application/x-www-form-urlencoded` body or the text fields of a `multipart/form-data` body. PHP reads a multipart body only when `enable_post_data_reading` is off. `formString` reads the last value of a name. Both servers pass the 4 multipart cases of `conformance/fields.json`.
- `Request` provides every query value in order without nesting, as an ordered map from each name to its values, and the raw query of the request target (HY-56). PHP read `$_GET`, which nests `a[]` and `a[b]` and keeps one value of a repeated name, so both servers now parse the raw query themselves. `queryInt` reads the last value of a name. Both servers pass the 17 cases of `conformance/fields.json`.
- `make server-parity`, part of `make check`, sends every request of the parity steps to the PHP server and the board Node server and requires the same status, headers and body after it replaces session identifiers, CSRF tokens and `ETag` values with placeholders (HY-55). It compared 41 responses equal. `BOARD_TIME` fixes the creation time of posts in both board servers.
- The Node.js server package `@polyspec/hyper-server` (`packages/hyper-node`) implements the rules of the PHP server: routes with a base path, loaders, actions with CSRF, results and stops, reply cookies and cache control, JSON tags, flash values and changed topics, kept values, request checks, plain errors, the data model check and sessions in files. It renders documents with the browser code and the template files of the asset build, writes JSON with the bytes of PHP `json_encode`, and decodes kept values as PHP `json_decode` does (HY-54). Loaders and actions receive one context with the request, the reply and the services. Its tests run the cases of the PHP server tests against the same fixtures, and `conformance/json.json` holds JSON cases that both servers pass, including U+2028 and U+2029, floats and empty maps. `make node-server` builds a Node server of the board example with `node:sqlite`, which renders the same documents as PHP.
- The request path must consist of printable ASCII characters, as RFC 9112 requires of a request target; both servers answer another path with 400 (HY-42). `node:http` rejects such a target before an application sees it, so the PHP server now follows the same rule.
- The manifest check of the browser code also requires a layout and a title template, and a title and a template for every route and route region, as the PHP manifest reader does.
- A route path can end with a rest parameter `{name*}`, which matches zero or more remaining request segments and holds the rest of the request path without decoding (HY-49). Both routers pass the cases of `conformance/rest.json`.
- A loader or an action can stop a request with `Redirect`, which answers 303 with the location, flash values and changed topics of a redirect result (HY-50), or with `Forbidden`, which answers 403 (HY-51).
- Loaders and actions receive the `Reply` of the request, which adds and removes cookies with the attributes of HY-45 and sets the `Cache-Control` of a page response; the response contains its cookies whatever its status (HY-52). A JSON page response has a strong `ETag`, and a request with the same `If-None-Match` receives 304 (HY-53). `Set-Cookie` is the one response header that holds several values.

### Fixed

- The read paths of a template end when a loop variable rebinds a name that an assignment before the loop read, as in `{:p = page.x}{@ page = p.items}{= page.title}{/}` (H2.6, HY-73). The analysis stored the loop variable as a local variable of the whole template, so the assignment read the loop variable, the loop source grew by `items.*` in every round, and the rounds never ended: `scripts/build-server.mjs` ran at full CPU without end on such a template. The loop variable now exists only in the body of its loop, where it has the paths of its source followed by `*`. `conformance/reads.json` holds the two cases `{:p = page.x}{@ page = p.items}{= page.title}{/}` and `{:p = q.x}{@ q = p.items}{/}`, and `reads.test.ts` computes the read paths of every case in a separate process with a limit of 10 seconds, so an analysis that does not end fails its case; before the change both cases failed at that limit.
- The PHP server fails a request whose shared handler or loader returns a value that is not a map, such as a list, with the plain 500 of HY-43 (HY-44). PHP merged a list into the shared data or used it as region data and answered 200, while the Node server already failed the request. Before the change `AppTest::testSharedDataAndRegionDataThatAreNotMapsFail` received 200 for a shared handler that returned `["b"]`; the Node server test of the same cases passes before and after the change.
- The PHP manifest check rejects `regions` or `routes` that are not lists and a region name or a route name that is not a string (HY-2). It accepted `"routes": "home"` with a PHP warning and no routes, the route name `5` as `"5"`, and the region name `[]` as `"Array"` with a warning. Before the change `AppTest::testManifestRejectsListsAndNamesOfAnotherType` accepted each of its three fixtures.
- The PHP server counts the elapsed time of the response hook and the disconnect hook on the monotonic clock (HY-60): `App::run(?int $started)` and `handle(..., ?int $started)` take an `hrtime(true)` start from their caller, or count from their own call. `App::run` subtracted `REQUEST_TIME_FLOAT` from `microtime(true)`, two wall clock times, so a system time that moved backwards during a request gave a negative elapsed time; a request log showed `-1.419ms`. `RunTest` failed before the change with `-9998.7` ms for a `REQUEST_TIME_FLOAT` ten seconds after now, and `AppTest` and `RunTest` failed for an `hrtime(true)` start.
- The asset build and the server build copy their output files with the mode 0644 and their directories with the mode 0755 (HY-68). They copied with `fs.cpSync` of Node, which creates its destination files with the mode 0200, and a virtiofs bind mount of a Linux container refuses that creation, so `scripts/build-server.mjs` failed in a container with `EACCES, Permission denied` for its `templates` directory. `tests/scripts/output-files.test.mjs` runs the server build and the copies in the official Node image with the output on a virtiofs bind mount of Apple `container`; it failed before the change.
- The build scripts read the browser package from the working directory: `data-template.json` from `packages/hyper-js/` and `checkManifest` and `templateReferences` from the build output in `packages/hyper-js/dist`. A build therefore failed outside the repository directory and without `dist`, and a build had to write `dist` into this repository first. The scripts now read `data-template.json` and the source of `packages/hyper-js` next to them; `make server`, `make server-fixtures` and `make node-fixtures` no longer run `make packages`. `tests/scripts/package-source.test.mjs` failed before the change with `./dist/index.js` not found and with `ENOENT` for `packages/hyper-js/data-template.json`.
- The PHP benchmark failed since `Polyspec\Hyper\Examples\Board\Posts` took a clock, because the benchmark is not part of `make check`. It now passes a fixed clock, and `make check` runs `make bench-server-smoke`, which runs the PHP benchmark once per measurement. The browser benchmark takes several minutes and stays outside `make check`; `docs/operations/benchmark.md` states this. The benchmark document now holds the results of the current code (2026-10-02, measured on a machine with load average 8): for 1,000 rows the generated PHP program renders in 12.8 ms and the native extension in 3.6 ms.
- The bundle limits rise to 32,500 gzip bytes for the SSR script and 33,800 for the CSR shell. The template runtime, which checks every number of the data model, grows the SSR script to 32,057 and the CSR shell to 33,364 gzip bytes; the hyper code adds 79 of them.
- The PHP session added `Expires`, `Pragma` and a second `Cache-Control` header to every response of a session, so a JSON response had two `Cache-Control` headers and a reply could not make a page cacheable. PHP also gave responses without a body, such as 303 and 204, the type `text/html`. The session now adds only its cookie, every page response has `Cache-Control: no-store` unless the reply sets it for status 200, and `App::run` turns off the default content type (HY-52). A comparison of complete response headers found these defects; `AppTest`, `RequestTest` and `RunTest` failed before the fix.
- These defects of swaps, kept values, redirects and sessions are fixed with tests that failed before:
  - The fix of the call order (HY-33) ended a `set`, `render` or `hy-set` change on any response, even one that did not contain its region, after the swap had already changed the page. The page then showed a value that was neither held nor stored. A change now ends only when the data of its own region was replaced, before the swap; when that happens during the swap, the region renders again from held data (HY-33).
  - The browser passed route regions to the page region as template definitions, so a route region saw the page region data in region responses but not in documents; after HY-48 the PHP document and an htmx navigation to the same URL could differ. Server and browser now both render route regions alone and pass HTML (HY-12, HY-13). `make parity` did not cover this case; a test now does.
  - Browser kept values were applied in declaration order instead of the order of HY-38 (browser storage, then pending server values).
  - Client-side rendering decoded a document against the requested path instead of the URL after redirects (HY-22).
  - Every request started a session and wrote a session file, including requests rejected before routing and paths without a route (HY-45).
The following defects of correctness and security are fixed. Each one has a test that failed before the fix.

- PHP server:
  - An unhandled exception printed the message, file paths and the stack trace, and one stored invalid UTF-8 byte broke the list for every visitor. The server now rejects input that is not UTF-8 with 400 (HY-42) and answers other failures with a plain 500 (HY-43).
  - `parse_url` read `/board/12:30` as `/` and `//board/1` as a host. The request path is now the request target before `?` or `#` (HY-42).
  - A POST with a non-page `Hy-Region` ran its action. The check now runs before loaders and actions (HY-16).
  - JSON carried integers outside the template data model with status 200. Both documents and JSON now fail with 500 (HY-44).
  - The session cookie had no `HttpOnly`, `SameSite` or `Secure`, and the server accepted identifiers that it did not create (HY-45).
  - Redirect locations such as `/\evil.example` were accepted (HY-46). `/_hyper/keep` stored values of any size; values longer than 4,096 bytes are now rejected (HY-40).
  - Empty kept maps and `stdClass` maps were not applied, and array spreading renumbered numeric data keys.
- Browser code:
  - After an SSR history restore, the browser kept the data of the earlier page; it now reads `#hy-data` of the restored document (HY-32).
  - Overlapping CSR restorations could mount the wrong page; only the latest one is rendered (HY-23).
  - CSR embedded browser kept values in `#hy-data`; the embedded data and JSON now stay server data, and browser values are applied only to held data. A `server` value whose saving has not completed now takes precedence over responses (HY-38, HY-39).
  - `set` added missing map keys (HY-33). A change through a parent or child of a kept path did not store it (HY-39). Region requests under a base path whose path already started with the base path were not prefixed (HY-23). `hy-set` rejected a string that ends with a backslash (HY-36).
  - A region request that received a non-JSON response swapped the body as HTML; it now does not swap and marks the region with `hy-error` (HY-47).
  - The client bundle contained the source of `hyper/data.tpl`; it now contains only the name (HY-34). Template references were computed by untested build code; `templateReferences` now lives in the package with tests.
- Example and development tools:
  - The comparison page ran `javascript:` URLs from `?ssr=` and accepted messages from any origin. Frames sent their whole body, including the CSRF token, to any parent. Frames now send a SHA-256 of the body to the embedding origin only, and the page accepts only http(s) origins.
  - The edge server cached `index.html` for a year; only files under `/assets/` are cached now.
- More defects of restorations, saves, request checks and failure marks are fixed with tests: a slow CSR restoration overwrote a later navigation (HY-23); a failed server save dropped its pending value, and a successful one could clear a later change (HY-39); one unrelated non-UTF-8 cookie blocked every page, so HY-42 now checks only `hy-keep` and the session cookie; `render`, `set` and `hy-set` changed held data before rendering and left failures unmarked (HY-47); kept values outside the data model caused lasting 500s and are now ignored or rejected (HY-38, HY-40); the request path of `?/x` and of absolute-form targets was wrong (HY-42); marks on regions outside the page region were not cleared, and cancelled requests were marked (HY-47); absolute and relative same-origin URLs were not prefixed (HY-23); redirect locations allowed C1 controls and invalid UTF-8 (HY-46); the session cookie could not be `Secure` behind a TLS-terminating CDN, and no response limited framing (HY-45). The example and the scripts start PHP with `display_errors=0`, because PHP prints startup warnings before the application runs (HY-43).
- More defects of the changes from "Keep region data in the server session, a cookie or Web Storage" to "Fix defects of kept data, requests and failures" are fixed with tests:
  - Two `set` calls at the same time lost one change. A change also stored the value of a response that arrived while it rendered, and swapped stale content over it. Calls now run in call order, and a change whose held data a response replaced ends without swapping, holding or storing (HY-33).
  - Saves of one path could arrive out of order, and an older failed save marked a region whose latest value was saved. Saves of a path are now sent one at a time with the latest value, and only the save of the latest change marks the region (HY-39).
  - A failure of `holdEmbedded` (template loading, rendering or unreadable embedded data) was not marked and rejected unhandled. It now marks the regions or the body and does not reject (HY-47).
  - A request that htmx aborted on its timeout was not marked. It is now a network failure (HY-47).
  - Kept maps and lists were checked only by their outer type, so a stored value with another inner shape caused 500 on every document. Kept values now conform to the shape of the data (HY-38). A conforming value that still breaks rendering makes its region render with its loader data (HY-38).
  - Query and form names nested in arrays skipped the UTF-8 check (HY-42).
  - Redirect locations accepted `.` and `..` segments, such as `/.//evil.example` (HY-46).
- `make templates-check` also checks that the layout places `{# title}`, `{# data}` and every manifest region once (HY-3), and manifests reject invalid topic names.

### Changed

- A 304 of HY-53 has the headers of the 200 response except `Content-Type`, and HY-52 gives no response without a body a `Content-Type`: a 304 carries no representation (RFC 9110, section 15.4.5), and php-fpm removed the `Content-Type` of a 304 while the Node server sent it, so the two servers answered the same request with other headers. `AppTest` and `app.test.ts` failed before the change.
- Lower the gzip limits of the SSR script and the CSR shell to 31,900 and 33,200 bytes, which the earlier merge had raised to 32,500 and 33,800, and state the rule in the development document: a limit is the measured size plus about 1 %, rounded up to 100 bytes, and a change that grows or shrinks an output past it changes the limit in the same change.
- Remove the data model check of the PHP server before it renders a document. Rendering binds every value of the regions and of the embedded response, so a value outside the data model already fails the document there; the check repeated that work, which costs about 2.3 ms for 1,000 rows. JSON responses, which are not rendered, keep the check (HY-44). A test pins that shared data outside the data model fails a document and JSON.
- The browser no longer checks the manifest that its bundle contains; `createApplication` does not call `checkManifest`. The asset build checks the manifest before it writes anything, and the Node server calls `checkManifest` when it starts, as the PHP server does (HY-2). The check was a repeat of the build and server checks and made up 471 of the SSR script's gzip bytes; a test pins that the asset build rejects an invalid manifest and writes nothing.
- The template repository now requires a namespace for a generated PHP program and checks every number by value. The server build writes the generated program in the namespace `Polyspec\Hyper\Program`, and a number outside ±(2^53 − 1), integer or not, fails a request with 500 and is not a kept value (HY-38, HY-44).
- The build now takes the namespace of the generated PHP program from the application (`--php-namespace`; `Polyspec\Hyper\Examples\Board\Program` for the board) and records it in `program.json`, instead of the fixed `Polyspec\Hyper\Program`, so the programs of several applications load in one PHP process and the rule that a process loads one generated program is removed (HY-48). `make template` also reinstalls the Composer copies of the PHP template package, and tests, assets and server builds run it first: Composer kept a stale copy when the package version did not change. `make check` starts with `make template-check`, which fails when a copy differs from the template repository.
- Remove the attribute `hy-region` and the request header `Hy-Region`, which repeated what the manifest already says. A POST with a non-page `Hy-Region` ran its action (fixed earlier by the rule HY-16, now removed), and an element with a region `id` but without the attribute made htmx put a whole HTML document into the region. A region element is now the element whose `id` is the region name (HY-3, HY-36); the extension requests JSON when the target is the page region element, and the server recognizes a region request by `HX-Request`, which htmx sends (HY-15, HY-21). `make templates-check` checks every region placement of the layout and of the route templates, and region placements take no block arguments.
- On HTTPS the kept cookie is `__Host-hy-keep`, so a sibling subdomain cannot set kept values (HY-39).
- Remove the Chromium `<thead>` measurement from `make bench-browser`; it measured a browser behavior, not this project.
- The PHP server renders with a program that `make server` compiles from the templates: the native template extension when PHP has loaded it, and otherwise the generated PHP program (HY-48). The PHP AST interpreter took 15.7 ms for 1,000 rows on an idle machine, and the generated program 9.6 ms on the same input, with identical output. The native extension was measured only on a heavily loaded machine, so its speed is not recorded here. The server renders every region alone and passes HTML definitions, because a generated program fixes the template of each definition. `make test-php` and `make parity` run with both programs. `App::open` takes `program:` in place of `templates:`, and `TemplateLoader` is removed.
- A JSON response carries kept values apart from the region data (HY-17). `regions` holds the loader data, and `kept` holds the conforming `server` and `cookie` values. The server applies them to render a document, and the browser applies them with its own values. The browser can therefore render a region without kept values that break it (HY-38).
- The server no longer checks cookies for UTF-8 (HY-42). It ignores an invalid `hy-keep`, and starts a new session for an invalid session cookie, instead of answering 400 to every request until the cookie expires.
- The recommended deployment serves direct requests with SSR and htmx requests with JSON from one server; the static shell is for backends that serve JSON only (`docs/operations/deployment.md`).

- Keep region data across reloads (HY-37 to HY-41). A region declares kept paths with their storage: `server` (the server session, saved by a background request that rendering does not wait for), `cookie` (the `hy-keep` cookie written by the browser code), `localStorage` or `sessionStorage`. The server applies `server` and `cookie` values before it renders, so the first SSR document shows them; the browser applies `localStorage` and `sessionStorage` values before it renders a response, and after loading for a server document. There is no change tracking.
