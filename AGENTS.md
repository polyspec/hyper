# Development

[한국어](AGENTS.ko.md).

## Documents

- Every document has a `.ko.md` file with the same information. Edit both in the same change.
- A record describes only this repository. A changelog entry, a task, a wave background, a comment and a commit message state a defect as a fact about this repository: the input, the behaviour and the expected behaviour. They name no other product, no user of this repository, no reporter and no source of a decision, and a sentence that carries no such fact is deleted. An identifier is named after its role in this repository.
- One authoritative document per topic. The protocol contract is in `docs/spec/`. Implementation and verification status is in `docs/features.md`. Planned tasks, their verification commands and their completion are in `docs/plans/execution-checklist.md`; every change belongs to a task there, and a task is added before its work starts. Current procedures are in `docs/operations/`. Actual changes and their verification results are in `CHANGELOG.md`.
- Documents describe current behavior. When the direction changes, change the specification first and mark parts that are not implemented.
- A behavior change, its documents, its feature status row and its changelog entry are one change.
- `make documents-check` verifies, as `config/documents.json` declares, document pairs, the markers `doc-id` (the same in both files) and `source-sha256` (in the Korean file, the sha256 of its English file), links and identical code blocks. Content accuracy is verified by reading the code and the tests.

## Implementation

- Do not keep backward compatibility. Remove old paths instead of adding compatibility layers, fallbacks or migrations.
- Use the simplest implementation that fully meets the current requirements. Do not add abstractions, configuration or indirection for uncertain future needs.
- Separate concerns into modules. Split a file that has more than one responsibility.
- Do not use temporary scripts or folders. Every check is a Makefile target, a script under `scripts/`, or a committed test, and is idempotent.
- A result depends only on the tree, the template release that the manifests and their locks pin and the commit of the tag `TEMPLATE_TAG` (`v0.0.5`) of the template repository, and the php-ext release asset of that tag that `config/template-ext.json` pins by its sha256, which `make install` fetches and `make ext` builds. Every input from outside the repository is named in a tracked file and verified before use: a package by its exact version and the integrity or shasum of its lock, the template repository by its tag (`TEMPLATE_TAG` of the Makefile, HY-80), a build output by the hash of its inputs. A dependency is declared in `package.json` or `composer.json` and installed by npm or Composer from its lock (HY-70). Until version 0.1 a dependency on another polyspec repository is a GitHub tag of that repository or an asset of its GitHub Release, never a branch or a commit. No tracked file names a Git commit, of this repository or of another. The guard of the full run keys a run by the tree and by the key `template`, the commit of the tag `TEMPLATE_TAG` that the Makefile reads from the template repository, and records both only in the ignored `var/full-run.json`. A mismatch fails with the expected and the actual value. No check reads the working tree of another checkout as it happens to be.
- Every tool whose release changes a result is pinned in a tracked file and checked before use (HY-81): `.node-version`, `.php-version`, `.python-version`, `packageManager` and `config/toolchain.json`. A tool is pinned as exactly as its results require: PHP and Python by their minor and make not at all, because its expansions are the same under 3.81 and 4. Tools are installed into the checkout (`var/tools`), never into the machine, whose tools every checkout and session shares; a download is used only with its pinned digest, and no tool installs another tool on first use. A recipe or a script starts a tool of the checkout by its absolute path, because make looks up a recipe line without shell syntax on its own `PATH`.
- No result depends on a live service or on time (HY-89): no check makes a registry query whose result depends on time, such as a latest lookup, the resolution of a version range or a query for outdated packages or new releases, and no check queries another live service; a download of a package that a lock pins by its exact version and integrity is installation and is allowed, as `npm ci` and `composer install` do; installs follow their locks without an audit, a test orders events by events or an injected clock and never by racing timers, and a server of a run listens on a port that the system assigns and reports. Every recipe runs npm and Composer offline (`npm_config_offline` and `COMPOSER_DISABLE_NETWORK` of the Makefile); only `make install-tools`, `make install`, `make install-browser` and `make kit-sync` download, through `$(ONLINE)`, and a missing download fails with the install target that makes it, never with the advice of a tool to retry online. A long operation, such as a server start, waits without a time limit and prints its progress.
- Performance is measured and reported and never fails a check: a size or a time above its limit prints a `WARNING` line with the value and the limit, an annotation `::warning::` on GitHub and a warning in the CI summary, and the check passes (`make bundle-size`, `make bench`). A measuring script fails only for a usage error or a missing input.
- Every GitHub workflow runs its jobs on `ubuntu-26.04-arm`, pins each action by its commit, sets no `timeout-minutes`, and runs every command of a step as one make target, never a script or a tool directly, so the settings and the checks of the Makefile apply to it (HY-90).
- An output that another process may read while it is written again is published without a missing or partly written file (HY-82): a file with one rename (`writeFileAtomic`), a directory from a staging directory of the writing process file by file (`scripts/publish.mjs`). No recipe removes an output and then writes it. A resource that two processes may write at once, such as a package manager install or the full run, is held with a lock of `scripts/kit/holder-lock.mjs`, and every other resource of a run, such as a port, a database or a temporary directory, belongs to that run alone.
- A check reads tool output in a form that the context of the run and an unpinned release do not change (HY-83): a make dry run through `dryRun` of `tests/scripts/make-dry-run.mjs`, a machine-readable form where the tool has one, and other text only of a tool pinned by HY-81.
- A check passes only when it checked something (HY-84): a test run with no test that ran, a selection or a list that selects nothing and a node test file that awaits at its top level fail. A failure states where it is reported what was expected, what happened and the output that shows the cause; a timeout names the step, and the full run prints the last lines of each failed target.
- A test creates what it reads (HY-85): it copies the tracked files of a fixture into its own temporary directory, and an input that another target writes, such as an install or a build, is named with `requireBuilt` and that target before the test reads it. A build output holds no absolute path of its checkout, and no build directory is shared between checkouts.
- A run of several checks runs every check to its end and then fails, naming each failed check (HY-86): a recipe uses `$(call check,...)` and `$(checks_result)`, a make with several checking goals runs with `-k`, and a CI step after the first runs with `if: ${{ !cancelled() }}`. Only steps that read the output of an earlier step stop at its failure.
- No process or file of a run outlives it (HY-87): a run owns its servers and its temporary directory from their creation and stops, awaits and removes them on its end, its failure and SIGINT and SIGTERM, and a test removes a directory only after the processes that use it have exited.
- Every tracked path has owners in `config/owner-checks.json` (HY-88): a change that adds a path adds its owner rule, and a test that copies part of the repository copies what that part imports.
- The shared tools are `scripts/kit/` and `tests/kit/`, the copy of the tag `v0.0.9` of the repository `polyspec/kit` (`kit.json`, `.kit/kit.lock.json`). A file of them is changed only in kit and copied with `make kit-sync KIT_TAG=<tag>`; `make kit-check` fails for a changed, missing or extra file. This repository differs from another only in `config/*.json` and in its own scripts, and a defect or a missing feature of a shared tool is reported to kit, not worked around here.
- Keep code and tests in separate directories inside each package.
- Handle a defect by adding a failing test that reproduces it, fixing the code, and keeping the test.
- Use repository-relative paths. Require explicit paths for external inputs.
- Do not use symbolic links. Package managers install every dependency, also a package of this repository, as a copy, and no bin link, and a changed copy of a package of this repository or of the template copy is published file by file (`scripts/publish.mjs`, HY-82); a recipe starts a tool with the file of its package (HY-79).
- Template syntax and rendering rules belong to the template language. This repository uses them and does not change them.

## Decision and acceptance rules

- Define the invariant, acceptance condition and failure condition in `docs/spec/protocol.md` before changing an implementation. Tests cite the rule identifiers (`HY-n`).
- Never weaken, skip or remove an accepted condition to make a failing implementation pass. Fix the implementation.
- Server rendering and browser rendering of the same region must produce the same bytes. `make parity` is the evidence for that invariant.
- Use the latest stable dependency release that supports the declared runtime range. Record every exact pin with its reason and its removal condition in `docs/operations/dependencies.md`.

## Changes and history

- Write commit messages, comments, documents and translations in direct language: name the action, state the subject and the object, explain a cause in one sentence, and do not use figurative or colloquial wording. Provide the same information in English and Korean.
- A commit message is written in English as `type(scope): Subject (#task)`, a blank line, then a body that states what changed and why, wrapped at 72 characters. The type is one of `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`. The subject has at most 50 characters, starts with a capital letter, is imperative and ends without a period.
- Work may be done on `main` directly. A branch or worktree, used for an agent or when the situation needs one, is named `{type}/{shortname}-{task id}` and `{project}-{shortname}-{task id}`, and is removed as soon as it is merged into `main`.
- Test code that cannot be merged into `main` is removed before the commit, or cherry-picked when it is worth keeping. When it cannot be removed at once, a checklist sub-item records it with its removal condition.

## Required checks

- During development and before a commit, run only the Red and Green unit tests of the change and `make documents-check`. Do not run `make owner-check`, `make check` or an end-to-end check, such as Apple `container`, a browser, parity or a server of a run, locally before a commit or a push: CI runs them after the push.
- Before marking a task `[o]` in `docs/plans/execution-checklist.md`, run the verification command of the task on the committed tree. The Verification column names the command that owns the task, not `make check`; rows that are already `[o]` keep their command.
- No local `make check` is required before a commit or a push. When one runs, it runs once per tree and template commit, when every active task is done, and never for each fix or each task. The guard `scripts/kit/full-run.mjs` enforces this before any step: `make check` is refused while a task is `[~]`, while tracked changes are uncommitted, and when `var/full-run.json` records a full run of the current tree and template commit; `make rerun-failed` reruns only the targets of the current tree and template commit that did not pass (`docs/operations/development.md`). Mark a feature implemented in `docs/features.md` only after a full run of its targets passes: a run of `.github/workflows/ci.yml`, or a local `make check`.
- For the push of `main` and every manual run (`workflow_dispatch`), GitHub runs the full suite in the jobs of `.github/workflows/ci.yml`, one per CI group, every target to its end; each job writes the job summary and uploads the report `var/ci/<name>/` with the status, the time, the first failure lines and the full log of each target (HY-91). This is where the full suite and the end-to-end checks run; fix every failure that it names before the next push. Known limit: the CI runner is Linux, so `make virtiofs-check`, the target of the full suite on Darwin only (`DARWIN_TARGETS`, HY-68), runs only when someone runs a local `make check` on a Mac.
- A push happens only when no task of `docs/plans/execution-checklist.md` is `[~]`, and that is the only gate before a push; it runs no test, neither in a pushed commit nor in the working tree. The tracked pre-push hook `.githooks/pre-push`, which `make hooks` writes, runs `node scripts/kit/push-gate.mjs hook`, which refuses such a push and names each active ID with its task. Every `make` run sets `core.hooksPath` to `.githooks`; `make hooks-check` and the guard of the full run fail while it is not set or the hook differs. `make push-gate-commit COMMIT=<sha>` runs the same gate on a commit for a push that skipped the hook, and the CI group `docs` runs it (`docs/operations/development.md`).
- Until version 0.1 a change is checked by the unit tests that own it, and `main` is pushed once, when every task of the checklist is `[o]` (HY-94): there is no pull request, no merge queue and no GitHub ruleset, and the push is `git push origin main`. The push of `main` runs `.github/workflows/ci.yml`, whose last job `ci-passed` passes only when every other job of the workflow passed; the CI run of that push is the evidence of the commit, and a release tag is set only after `ci-passed` succeeded for the tagged commit (`docs/operations/development.md`).

## Release

- Until version 0.1 `main` is pushed once, when every task is done, and the CI run of that push is the evidence of its commits. A release is a tag of a commit of `main` whose CI run concluded `ci-passed` success (HY-95), and only the maintainer creates, moves or pushes a tag.
- Every change adds its entry under `## Unreleased` at the top of `CHANGELOG.md` and `CHANGELOG.ko.md`.
- The version-bump commit `chore(release): Release X.Y.Z (#<task>)` sets the version X.Y.Z in `package.json`, `packages/hyper-client/package.json`, `packages/hyper-server-node/package.json`, `packages/hyper-build/package.json`, `packages/hyper-server-php/composer.json` and `packages/hyper-python/pyproject.toml` and `tests/package-install/package.json` with its lock, the requirement of `@polyspec/hyper-client` in `packages/hyper-server-node/package.json` and `packages/hyper-build/package.json` and of `polyspec/hyper-server` in the private root `composer.json` and `examples/board/composer.json` with its lock, and the consumer projects of `tests/release-install`, whose manifests and locks `make release-consumer-lock TAG=vX.Y.Z` writes after `make release-assets TAG=vX.Y.Z`, and renames `## Unreleased` of both changelogs to `## X.Y.Z`, with a new empty `## Unreleased` above it.
- The maintainer tags the commit of `main` `vX.Y.Z` after its CI run concluded `ci-passed` success and pushes the tag. The push runs `.github/workflows/release.yml`, which requires the tagged commit on `main` with the check `ci-passed` passed, the version in every manifest and the section `## X.Y.Z` in `CHANGELOG.md` and `CHANGELOG.ko.md`, builds the package archives, named `<package>-<language>-<version>.<ext>`, and creates the GitHub Release (`docs/operations/development.md`).

## Checklist

- This repository has one checklist, `docs/plans/execution-checklist.md`. Split a task into sub-items or add tasks to it; do not create another checklist. Every repository keeps its own checklist.
- A task has one of four states: `[ ]` waiting, `[~]` in progress, `[o]` done, `[!] cause: <cause>; retry: <condition>` bypassed. `make documents-check` accepts no other state.
- A task state marker, also an x or a capital X between brackets as Markdown task lists write it, appears in the checklist only as the state of a task row, at the start of its last cell. The checklist has no legend; its texts name states in words. `make documents-check` fails for any other marker and names its file, line and column.
- The checklist holds only headings and task tables, and `make documents-check` fails for any other line with its file, line and column. Each wave is a heading `## Wave <n> — <title>`, whose wave name links the section `wave-<n>` of `docs/plans/waves.md`, followed by a table with the columns ID, Task, Verification and Status. A task ID has the form `H<wave>.<number>`, and a task row starts with it. `docs/plans/waves.md` holds the dependencies and the background of each wave; a wave starts when the waves that it names as dependencies are done.
- A task changes the specification first, then adds failing tests that cite the rule identifiers, then changes the implementation.
- `[!]` is used only when the next task cannot proceed without bypassing this one. When the retry condition holds, resume the task without waiting for approval. `[!]` is not done. An audit covers only the `[!]` tasks with their causes and retry conditions and does not repeat unrelated full test runs.
- A new problem gets a new task. A problem related to a task that is `[o]` gets a sub-item with the next derived ID (`H5.2-1`, `H5.2-2`) that goes through `[~]` and `[o]`; the `[o]` task keeps its state.
- Independent tasks may run in parallel, but finishing a task in progress comes before starting a new one: the number of `[o]` tasks grows, not the number of `[~]` tasks.
- Uncommitted changes never span more than one task. When a task becomes `[o]`, its changelog entry and its commit are made in the same unit of work.
- A received instruction is classified first: a task of the checklist, a rule of this file, a note of the agent memory, or an answer only. The agent memory holds only what the requester and the agent need between sessions; what the project must keep goes into the repository (documents, comments, commit messages). Unless the instruction states that it is urgent, record it as a task with its priority and continue the task in progress. Rules belong in this file without duplication, never in the checklist or the changelog.
- Korean documents write technical terms in English and only the surrounding text in Korean.
