# Repository rules

[한국어](repository-rules.ko.md).

These rules govern how this repository builds, installs, checks and releases its packages. They are not part of the region protocol of `docs/spec/`, which every server implements; the tests of the build commands and of the repository tools (`packages/cli`, `tests/scripts`) cite them by their ids `HR-n`. The numbers are those that the rules had in the protocol document, so the changelogs and plan records that name `HY-n` for these rules keep their meaning.

## Build and assets

- **HR-34** One run of `hyper build` (HR-96) writes the following outputs and computes the build id (HY-125) once. Below `public/assets` of the application the build adds files whose names contain a hash of their content, and `client/assets.json` lists the files of each build. The files of the build before stay, so a server or an open page of that build still loads every file of it. A build whose list differs from the list of the build before it removes, after it published its outputs, exactly the files of the build two lists back: those that `client/assets.previous.json` named and that neither the list of the build before nor its own list names, and it prints each (HYC-16.17, HYC-16.18). A build of unchanged sources moves no list and removes nothing (HYC-16.19). The build removes no other file, so a file that the application placed there stays, and a build with fewer than two earlier lists removes nothing (HYC-16.20). Before it writes a file it records every path of the three lists in `client/assets.previous.json`, and it removes only after the publish, so a build that ends early leaves no file without a list and no list that names a missing file (HYC-16.21). An earlier list of another form fails the build before it writes (HYC-16.22). Below `--output` the build owns only `client/` and `program/`, which it publishes as directories (HR-82); it neither reads nor removes any other file there.

  | Path | Consumer | Content |
  |---|---|---|
  | `<app>/public/assets/templates/<name>.<hash>.json` | browser | one AST file per template, `hyper/data.tpl` included |
  | `<app>/public/assets/hyper-<hash>.js`, `hyper-chunk-<hash>.js` | browser | the client entry and its chunks (HYC-16), when `client/main.ts` exists |
  | `<app>/public/assets/<name>.<hash>.<extension>` | browser | each asset of `--asset` and `--tailwind` (HR-77) |
  | `<output>/client/manifest.json` | the layout code of the application | the URL of the entry as `hyper` and the URL of each asset by its name (HYC-16) |
  | `<output>/client/assets.previous.json` | the next build, for the removal (HYC-16.18) | `{"files": [...]}`, the files of the last build before this one whose list differed; the build id leaves it out (HY-125.25) |
  | `<output>/client/assets.json` | the next build, which keeps the files of this build for one different build more (HYC-16.18) | `{"files": [...]}`, every path `public/assets/...` that this build wrote, in byte order |
  | `<output>/client/templates.index.json` | the checks of a build | each template name with its file URL; the client bundle holds the same index |
  | `<output>/client/csr/` | static deployment, `ClientRendering` of HY-62 | the static shell `index.html`, `assets/` with the copies of the files of this build and the `--static` files, when `client/main.ts` exists and `--api` is given |
  | `<output>/program/` | the three servers | `templates/`, `reads.json` (HY-73) and `build.json` (HY-48.21); no generated PHP program (HY-48.20) |

  The build makes every output in staging directories of its process, computes the id, writes the shell and both `build.json`, and publishes `public/assets`, then `client/`, then `program/`, each `build.json` last. The intermediate files of the PHP compilation lie in a temporary directory of the run and not in `program/`. The index also contains `hyper/data.tpl`. `program/` holds no copy of `hyper/data.tpl`, because the core gives the reserved template to every server (HY-31.9). The client bundle contains the index and the name of `hyper/data.tpl`, and no template. The client imports the index as the module `@polyspec/hyper-client/templates-index`, which the build resolves to the index of the same build; the package declares only its type. `tests/scripts/build.test.mts` checks the outputs.
- **HR-68** `hyper build` and the copies of the scripts of this repository create every file that they copy into their output with the mode 0644 and every directory with the mode 0755, and write the bytes of the source file. They do not create a file with a mode that its owner cannot read, because a virtiofs bind mount of a Linux container (Apple `container`) refuses such a creation with `EACCES`, and `fs.cpSync` of Node creates its destination files with the mode 0200. The modes do not depend on the umask of the process: each file and each directory that a copy creates is set to its mode after its creation, so a process of another user reads every output. `tests/scripts/output-files.test.mts` checks the modes under the umask 077 and, where sudo starts a process as `nobody` without a password, as on the GitHub runner, the reads of another user on every platform; `make virtiofs-check` (`tests/virtiofs/output-files.test.mts`), a target of the full suite on Darwin only (`DARWIN_TARGETS`), runs both copies in Apple `container` with the output on a virtiofs bind mount and fails when `container` is missing.
- **HR-70** `hyper build` and the template build of the test fixtures read the template language from the template packages that `@polyspec/hyper-cli` requires (HR-96), by their package names: the parser, the render runtime and the manifest check bundle use `@polyspec/template`. The build resolves `@polyspec/template` in the client bundle to the same package, whatever template package the application installed. npm installs that package and its platform packages from the tarballs of the template release, which the private root `package.json` names by their URLs (`https://github.com/polyspec/template/releases/download/v<version>/<package>-<version>.tgz`) with `allow-remote=root` in `.npmrc`, and npm resolves the exact version that a package of the workspace requires to the tarball of the root, so no manifest holds `overrides`; `package-lock.json` pins each tarball by its `resolved` URL and its `integrity`, and `npm ci` installs them. The PHP template is the extension `polyspec_template` (HR-78): the Composer manifests require `ext-polyspec_template` and declare the template version for it in `config.platform`, and no Composer lock holds a template package (H31.5). The published manifests `packages/client/package.json`, `packages/ts/package.json` and `packages/cli/package.json` require the exact template version, and `packages/php/composer.json` declares it for the extension. No build takes a template directory: an option `--template-dir` fails as an unknown option. `tests/scripts/template-dir.test.mts` and `tests/scripts/template-copy.test.mjs` check it.
- **HR-77** `hyper build` compiles a stylesheet of the application with Tailwind CSS for each option `--tailwind <source>=<name>`, whose source is a path relative to the application directory, and writes the output as the asset `<name>`, as `--asset` writes a file (HR-96): `public/assets/<name>.<hash>.css`, its copy in `client/csr/assets`, its URL as the member `<name>` of `client/manifest.json` and its path in `client/assets.json`; the layout links it by that member, and no output has a fixed path. The output declares the cascade layers `theme`, `base`, `components` and `utilities` in that order, holds the theme variables and the utility classes of the latest stable Tailwind CSS that the files below `templates/` and `client/` use, and holds the rules of the source unchanged in the layer `components`, so a utility class overrides them. It holds no rule of the layer `base`, so an element looks as the rules of the application and the browser give it, as without Tailwind CSS. The build fails before it writes any output when the source cannot be read or Tailwind CSS refuses it. A stylesheet whose relative `url()` names another file is written by the application with the files that it names as `--asset` inputs or with absolute URLs, because the hashed name moves the stylesheet. `tests/scripts/build.test.mts` builds an application whose template uses a utility class.
- **HR-96** The command tool is the npm package `@polyspec/hyper-cli` with the one bin `hyper` and its subcommands `hyper build` (HY-48, HY-73, HY-125, HR-34, HYC-16, HR-77) and `hyper check` (HY-2, HY-48.3). A non-interactive caller may rely on the bin, its arguments and its exit code, 0 for success and any other code for a failure, and on nothing else: the text of stdout and stderr and the modules of the package are no interface. A usage error, an unknown subcommand or an unknown option exits with 2.
  - Input: one application directory `--app`, which holds `app/app.json`, `templates/`, optionally `client/main.ts`, and `public/`; `examples/board` follows it.
  - `hyper build --app <directory> --output <directory>` takes the options `--api <base path>` (the data base path of the static shell, HY-62; the shell is written only when `client/main.ts` exists and `--api` is given, and `--api` without `client/main.ts` fails), `--asset <name>=<path>` (a file of the application written without change under a hash name, HYC-16), `--tailwind <source>=<name>` (HR-77) and `--static <path below public/>` (a file copied without a hash into the shell, HYC-16; it needs the shell). It refuses the option `--php-namespace` of earlier releases by its name, with a usage error that says to remove the option and its value from the command, because the build writes no generated PHP program (HY-48.20). The asset names follow HYC-16.13. Every option is checked, and the manifest (HY-2) and the template rules (HY-48.3) pass, before the build writes any output. It takes no build id (HY-125.21).
  - `hyper check --app <directory>` checks the manifest and the template rules only, writes no file and reads no output.
  - The documents name a call after an install as a devDependency from the release archive, as a `package.json` script or as `npm exec --package=@polyspec/hyper-cli -- hyper build`; `npx hyper` and `npm exec hyper` without an install run the unrelated public package `hyper` of npm, so they are not used.

  The package is released as `polyspec-hyper-cli-X.Y.Z.tgz` with the other packages (HR-95). Its `files` are `bin` and `lib` and its `exports` only `./package.json`, and its modules import only the files that it publishes, built-in modules of Node and the packages that its manifest requires at exact versions: `@polyspec/hyper`, whose entry `@polyspec/hyper/build` gives the manifest check, the reserved template `hyper/data.tpl` and the read paths of `reads.json`, which it computes with the Rust core (HR-61, HY-73.34), so that a build and the servers apply one implementation of these rules and the build needs the native addon of its platform, the template packages (HR-70), esbuild and Tailwind CSS. The package does not require `@polyspec/hyper-client`: `hyper build` bundles the client code of an application, whose import of `@polyspec/hyper-client` resolves from the dependencies of the application, so the application declares that package. The source lies once in `packages/cli`: the Makefile runs the bin by its file (HR-79) and the scripts of this repository import its modules from there, with no copy and no rewrite when it is packed. The bin takes only the inputs and the outputs of an application; no option names a path of this repository. `tests/scripts/package-source.test.mts` checks the imports and `tests/scripts/cli.test.mts` the subcommands, the exit codes and the options.

## Packages

- **HR-61** The npm packages `@polyspec/hyper-client` and `@polyspec/hyper` publish JavaScript modules with type declarations, which `make packages` writes to the `dist` directory of each package. The `exports` of each package name `dist/index.js` and `dist/index.d.ts` as its entry, and the package contains only `dist` of its build output; `@polyspec/hyper-client` also exports the declaration `templates-index.d.ts` (HR-34) and the data file `data-template.json`, the source of the reserved template `hyper/data.tpl` that the builds read (HR-96), and `@polyspec/hyper` also exports the entry `./build` (`dist/build.js`, `dist/build.d.ts`), the rules of the Rust core that the command tool applies in a build: `readsFile` gives the text of `reads.json` for the JSON text of a manifest and the template sources by their names (HY-73.34, HY-73.32), so Node runs it from `node_modules`, where Node does not strip types, without a bundler. Their TypeScript source uses only syntax that can be erased (`erasableSyntaxOnly`), and the declarations type-check in a package that sets `erasableSyntaxOnly`. `make package-check` installs both packages into `tests/package-install` with `npm ci --offline` from its `package-lock.json` (HR-89), which links them to their directories in this repository, type-checks its test against the declarations and runs it under `node`; the test checks that each package exports `dist/index.js` and that the archive that `npm pack` lists holds the build and the declarations and no `src`.
- **HR-79** npm installs with its own defaults. The root `package.json` declares the npm workspaces `packages/client`, `packages/cli` and `packages/ts`, which npm links into the root `node_modules`, and `@polyspec/template` by the URL of its tarball, to which npm resolves the exact version that the workspaces require; `.npmrc` sets no `install-links` and no `bin-links`. `make packages` builds each npm package into its `dist`, which the link shows at once. The recipes start the tools through the bin links of npm (`node_modules/.bin`) by their absolute paths, and each npm package declares its build as `tsc -p tsconfig.build.json`, so `npm run build` in `packages/client` or `packages/ts` compiles it; `tests/scripts/package-build.test.mts` checks that `npm exec tsc` finds the compiler and builds each package so. `tests/package-install` installs the npm packages with `npm ci`, which links each to its directory (H23.8). The private root `composer.json` installs `packages/php` for development into the root `vendor`: its autoload maps the namespaces of `packages/php/src` and `packages/php/tests`, so the tests run the tree. Composer installs `polyspec/hyper` in the root and in the board from the path repository `packages/php` with its default, a symbolic link to the package directory, so the board runs the source of the checkout. Each polyspec package that a path repository of the root or of the board provides is a symbolic link to its source directory in the `vendor` of that project. `make hyper-php-install` runs `composer install` of the board under `var/install.lock`. `tests/scripts/no-symlinks.test.mts` fails when such a package in a `vendor` is a directory copy or links to another directory; third-party packages are not checked.
- **HR-98** The name of every package of this repository states its role. The server library, the package of the main specification, carries the name of the repository, `hyper`; the browser package is `hyper-client` and the command tool `hyper-cli` (S5, S10 of kit). `server` is the role of the specification and no package name. Its directory below `packages/` carries no repository prefix: the server library holds one directory per language, the npm package `@polyspec/hyper` in `packages/ts`, the Composer package `polyspec/hyper` in `packages/php` with the PHP namespace `Polyspec\Hyper`, the Python distribution `polyspec-hyper` in `packages/python` with the import package `polyspec.hyper`, and its Rust core, the crate `polyspec-hyper`, in `packages/rust`; the npm package `@polyspec/hyper-client` sits in `packages/client` and the npm package `@polyspec/hyper-cli` in `packages/cli`. The native module of a language package sits in `native/` of its directory (binding L-2a): the PHP extension `polyspec_hyper` is the Composer package `polyspec/hyper-native` in `packages/php/native`, the Python module is `polyspec.hyper._binding._native` from `packages/python/native` and the Node addon `hyper.<target>.node` from `packages/ts/native`. `packages/` holds no other directory. `config/release.json` releases each npm and Composer package from its directory, except `@polyspec/hyper`, which the recipes of binding release with its native modules, and names the manifests of `@polyspec/hyper` and of the Python distribution, which the recipes of binding release (H35.35-2, H35.35-3), so the GitHub label of a release archive (HR-95) states the product and the runtime of its package, such as `polyspec-hyper-client-ts-X.Y.Z`. `tests/scripts/package-names.test.mts` checks the manifest and the release entry of each package and the manifest of `polyspec/hyper-native`.

## Toolchain and checks

- **HR-55** `make server-parity` runs the steps of `examples/board/tests/parity/requests.json` against the PHP server and the board Node server at the same time, each with its own empty database and session and with the same creation time of posts (`BOARD_TIME`). For every request of the steps, the HTML document, the document JSON and the region JSON alike, the status, the headers and the body of both responses must be equal. Before the comparison it replaces the session identifier in the session cookie with `<session>`, the masked CSRF token of each response (HY-24) with `<csrf>` in headers and bodies, and the `ETag` value with `<etag>` after it checks that the value is the tag of its body (HY-53), because the body contains the masked token; the session token for that check is the second half of the masked value XOR its first half. It leaves out the headers that the HTTP server program writes by itself: `Date`, `Connection`, `Keep-Alive`, `Content-Length`, `Transfer-Encoding`, and the `Host` and `X-Powered-By` of the PHP built-in server. Headers are compared as a set of name and value pairs, and `Set-Cookie` with each of its values. The same run also performs the browser comparison of `make parity` against the PHP server.
- **HR-78** This repository builds the native template extension from the php-ext package `polyspec/template` of the template release `TEMPLATE_VERSION`, which the Composer repository of the release (`packages.json`) names with a pre-packaged binary for each platform (H14.1-7, H27.45, H31.5). `make hyper-install` runs `make template-ext` through `$(ONLINE)`: its recipe runs PIE itself, which adds that repository and builds the package for the PHP of `PATH` in an empty `var/pie/polyspec/template`, and publishes the one library that PIE recorded there, which `scripts/pie-binary.mts` names, to `build/ext/polyspec_template.so` (H27.51). `make ext` builds nothing and only requires that library, and PHPStan reads no stub of the extension (H25.60). No recipe reads or copies the template repository for the extension, and no recipe builds in it. `tests/scripts/template-ext.test.mts` checks it.
- **HR-80** Release declarations pin the assets of the template release (`v0.0.31`), not a tracked Git commit, and each install verifies every template asset that it installs by its integrity: npm by the sha512 of `package-lock.json` and `tests/package-install/package-lock.json` and uv by the sha256 of `packages/python/pyproject.toml` and `packages/python/uv.lock`. The Composer repository of a release names the php-ext zip and the platform zips with no shasum, so `config/php-ext-pins.json` pins the sha256 of each platform zip of `polyspec_template`, `polyspec_json` and `polyspec_session_store`, by PHP minor and platform, from the field `digest` of its release asset, Composer inside PIE downloads the platform zip into its cache as `files/<package>/<sha1 of the URL>.zip` and reuses a zip of the cache of the machine, so `make template-ext` and `make json-ext` set `COMPOSER_CACHE_DIR` to `cache` of their empty PIE working directory and run `scripts/php-ext-verify.mts` after `pie build`, which fails before the library is published for a zip whose sha256 differs, naming the file, the actual and the expected sha256, for a zip of no pinned URL, and for a cache without a zip (H35.51). The same file pins the sha256 of the release asset `packages.json` of the template and the json release from its field `digest`; before PIE, `scripts/php-ext-requires.mts` downloads each into `repository/<package>/packages.json` of the PIE working directory and fails naming the file, the expected and the actual sha256 when they differ, before anything reads it, and PIE adds that verified copy as its repository, not the URL; the trap of the recipe removes it (H35.54). A run of `make template-ext`, with `make json-ext` before it, verified the zips of json 0.0.34 and template 0.0.29, the pins before json 0.0.38 and template 0.0.30, for PHP 8.4 on `arm64-darwin` (H35.52). No check, CI job or release step checks out the template repository. Local development uses declared installed-source links; final verification records its tree and runtime versions in the ignored native report. `tests/scripts/template-pins.test.mts` checks each pin and `tests/scripts/template-version.test.mts` the one release version.
- **HR-81** Every tool whose release changes a result of this repository is pinned in a tracked file: npm in `mise.toml` as `npm:npm`, with its digests in `mise.lock`, which `devEngines` of `package.json` names (kit K938), PHP by its minor release (`8.4`) in `.php-version`, and Node.js, Python, Composer and the other tools of mise in `mise.toml`, with their digests for every platform in `mise.lock` (kit K127). `make install-tools TOOLS=npm` installs mise, the Node.js of `mise.toml` and npm, and `make install-tools` the tools of `mise.lock`, into the ignored directory `var/tools` of the checkout and never into the machine, because a machine-wide tool is shared by every checkout and session and an install for one replaces the tool of the others; it uses a download only when its digest equals the pin. `var/tools/bin` holds `node`, `npm` and `npx` and `var/tools/mise/shims` the commands of mise, `python3` and `composer` among them, which the Makefile puts first on `PATH` for every recipe and the programs that it starts. Recipes and scripts start Node.js, npm, Composer and Python by those absolute paths (`$(NODE)`, `$(NPM)`, `$(COMPOSER)`, `$(PYTHON)`), because make 3.81 looks up the program of a recipe line without shell syntax on the `PATH` of its own process and not on the exported one. A PHP patch release of the pinned minor passes; Python is pinned to its exact release. make is not pinned: the expansion of every target gives the same commands under GNU Make 3.81 and 4, and the recipes start npm and Composer by their absolute paths, which make 3.81 needs. A tool that is missing fails the target that runs it (kit K854). `make ext` builds the native extension with phpize and php-config of the PHP of `PATH`, the PHP that the checks run. The CI jobs start the bootstrap with the Node.js of `mise.toml` (`node-version-file`) and set up PHP from `.php-version` (`php-version-file`) and install the tools of mise with `make install-tools`, and the record of a CI run names the running release of each tool. The tools are tested in kit; `tests/scripts/toolchain.test.mts` and `tests/scripts/template-copy.test.mjs` check the recipes.
- **HR-82** An output that another process may read while it is written again is published without a missing or partly written file. A single file is written to a file of the writing process next to it and moved into place with one rename (`writeFileAtomic` of `packages/cli/lib/output-files.mjs`): the template files, the index, the manifest and the scripts of the asset build, the stylesheet of `--tailwind` and the index of the template build. A directory is written into a staging directory of the writing process (`<target>.next-<pid>`) and published by `publish` of `packages/cli/lib/publish.mjs`: each file moves into the target with one rename, the files that readers open first last, and then the files that the new output does not have are removed. It publishes the declared template copy (`copy.json` last), the server program (`reads.json` and then `build.json` last), the static deployment `csr/` (`index.html` last) and the `dist` of each npm package; a reader finds the previous or the new version of each file and never a missing one, and a reader of several files during one publication can combine files of the two versions. The PHP server package in the vendor of the board is a symbolic link that Composer creates, so it has no publication of its own: `make hyper-php-install` runs `composer install` of the board under `var/install.lock` (HR-79). Two writers of one output both succeed. The package manager installs of `make hyper-install` hold the lock `var/install.lock`, and a full run holds `var/report/full-run.lock` (`holder-lock` of `@polyspec/kit`): a second holder fails with the first, and a lock of an ended process stays until `node node_modules/@polyspec/kit/dist/holder-lock.mjs clear <lock>` removes it. `tests/scripts/publish.test.mts`, `tests/scripts/toolchain.test.mts` check it.
- **HR-83** A check that reads the output of a tool reads a form that does not change with the context of the run or with a release that is not pinned. A make dry run starts make without the variables of a calling make (`MAKEFLAGS`, `MFLAGS`, `MAKELEVEL`, `MAKEOVERRIDES`) and with `--no-print-directory`, through `dryRun` of `tests/scripts/make-dry-run.mts`, so the lines `make: Entering directory` of a make that runs inside another make or with `-w` never reach the assertion. A machine-readable form is read where the tool has one, such as `git status --porcelain` and `--version`; no script parses the JSON of `npm pack`, whose shape changed between npm 11 and npm 12 (HR-80). An assertion on text that has no such form, such as the start line of the PHP built-in server or the list of Playwright, reads a tool pinned by HR-81. `tests/scripts/make-dry-run.mts` removes inherited make variables before each dry run. A dry run runs no command of a recipe: make runs a recipe line that names `$(MAKE)` under `-n` too, with every other command of that line, so each such line is one make call and nothing else, and a condition of that call is a line of the recipe that the called make runs (`php-check-installed` of `install-tools`). `tests/scripts/make-recursion.test.mts` checks it.
- **HR-84** A check passes only when it checked something, and a failure states its cause where the result is reported. A test run of `run-tests` of `@polyspec/kit` fails when no test passed, failed or ran out of time, as when no file, no test or no name pattern selects one, and prints `no test ran`; the progress reporters of node and vitest give the runner their counts through the file of `KIT_TEST_RESULT`, and PHPUnit also fails an empty suite (`failOnEmptyTestSuite`). No node test file awaits at its top level, because `node --test --test-force-exit` ends a file when its registered tests end and never runs a test registered after such an await. `scripts/check-parity.mts` fails for a request file without a status or a compare step and, with `--node`, when the Node server answered no compared request. The native final runner records failed-target evidence in its record and summary and preserves each target log. Every line of a log starts at column 0: a check of a recipe runs through `scripts/line-end.mts`, and the full run and the CI report pass on complete lines only, each ending a stream that a tool left without a final newline with one, so no line-based reader finds two lines joined. `tests/scripts/check-parity.test.mts` check it.
- **HR-85** A test creates what it reads, or names it as the output of another target before it reads it. A test copies the tracked files of a fixture into a temporary directory (`copyTracked` of `scripts/tracked-files.mts`) instead of the fixture directory, which may hold the output of an earlier run. A test that reads an install or a build of another target, such as `node_modules`, the `dist` of `make packages`, the `vendor` of `make hyper-install`, calls `requireBuilt` of `tests/scripts/requires.mts`, which fails with the missing path and the make target that writes it; the asset and template build tests read the template package that npm installed (HR-70). A build output holds no absolute path of the checkout that writes it, and the native extension builds in a temporary directory of the run and is published into `build/ext` of its own checkout. `tests/scripts/build-assets.test.mts`, `tests/scripts/template-dir.test.mts` and `tests/scripts/run-tests.test.mjs` check it.
- **HR-86** A run of several checks runs every check to its end and then fails when one failed, naming each failed check. A Makefile recipe with several checks (`test-js`, `hyper-test-node`, `test-php`, `lint`, `parity`, `bench-server`) runs them with `$(call check,<name>,<command>)`, which prints the command, runs it in a subshell and records its name when it fails, and ends with `$(checks_result)`, which prints `failed checks:` with every failed name and fails. The full run runs each target of `CHECK_TARGETS` with its own `make -k <target>` to its end (H11.1-1). A step of a CI job after its first step runs with `if: ${{ !cancelled() }}`, and a make with several goals that check runs with `-k`. A check that is a make target is no command of `$(call check,...)`, whose line a dry run would run (HR-83), and the goals of one `$(MAKE) -k` are no such checks either, because make passes the output of a goal on without a final newline (HR-84) and names a failed goal only where it failed, not after the last goal. `recipe-check` therefore runs the commands of the five case runners and of the comparison that reads their results with `$(call check,...)`; a variable of the Makefile holds each command for it and for the target that runs that command alone (`recipe-run-*`, `recipe-compare`), and `recipe-check` has the prerequisites of the five runners. A recipe of dependent steps, such as an install or a build, stops at its first failure, because a later step reads the output of the earlier one. `tests/scripts/check-recipes.test.mts` checks it.
- **HR-87** No process or file of a run outlives it. `serverRun` of `scripts/board-servers.mts` gives a run its temporary directory and its server children; every server joins the children when it is spawned, before it reports its address, and `close` stops every child, waits until each has exited and then removes the directory, on the end and the failure of the run and on SIGINT and SIGTERM, after which the process ends with 130 or 143. When a server of the board fails to start, the servers that started have exited before the start rejects. `scripts/check-parity.mts`, `scripts/run-e2e.mts` and `benchmarks/browser.mts` use it, and `scripts/serve-demo.mts` handles its signals before it starts a server. A test removes a directory only after the processes that use it have exited: the demos of `tests/scripts/serve-demo.test.mts` stop in the hook that then removes their directory, `tests/scripts/check-parity.test.mts` runs the check in a process group of its own and kills the group, and `RunTest` releases its server and its log in `finally`. `tests/scripts/board-servers.test.mts`, `tests/scripts/check-parity.test.mts` and `tests/scripts/serve-demo.test.mts` check it.
- **HR-88** Every tracked path has owners, and a change runs the owners of the paths that it touches. `config/owner-checks.json` declares for globs of paths the make targets and the node test files that own them. `make owner-validate` (`owner-check` of `@polyspec/kit`) fails when a tracked or new path matches no rule, a glob matches no path, a target is not a target of the Makefile or runs the full suite, or a test file does not exist; `make owner-check` runs the owners of the changed paths: the uncommitted changes, `PATHS`, or the changes since `BASE`. The node test files run through `make hyper-test-scripts TESTS=<files>`, which writes their inputs first (HR-85). A removed path that no rule owns selects nothing. `.gitignore` ignores no tracked file and every output of the installs, builds, test runs and guards. `tests/scripts/ignored-files.test.mts` check it.
- **HR-89** No result depends on a live service, on the timing of a step or on a resource that a run does not own. No check makes a registry query whose result depends on time: no latest lookup or `@latest`, no resolution of a version range and no metadata query about outdated packages or new releases. A download of a package that a lock pins by its exact version and its integrity is installation and is allowed, as `npm ci` and `composer install` are. npm runs only `ci` with `--no-audit` and `run`, Composer only `install`, both from their locks, and `tests/package-install` installs offline from its tracked `package-lock.json` (`npm ci --offline`); the other downloads are the pinned tools of HR-81, verified by their digests. Every recipe and the programs that it starts run npm and Composer offline: the Makefile exports `npm_config_offline=true` and `COMPOSER_DISABLE_NETWORK=1`, and only the downloads of `make install-tools`, `make hyper-install`, `make hyper-install-browser` (Chromium of the pinned Playwright) and `make hyper-install-virtiofs` (the digest-pinned image) lift them with `$(ONLINE)`; `make ext` downloads nothing, and the php-ext asset is downloaded by `make hyper-install` only (H14.1-7). A test orders its events by events, such as the close of a connection that the server has seen, and never by the race of timers. A server of a test listens on a port that the system assigns and reports, so no process can take the port between its choice and its use: the PHP built-in server of `RunTest` starts on port 0 and the test reads the address from its start line. The start of a server waits without a time limit and prints a progress line every 5 seconds that names the line it waits for and the last line that the server printed. A check over a list fails with the expected and the actual count when the list is empty, such as `scripts/check-bundle-size.mts` without template files. `tests/scripts/toolchain.test.mts`, `tests/scripts/board-servers.test.mts`, `tests/scripts/check-bundle-size.test.mts` and `packages/ts/tests/http.test.ts` check it.

## Workflows and release

- **HR-90** Every job of a GitHub workflow of this repository, the release workflow `.github/workflows/release.yml` included, runs on the declared runner `ubuntu-26.04-arm`, except the jobs `platform` and `php` of `assets.yml`, which run on the runner of each platform of the release (`ubuntu-26.04`, `ubuntu-26.04-arm`, `macos-15`), because the asset of a platform is built and loaded on that platform alone; every job pins every action by its commit with its release in a comment, and has no `timeout-minutes`, because a step is a long operation that the runner logs line by line and judges by its exit code. Every step that runs a command runs one make target, never a script or a tool directly, so the exported settings and the checks of the Makefile apply to it (HR-81, HR-89). Every job of `ci.yml`, `release.yml` and `assets.yml` that runs steps has exactly one run step, `make ci-<job>` with make variables only (`make ci-assets-<job>` in `assets.yml`, `make ci-release-<job>` in `release.yml`): `make ci-check NAME=${{ matrix.name }}` of the job `check`, `make ci-assets-platform RELEASE=${{ inputs.release }}` of the job `platform`, `make ci-release-release TAG=${{ needs.tag.outputs.tag }} VERSION=${{ needs.tag.outputs.version }}` of the job `release` and `make ci-passed RESULTS='${{ toJSON(needs) }}' FAIL_SKIPPED=1` of the judgement job `ci-passed`. A value is a word, a matrix value, an input of the called workflow or an output of a needed job; the JSON of `needs` of `ci-passed` and the quoted expressions of the event of the job `tag` of `release.yml`, which names the CI run that it tags, are the only other expressions; a job whose content is YAML steps, step conditions and expressions cannot be run locally without emulating the runner of GitHub, and a local run `make ci-<job> NAME=<value>` is the call that CI makes. Every other step of such a job is a `uses:` step that provisions the runner or carries the report, and only a `uses:` step has an `if:`: the upload of the report runs with `if: ${{ !cancelled() }}`, so a failed run step still leaves its report (HR-86). The recipe holds the order and the conditions: the setup steps first, stopping at the first failure, then every target to its end, then the report always (HR-91). The recipes of the release, `ci-release-tag`, `ci-assets-<job>` and `ci-release-release`, run their steps in order and stop at the first failure, because each needs the one before it (HR-95). `tests/scripts/ci-workflow.test.mts` checks it.
- **HR-91** The full suite runs on GitHub for the push of `main` and every manual run, in the workflow `.github/workflows/ci.yml`, whose `on:` block is exactly `push` to `main` and `workflow_dispatch`; the release `.github/workflows/release.yml` runs on a completed run of `ci` on `main` and on a manual run (HR-95), and no other workflow exists. No job calls another workflow. The job `check` runs one matrix entry per CI group with `fail-fast: false`; the entries name `CI_GROUPS` of the Makefile, each entry runs `make ci-check NAME=<group>`, and the Makefile declares the tools (`CI_TOOLS_<group>`), the setup steps (`CI_SETUP_<group>`) and the targets (`CI_TARGETS_<group>`) of each group, which `make ci-targets` runs; the targets of the groups are together the targets of `CHECK_TARGETS` of the Makefile, each once, and the group `gates` runs `GATE_TARGETS`, the checkers of kit, and `python` runs the Python unit and render tests. A group gathers the targets that need the same setup, which its `CI_SETUP_<group>` installs: `node` needs only Node.js, `php` also PHP and `make hyper-install-php`, `python` Python (`make hyper-install-python`), `docs` PHP, Python and Redis (`make hyper-install-redis`), `gates` PHP, Python and the PHP symbol extractor, and `board` PHP, Python and Chromium (`make hyper-install-browser`), which no other group installs; the bootstrap of every job installs npm into `var/tools`, and `make install-tools TOOLS="<CI_TOOLS_<group>>"` installs the tools of `mise.lock` that the group selects. `make hyper-install-php` of the groups `docs`, `php` and `board` builds the native extension with PIE, phpize and php-config of the PHP of setup-php (`make template-ext`), and `make ext` only requires the built library. The toolchain comes from the pinned files: Node.js and Python from `mise.toml`, which the bootstrap and `make install-tools` install at the digests of `mise.lock`, and PHP from `.php-version` (HR-81); no job checks out the template repository, and every template asset comes from the release that the locks pin (HR-80, HR-78). `make ci-targets TARGETS="<targets>" CI_REPORT=var/ci/<name>` (`ci-targets` of `@polyspec/kit`) runs each target with its own `make -k <target>` to its end, also after a failed target, without a time limit, and writes the report: `record.json` with the tree, the running releases of the tools and each target with its status, its times and, for a failed target, its first failure lines (the lines that a test reporter marks with `✖` with their indented detail lines, else its error lines, else its last lines, then how make ended); `targets/<target>.log` with the full output; and `summary.md`. No report write stops the run: a failed write is printed and recorded, and the run fails. `make ci-summary CI_REPORT=var/ci/<name>` writes the summary into the report and the job summary, also for a run that recorded nothing or did not record its end, and names each setup step that failed from the outcomes that `make ci-check` passes it (`CI_STEPS`); `make ci-check` runs it after a failed setup step or target too, and the job uploads the report as the artifact `ci-<name>-<run id>-<attempt>` after a failed step. Before the summary, `make ci-results CI_REPORT=var/ci/<name>` copies the case results of the recipe runners, `var/recipe/results/*.txt`, into `recipe-results/` of the report, and a group that ran no runner has none; a runner with failed cases fails with their count, the results file and each failed case line indented on a line of its own, so the first failure lines name the failed cases and the report holds every case (HR-84). `tests/scripts/ci-workflow.test.mts` check it.
- **HR-94** Until version 0.1 a change is checked by the unit tests that own it and pushed to `main` once, when every task of `docs/plans/execution/checklist.md` is done; the repository has no pull request, no merge queue and no GitHub ruleset. A push is not checked, and hyper keeps no Git hook; `make commit` checks the message of a commit. The push of `main` runs `.github/workflows/ci.yml` (HR-91), whose last job `ci-passed` runs after every other job and passes only when each of them has the result `success`; the run of that job on a commit of `main` is the evidence of the commit, and a release requires it of the run whose id it takes (HR-95). `tests/scripts/ci-workflow.test.mts` check it.
- **HR-95** A release is the commit of a successful push or manual run of `.github/workflows/ci.yml` on `main` (HR-94), tagged `vX.Y.Z`; no tag is created, moved or pushed by hand, and no tag push starts a workflow. When the CI run of a push whose tip is the version-bump commit succeeds, `.github/workflows/release.yml` starts by itself and releases that commit (kit K987); the maintainer can start it again with `gh workflow run release.yml -f run=<id>`. `.github/workflows/release.yml` (`on: workflow_dispatch` with the input `run`, permission `contents: write`) has three jobs: `tag`, whose run step `make ci-release-tag` tags the commit; `assets`, which calls `.github/workflows/assets.yml` for the tree of the tag with the release check of binding; and `release`, whose run step `make ci-release-release` builds the archives of kit, publishes the draft, adds the assets of each platform and makes the release public. Each recipe runs its steps in order and stops at the first failure, because each needs the one before it. The tag exists before the jobs `assets` and `release` run and is never moved, so every run of `ci.yml` calls `assets.yml` for its commit with the same recipes and runs `make release-candidate-assets`, which builds the archives of kit from the committed HEAD with no tag: a step that fails after the tag loses the version, so it runs in CI first. The steps are targets of the Makefile, which run the release utilities of `@polyspec/kit` and read `config/release.json`: `make release-tag` requires RUN to be a completed successful push or manual run of ci.yml on `main` whose commit is an ancestor of `origin/main`, read from the GitHub API, reads X.Y.Z from the first section `## X.Y.Z` of `CHANGELOG.md` at its commit (kit K924), creates the annotated tag `vX.Y.Z` (`git tag -a vX.Y.Z -m vX.Y.Z`) at that commit and pushes it, and does not run the tests again. The later steps run on the tag: `make release-tools` installs the tools of the release, `make release-assets` builds the packages and writes the archive of each package that `config/release.json` names in `packages` (`npm pack` for an npm package, the zip of the directory of the tagged commit for a Composer package) and `packages.json` into `var/release/assets`; each archive holds the manifest of the tree unchanged: a published manifest names every polyspec package by an exact version, a package of this repository by the version of the release and `@polyspec/template` and `ext-polyspec_template` by the version of `TEMPLATE_TAG`, and `packages/php/composer.json` declares `version` and no `repositories`; an archive keeps the name its packer gives and carries the GitHub label `<vendor>-<product>-<runtime>-<version>` of the product and the runtime that `config/release.json` declares for its package (kit P39), such as `polyspec-hyper-php-X.Y.Z` for `polyspec/hyper`; `make release-publish` creates the draft GitHub Release of the tag with the archives and the section X.Y.Z of the change log, and `make release-undraft` makes it public. `make release-coverage` fails for a tracked manifest that `config/release.json` does not classify. Each failure names the run, the tag, the check or the file and both values. The tests of the steps are in kit, and `tests/scripts/ci-workflow.test.mts` requires that no workflow starts on a tag push and the trigger of each workflow. git defines annotated tags for releases: they record the tagger and the time, and `git describe` reads them; `make release-tag` refuses a lightweight tag. A published tag is never moved or replaced, so the lightweight tags v0.0.1 to v0.0.4 and v0.0.9 to v0.0.11 stay as they were published.
- **HR-99** The release recipes of the bindings are `packages/release.mk`, which `binding release-recipes` of the binding generator of `package.json` writes for `packages/rust/interface.json` (binding GN-19h, CK-94). `make release-recipes` writes it, each recipe of a job of the release (`ci-assets-<job>`, `ci-release-release`) runs that target before it runs a target of the file, and Git ignores the file, since it is generated. - **HR-100** The generated tests of every binding run the cases of `contracts/` of the members of the core: `make binding-cases` writes the sections that `config/binding-cases.json` names into `var/binding-cases/`, which Git ignores, in the form of a binding case, one key for each parameter of the member and `result` or `raises` with the kind, and `packages/rust/interface.json` names each group in a row of `cases`.
