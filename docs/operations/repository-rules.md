# Repository rules

[한국어](repository-rules.ko.md).

These rules govern how this repository builds, installs, checks and releases its packages. They are not part of the region protocol of `docs/spec/`, which every server implements; the tests of the build commands and of the repository tools (`packages/build`, `tests/scripts`) cite them by their ids `HR-n`. The numbers are those that the rules had in the protocol document, so the changelogs and plan records that name `HY-n` for these rules keep their meaning.

## Build and assets

- **HR-34** The asset build writes every template AST to its own file whose name contains a hash of its content, and an index that maps each template name to its file URL. The index also contains `hyper/data.tpl`. The client bundle contains the index and the name of `hyper/data.tpl`, and no template. Below `public/assets` the build only adds files whose names contain a hash of their content and removes none, so a server or an open page of an earlier build still loads every file of that build; the application removes the files that no build in use names. The build writes its outputs without a hash, the index, the manifest (HYC-16) and the static shell `csr/`, into the directory that the required option `--output` names. The client imports the index as the module `@polyspec/hyper-client/templates-index`, which the build resolves to the index of the same build; the package declares only its type.
- **HR-68** The asset build and the server build create every file that they copy into their output with the mode 0644 and every directory with the mode 0755, and write the bytes of the source file. They do not create a file with a mode that its owner cannot read, because a virtiofs bind mount of a Linux container (Apple `container`) refuses such a creation with `EACCES`, and `fs.cpSync` of Node creates its destination files with the mode 0200. The modes do not depend on the umask of the process: each file and each directory that a copy creates is set to its mode after its creation, so a process of another user reads every output. `tests/scripts/output-files.test.mts` checks the modes under the umask 077 and, where sudo starts a process as `nobody` without a password, as on the GitHub runner, the reads of another user on every platform; `make virtiofs-check` (`tests/virtiofs/output-files.test.mts`), a target of the full suite on Darwin only (`DARWIN_TARGETS`), runs both copies in Apple `container` with the output on a virtiofs bind mount and fails when `container` is missing.
- **HR-70** The asset build, the template build and the server build read the template language from the template packages that `@polyspec/hyper-build` requires (HR-96), by their package names: the parser, the render runtime and the manifest check bundle use `@polyspec/template`, and the server build uses the compiler modules `@polyspec/template-compiler/compiler.mjs`, `ast-artifact.mjs` and `type-manifest.mjs`. The asset build resolves `@polyspec/template` in the client bundle to the same package, whatever template package the application installed. npm installs both packages from the tarballs of the template release, which the private root `package.json` names by their URLs (`https://github.com/polyspec/template/releases/download/v<version>/<package>-<version>.tgz`), with an override of each to the same URL for the packages of the workspace and `allow-remote=root` in `.npmrc`; `package-lock.json` pins each tarball by its `resolved` URL and its `integrity`, and `npm ci` installs them. Composer installs `polyspec/template` from the zip of the template release, which the `package` repository of the private root `composer.json` and of `examples/board/composer.json` names by its URL and sha1; `composer.lock` records that `dist`, and Composer fetches and verifies it itself (H23.11, H27.44). The published manifests `packages/client/package.json`, `packages/server/ts/package.json`, `packages/build/package.json` and `packages/server/php/composer.json` require the exact template version. No build takes a template directory: an option `--template-dir` fails as an unknown option. `tests/scripts/template-dir.test.mts` and `tests/scripts/template-copy.test.mjs` check it.
- **HR-77** The asset build compiles a stylesheet of the application with Tailwind CSS when the option `--tailwind <source>=<output>` names it; both paths are relative to the application directory. The output declares the cascade layers `theme`, `base`, `components` and `utilities` in that order, holds the theme variables and the utility classes of the latest stable Tailwind CSS that the files below `templates/` and `client/` use, and holds the rules of the source unchanged in the layer `components`, so a utility class overrides them. It holds no rule of the layer `base`, so an element looks as the rules of the application and the browser give it, as without Tailwind CSS. The build writes the output with the other outputs, and the build fails when the source cannot be read or Tailwind CSS refuses it. `tests/scripts/build-assets.test.mts` builds an application whose template uses a utility class.
- **HR-96** The build commands are the npm package `@polyspec/hyper-build` with the bins `hyper-build-server` (HY-48, HY-73) and `hyper-build-assets` (HR-34, HYC-16, HR-77), released as `polyspec-hyper-build-npm-X.Y.Z.tgz` with the other packages (HR-95). Its `files` are `bin` and `lib` and its `exports` only `./package.json`, and its modules import only the files that it publishes, built-in modules of Node and the packages that its manifest requires at exact versions: `@polyspec/hyper-client` for the manifest check, the read paths and the reserved template `hyper/data.tpl` (`@polyspec/hyper-client/data-template.json`), the template packages (HR-70), esbuild and Tailwind CSS. The source lies once in `packages/build`: the Makefile runs the bins by their files (HR-79) and the scripts of this repository import its modules from there, with no copy and no rewrite when it is packed. A bin takes only the inputs and the outputs of an application; no option names a path of this repository. `tests/scripts/package-source.test.mts` checks the imports.

## Packages

- **HR-61** The npm packages `@polyspec/hyper-client` and `@polyspec/hyper-server` publish JavaScript modules with type declarations, which `make packages` writes to the `dist` directory of each package. The `exports` of each package name `dist/index.js` and `dist/index.d.ts` as its entry, and the package contains only `dist` of its build output; `@polyspec/hyper-client` also exports the declaration `templates-index.d.ts` (HR-34) and the data file `data-template.json`, the source of the reserved template `hyper/data.tpl` that the builds read (HR-96), so Node runs it from `node_modules`, where Node does not strip types, without a bundler. Their TypeScript source uses only syntax that can be erased (`erasableSyntaxOnly`), and the declarations type-check in a package that sets `erasableSyntaxOnly`. `make package-check` installs both packages into `tests/package-install` with `npm ci --offline` from its `package-lock.json` (HR-89), which links them to their directories in this repository, type-checks its test against the declarations and runs it under `node`; the test checks that each package exports `dist/index.js` and that the archive that `npm pack` lists holds the build and the declarations and no `src`.
- **HR-79** npm installs with its own defaults. The root `package.json` declares the npm workspaces `packages/client`, `packages/build` and `packages/server/ts`, which npm links into the root `node_modules`, and `@polyspec/template` with an override for the dependencies of the workspaces; `.npmrc` sets no `install-links` and no `bin-links`. `make packages` builds each npm package into its `dist`, which the link shows at once. The recipes start the tools through the bin links of npm (`node_modules/.bin`) by their absolute paths, and each npm package declares its build as `tsc -p tsconfig.build.json`, so `npm run build` in `packages/client` or `packages/server/ts` compiles it; `tests/scripts/package-build.test.mts` checks that `npm exec tsc` finds the compiler and builds each package so. `tests/package-install` installs the npm packages with `npm ci`, which links each to its directory (H23.8). The private root `composer.json` installs `packages/server/php` for development into the root `vendor`: its autoload maps the namespaces of `packages/server/php/src` and `packages/server/php/tests`, so the tests run the tree. Composer installs `polyspec/hyper-server` in the root and in the board from the path repository `packages/server/php` with its default, a symbolic link to the package directory, so the board runs the source of the checkout. Each polyspec package that a path repository of the root or of the board provides is a symbolic link to its source directory in the `vendor` of that project. `make hyper-server-php-install` runs `composer install` of the board under `var/install.lock`. `tests/scripts/no-symlinks.test.mts` fails when such a package in a `vendor` is a directory copy or links to another directory; third-party packages are not checked.
- **HR-98** The name of every package of this repository states its role: `hyper-client` for the browser package, `hyper-server` for a server and `hyper-build` for the build commands. Its directory below `packages/` carries no repository prefix (S5 of kit): it is the role, and the server, a component with ports, holds one directory per runtime: the npm package `@polyspec/hyper-client` in `packages/client`, the npm package `@polyspec/hyper-server` in `packages/server/ts`, the Composer package `polyspec/hyper-server` in `packages/server/php`, the Python distribution `polyspec-hyper-server` in `packages/server/python`, whose import package stays `polyspec.hyper`, and the npm package `@polyspec/hyper-build` in `packages/build`. `packages/` holds no other directory. `config/release.json` releases each npm and Composer package from its directory and names the manifest of the Python distribution, which is consumed by the git tag, so the name of a release archive (HR-95) states the role and the registry of its package, such as `polyspec-hyper-client-npm-X.Y.Z.tgz`. `tests/scripts/package-names.test.mts` checks the manifest and the release entry of each package.

## Toolchain and checks

- **HR-55** `make server-parity` runs the steps of `examples/board/tests/parity/requests.json` against the PHP server and the board Node server at the same time, each with its own empty database and session and with the same creation time of posts (`BOARD_TIME`). For every request of the steps, the HTML document, the document JSON and the region JSON alike, the status, the headers and the body of both responses must be equal. Before the comparison it replaces the session identifier in the session cookie with `<session>`, the masked CSRF token of each response (HY-24) with `<csrf>` in headers and bodies, and the `ETag` value with `<etag>` after it checks that the value is the tag of its body (HY-53), because the body contains the masked token; the session token for that check is the second half of the masked value XOR its first half. It leaves out the headers that the HTTP server program writes by itself: `Date`, `Connection`, `Keep-Alive`, `Content-Length`, `Transfer-Encoding`, and the `Host` and `X-Powered-By` of the PHP built-in server. Headers are compared as a set of name and value pairs, and `Set-Cookie` with each of its values. The same run also performs the browser comparison of `make parity` against the PHP server.
- **HR-78** This repository builds the native template extension from the package `polyspec/template-php-ext` of the template release `TEMPLATE_VERSION`, which the Composer repository of the release (`packages.json`) names with the sha1 of its zip (H14.1-7, H27.45). `make hyper-install` runs `make template-ext` through `$(ONLINE)`: its recipe runs PIE itself, which adds that repository and builds the package with phpize, configure and make of the PHP of `PATH` in an empty `var/pie/polyspec/template-php-ext`, and publishes the one library that PIE recorded there, which `scripts/pie-binary.mts` names, to `build/ext/polyspec_template.so` (H27.51). `make ext` builds nothing and only requires that library, and PHPStan reads no stub of the extension (H25.60). No recipe reads or copies the template repository for the extension, and no recipe builds in it. `tests/scripts/template-ext.test.mts` checks it.
- **HR-80** Release declarations pin the template archives and `TEMPLATE_TAG` (`v0.0.15`), not a tracked Git commit. `make template-tag` fails when `TEMPLATE_REPOSITORY` has no declared tag and names expected and actual tags. CI checks out that tag. Local development uses declared installed-source links; final verification records its tree and runtime versions in the ignored native report. `tests/scripts/template-pins.test.mts`, `tests/scripts/template-version.test.mts` and `tests/scripts/ci-workflow.test.mts` verify these declarations.
- **HR-81** Every tool whose release changes a result of this repository is pinned in a tracked file: npm in `packageManager` of `package.json` (`npm@<version>+sha512.<digest of the release tarball>`), PHP by its minor release (`8.4`) in `.php-version`, and Node.js, Python, Composer and the other tools of mise in `mise.toml`, with their digests for every platform in `mise.lock` (kit K127). `make install-tools TOOLS=npm` installs mise, the Node.js of `mise.toml` and npm, and `make install-tools` the tools of `mise.lock`, into the ignored directory `var/tools` of the checkout and never into the machine, because a machine-wide tool is shared by every checkout and session and an install for one replaces the tool of the others; it uses a download only when its digest equals the pin. `var/tools/bin` holds `node`, `npm` and `npx` and `var/tools/mise/shims` the commands of mise, `python3` and `composer` among them, which kit.mk puts first on `PATH` for every recipe and the programs that it starts. Recipes and scripts start Node.js, npm, Composer and Python by those absolute paths (`$(NODE)`, `$(NPM)`, `$(COMPOSER)`, `$(PYTHON)`), because make 3.81 looks up the program of a recipe line without shell syntax on the `PATH` of its own process and not on the exported one. A PHP patch release of the pinned minor passes; Python is pinned to its exact release. make is not pinned: the expansion of every target gives the same commands under GNU Make 3.81 and 4, and the recipes start npm and Composer by their absolute paths, which make 3.81 needs. A tool that is missing fails the target that runs it (kit K854). `make ext` builds the native extension with phpize and php-config of the PHP of `PATH`, the PHP that the checks run. The CI jobs start the bootstrap with the Node.js of `mise.toml` (`node-version-file`) and set up PHP from `.php-version` (`php-version-file`) and install the tools of mise with `make install-tools`, and the record of a CI run names the running release of each tool. The tools are tested in kit; `tests/scripts/toolchain.test.mts` and `tests/scripts/template-copy.test.mjs` check the recipes.
- **HR-82** An output that another process may read while it is written again is published without a missing or partly written file. A single file is written to a file of the writing process next to it and moved into place with one rename (`writeFileAtomic` of `packages/build/lib/output-files.mjs`): the template files, the index, the manifest and the scripts of the asset build, the stylesheet of `--tailwind` and the index of the template build. A directory is written into a staging directory of the writing process (`<target>.next-<pid>`) and published by `publish` of `packages/build/lib/publish.mjs`: each file moves into the target with one rename, the files that readers open first last, and then the files that the new output does not have are removed. It publishes the declared template copy (`copy.json` last), the server program (`program.json` and then `php/GeneratedProgram.php` last), the static deployment `csr/` (`index.html` last) and the `dist` of each npm package; a reader finds the previous or the new version of each file and never a missing one, and a reader of several files during one publication can combine files of the two versions. The PHP server package in the vendor of the board is a symbolic link that Composer creates, so it has no publication of its own: `make hyper-server-php-install` runs `composer install` of the board under `var/install.lock` (HR-79). Two writers of one output both succeed. The package manager installs of `make hyper-install` hold the lock `var/install.lock`, and a full run holds `var/report/full-run.lock` (`holder-lock` of `@polyspec/kit`): a second holder fails with the first, and a lock of an ended process stays until `node node_modules/@polyspec/kit/dist/holder-lock.mjs clear <lock>` removes it. `tests/scripts/publish.test.mts`, `tests/scripts/toolchain.test.mts` check it.
- **HR-83** A check that reads the output of a tool reads a form that does not change with the context of the run or with a release that is not pinned. A make dry run starts make without the variables of a calling make (`MAKEFLAGS`, `MFLAGS`, `MAKELEVEL`, `MAKEOVERRIDES`) and with `--no-print-directory`, through `dryRun` of `tests/scripts/make-dry-run.mts`, so the lines `make: Entering directory` of a make that runs inside another make or with `-w` never reach the assertion. A machine-readable form is read where the tool has one, such as `git status --porcelain` and `--version`; no script parses the JSON of `npm pack`, whose shape changed between npm 11 and npm 12 (HR-80). An assertion on text that has no such form, such as the start line of the PHP built-in server or the list of Playwright, reads a tool pinned by HR-81. `tests/scripts/make-dry-run.mts` removes inherited make variables before each dry run.
- **HR-84** A check passes only when it checked something, and a failure states its cause where the result is reported. A test run of `run-tests` of `@polyspec/kit` fails when no test passed, failed or ran out of time, as when no file, no test or no name pattern selects one, and prints `no test ran`; the progress reporters of node and vitest give the runner their counts through the file of `KIT_TEST_RESULT`, and PHPUnit also fails an empty suite (`failOnEmptyTestSuite`). No node test file awaits at its top level, because `node --test --test-force-exit` ends a file when its registered tests end and never runs a test registered after such an await. `scripts/check-parity.mts` fails for a request file without a status or a compare step and, with `--node`, when the Node server answered no compared request. The native final runner records failed-target evidence in its record and summary and preserves each target log. Every line of a log starts at column 0: a check of a recipe runs through `scripts/line-end.mts`, and the full run and the CI report pass on complete lines only, each ending a stream that a tool left without a final newline with one, so no line-based reader finds two lines joined. `tests/scripts/check-parity.test.mts` check it.
- **HR-85** A test creates what it reads, or names it as the output of another target before it reads it. A test copies the tracked files of a fixture into a temporary directory (`copyTracked` of `scripts/tracked-files.mts`) instead of the fixture directory, which may hold the output of an earlier run. A test that reads an install or a build of another target, such as `node_modules`, the `dist` of `make packages`, the `vendor` of `make hyper-install`, calls `requireBuilt` of `tests/scripts/requires.mts`, which fails with the missing path and the make target that writes it; the asset and template build tests read the template package that npm installed (HR-70). A build output holds no absolute path of the checkout that writes it, and the native extension builds in a temporary directory of the run and is published into `build/ext` of its own checkout. `tests/scripts/build-assets.test.mts`, `tests/scripts/template-dir.test.mts` and `tests/scripts/run-tests.test.mjs` check it.
- **HR-86** A run of several checks runs every check to its end and then fails when one failed, naming each failed check. A Makefile recipe with several checks (`test-js`, `hyper-test-node`, `test-php`, `lint`, `parity`, `bench-server`) runs them with `$(call check,<name>,<command>)`, which prints the command, runs it in a subshell and records its name when it fails, and ends with `$(checks_result)`, which prints `failed checks:` with every failed name and fails. The full run runs each target of `CHECK_TARGETS` with its own `make -k <target>` to its end (H11.1-1). A step of a CI job after its first step runs with `if: ${{ !cancelled() }}`, and a make with several goals that check runs with `-k`. A recipe of dependent steps, such as an install or a build, stops at its first failure, because a later step reads the output of the earlier one. `tests/scripts/check-recipes.test.mts` checks it.
- **HR-87** No process or file of a run outlives it. `serverRun` of `scripts/board-servers.mts` gives a run its temporary directory and its server children; every server joins the children when it is spawned, before it reports its address, and `close` stops every child, waits until each has exited and then removes the directory, on the end and the failure of the run and on SIGINT and SIGTERM, after which the process ends with 130 or 143. When a server of the board fails to start, the servers that started have exited before the start rejects. `scripts/check-parity.mts`, `scripts/run-e2e.mts` and `benchmarks/browser.mts` use it, and `scripts/serve-demo.mts` handles its signals before it starts a server. A test removes a directory only after the processes that use it have exited: the demos of `tests/scripts/serve-demo.test.mts` stop in the hook that then removes their directory, `tests/scripts/check-parity.test.mts` runs the check in a process group of its own and kills the group, and `RunTest` releases its server and its log in `finally`. `tests/scripts/board-servers.test.mts`, `tests/scripts/check-parity.test.mts` and `tests/scripts/serve-demo.test.mts` check it.
- **HR-88** Every tracked path has owners, and a change runs the owners of the paths that it touches. `config/owner-checks.json` declares for globs of paths the make targets and the node test files that own them. `make owner-validate` (`owner-check` of `@polyspec/kit`) fails when a tracked or new path matches no rule, a glob matches no path, a target is not a target of the Makefile or of `kit.mk` of `@polyspec/kit` or runs the full suite, or a test file does not exist; `make owner-check` runs the owners of the changed paths: the uncommitted changes, `PATHS`, or the changes since `BASE`. The node test files run through `make hyper-test-scripts TESTS=<files>`, which writes their inputs first (HR-85). A removed path that no rule owns selects nothing. `.gitignore` ignores no tracked file and every output of the installs, builds, test runs and guards. `tests/scripts/ignored-files.test.mts` check it.
- **HR-89** No result depends on a live service, on the timing of a step or on a resource that a run does not own. No check makes a registry query whose result depends on time: no latest lookup or `@latest`, no resolution of a version range and no metadata query about outdated packages or new releases. A download of a package that a lock pins by its exact version and its integrity is installation and is allowed, as `npm ci` and `composer install` are. npm runs only `ci` with `--no-audit` and `run`, Composer only `install`, both from their locks, and `tests/package-install` installs offline from its tracked `package-lock.json` (`npm ci --offline`); the other downloads are the pinned tools of HR-81, verified by their digests. Every recipe and the programs that it starts run npm and Composer offline: the Makefile exports `npm_config_offline=true` and `COMPOSER_DISABLE_NETWORK=1`, and only the downloads of `make install-tools`, `make hyper-install`, `make hyper-install-browser` (Chromium of the pinned Playwright) and `make hyper-install-virtiofs` (the digest-pinned image) lift them with `$(ONLINE)`; `make ext` downloads nothing, and the php-ext asset is downloaded by `make hyper-install` only (H14.1-7). A test orders its events by events, such as the close of a connection that the server has seen, and never by the race of timers. A server of a test listens on a port that the system assigns and reports, so no process can take the port between its choice and its use: the PHP built-in server of `RunTest` starts on port 0 and the test reads the address from its start line. The start of a server waits without a time limit and prints a progress line every 5 seconds that names the line it waits for and the last line that the server printed. A check over a list fails with the expected and the actual count when the list is empty, such as `scripts/check-bundle-size.mts` without template files. `tests/scripts/toolchain.test.mts`, `tests/scripts/board-servers.test.mts`, `tests/scripts/check-bundle-size.test.mts` and `packages/server/ts/tests/http.test.ts` check it.

## Workflows and release

- **HR-90** Every job of a GitHub workflow of this repository, except the jobs of `.github/workflows/release.yml` and `.github/workflows/ci-pipeline.yml`, the release workflow and the gates workflow that `@polyspec/kit` vendors and that `make kit-check` holds to the package (H23.7, K910), and except the job `kit` of `ci.yml`, which calls `ci-pipeline.yml` and so runs the jobs of that workflow, runs on the declared runner `ubuntu-26.04-arm`, pins every action by its commit with its release in a comment, and has no `timeout-minutes`, because a step is a long operation that the runner logs line by line and judges by its exit code. Every step that runs a command runs one make target, such as `make ci-targets TARGETS="..."` of the job `check`, never a script or a tool directly, so the exported settings and the checks of the Makefile apply to it (HR-81, HR-89), and every step after the first of a job runs with `if: ${{ !cancelled() }}` (HR-86). `tests/scripts/ci-workflow.test.mts` checks it.
- **HR-91** The full suite runs on GitHub for the push of `main` and every manual run, in the workflow `.github/workflows/ci.yml`, whose `on:` block is exactly `push` to `main` and `workflow_dispatch`; the release `.github/workflows/release.yml` runs only on a manual run (HR-95), `.github/workflows/ci-pipeline.yml` of kit only when the job `kit` of `ci.yml` calls it, and no other workflow exists. The job `kit` runs the gates of kit, cross-language parity among them; the job `check` runs one matrix entry per CI group with `fail-fast: false`, and each entry names its `targets`, which it runs with `make ci-targets`; the targets of the entries are together the targets of `CHECK_TARGETS` of the Makefile, each once, and `python-render` runs the Python render tests and the Python server comparison. A group gathers the targets that need the same setup: `docs` needs only Node.js, `php` and `node` also PHP, the template checkout and `make hyper-install`, and `board` and `python-render` also Chromium (`make hyper-install-browser`); no other group installs it; every job runs `make install-tools TOOLS=npm` and `make install-tools`, which install npm and the tools of `mise.lock`, Python among them, into `var/tools`. `make hyper-install-php` of the groups `docs`, `php` and `board` builds the native extension with PIE, phpize and php-config of the PHP of setup-php (`make template-ext`), and `make ext` only requires the built library. The toolchain comes from the pinned files: Node.js and Python from `mise.toml`, which the bootstrap and `make install-tools` install at the digests of `mise.lock`, and PHP from `.php-version` (HR-81); the template repository is checked out at the tag `TEMPLATE_TAG` of the Makefile as `../template` (HR-80), and no recipe copies or builds in it for the extension (HR-78). `make ci-targets TARGETS="<targets>" CI_REPORT=var/ci/<name>` (`ci-targets` of `@polyspec/kit`) runs each target with its own `make -k <target>` to its end, also after a failed target, without a time limit, and writes the report: `record.json` with the tree, the running releases of the tools and each target with its status, its times and, for a failed target, its first failure lines (the lines that a test reporter marks with `✖` with their indented detail lines, else its error lines, else its last lines, then how make ended); `targets/<target>.log` with the full output; and `summary.md`. No report write stops the run: a failed write is printed and recorded, and the run fails. `make ci-summary CI_REPORT=var/ci/<name>` writes the summary into the report and the job summary, also for a run that recorded nothing or did not record its end, and names each setup step that failed; the job uploads the report as the artifact `ci-<name>-<run id>-<attempt>`. Both steps run after a failed step. `tests/scripts/ci-workflow.test.mts` check it.
- **HR-94** Until version 0.1 a change is checked by the unit tests that own it and pushed to `main` once, when every task of `docs/plans/execution/checklist.md` is done; the repository has no pull request, no merge queue and no GitHub ruleset. A push is not checked; every `make` run sets `core.hooksPath` to `.githooks`, the hooks that `make hooks` writes (`git-hooks` of `@polyspec/kit`), and `make hooks-check` fails while it is not set or a hook differs. The push of `main` runs `.github/workflows/ci.yml` (HR-91), whose last job `ci-passed` runs after every other job and passes only when each of them has the result `success`; the run of that job on a commit of `main` is the evidence of the commit, and a release requires it of the run whose id it takes (HR-95). `tests/scripts/ci-workflow.test.mts` check it.
- **HR-95** A release is the commit of a successful push or manual run of `.github/workflows/ci.yml` on `main` (HR-94), tagged `vX.Y.Z`; no tag is created, moved or pushed by hand, and no tag push starts a workflow. After the CI run of the version-bump commit succeeded, the maintainer runs `gh workflow run release.yml -f run=<id> -f version=X.Y.Z` with the id of that run. `.github/workflows/release.yml` (`on: workflow_dispatch` with the inputs `run` and `version`, permission `contents: write`) is one job on `ubuntu-24.04`, the runner of the workflow of kit, whose steps stop at the first failure, because each needs the one before it. The steps are the targets of `kit.mk` of `@polyspec/kit` and read `config/release.json`: `make release-tag` requires RUN to be a completed successful push or manual run of ci.yml on `main` whose commit is an ancestor of `origin/main`, read from the GitHub API, creates the annotated tag `vX.Y.Z` (`git tag -a vX.Y.Z -m vX.Y.Z`) at that commit and pushes it, and does not run the tests again; it compares no version of a manifest with the version of the dispatch. The later steps run on the tag: `make release-prepare` checks out the template repository at `TEMPLATE_TAG` and runs `make hyper-install`, `make release-tools` installs the tools of the release, `make release-assets` builds the packages and writes `polyspec-hyper-client-npm-X.Y.Z.tgz`, `polyspec-hyper-server-npm-X.Y.Z.tgz` and `polyspec-hyper-build-npm-X.Y.Z.tgz` (`npm pack`), `polyspec-hyper-server-php-X.Y.Z.zip` (`git archive` of `packages/server/php` of the tagged commit) and the wheel of `packages/server/python` into `var/release/assets`; each archive holds the manifest of the tree unchanged: a published manifest names every polyspec package by an exact version, a package of this repository by the version of the release and `@polyspec/template`, `@polyspec/template-compiler` and `polyspec/template` by the version of `TEMPLATE_TAG`, and `packages/server/php/composer.json` declares `version` and no `repositories`; an archive is named `<package>-<language>-<version>.<ext>` with `@scope/` and `vendor/` written as `scope-` and `vendor-`; `make release-publish` creates the draft GitHub Release of the tag with the archives and the section X.Y.Z of the change log, and `make release-undraft` makes it public. `make release-coverage` fails for a tracked manifest that `config/release.json` does not classify. Each failure names the run, the tag, the check or the file and both values. The tests of the steps are in kit, and `tests/scripts/ci-workflow.test.mts` requires that no workflow starts on a tag push and the trigger of each workflow. git defines annotated tags for releases: they record the tagger and the time, and `git describe` reads them; `make release-tag` refuses a lightweight tag. A published tag is never moved or replaced, so the lightweight tags v0.0.1 to v0.0.4 and v0.0.9 to v0.0.11 stay as they were published.
