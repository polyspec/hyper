# 저장소 규칙

[English](repository-rules.md).

이 규칙은 이 저장소가 package를 빌드하고 설치하고 검사하고 릴리스하는 방법을 정한다. 모든 서버가 구현하는 `docs/spec/`의 region protocol에 속하지 않는다. build 명령과 저장소 도구의 test(`packages/build`, `tests/scripts`)가 `HR-n` id로 이 규칙을 인용한다. 번호는 규칙이 protocol 문서에서 가졌던 번호와 같으므로, 이 규칙을 `HY-n`으로 부른 changelog와 plan 기록의 뜻이 그대로 남는다.

## 빌드와 asset

- **HR-34** 에셋 빌드는 다음을 쓴다. 클라이언트 번들은 색인과 `hyper/data.tpl`의 이름을 담고, 템플릿은 담지 않는다.
  - 템플릿마다 AST 파일 하나. 파일 이름에는 내용의 해시가 들어간다.
  - 색인. 각 템플릿 이름을 파일 URL에 대응시킨다. 색인은 `hyper/data.tpl`도 담는다.
  - `public/assets` 아래에는 이름에 내용의 해시가 들어간 파일을 더하기만 하고 지우지 않는다. 그래서 이전 build의 서버나 열려 있는 페이지가 그 build의 모든 파일을 계속 불러온다. 쓰이는 어떤 build도 적지 않은 파일은 애플리케이션이 지운다.
  - 해시가 없는 출력, 즉 색인, manifest(HYC-16), 정적 셸 `csr/`는 필수 옵션 `--output`이 가리키는 디렉터리에 쓴다.
  - 클라이언트는 색인을 module `@polyspec/hyper-client/templates-index`로 import하고, build가 이 module을 같은 build의 색인으로 resolve한다. package는 그 type만 선언한다.
- **HR-68** asset build와 server build는 출력으로 복사하는 모든 파일을 mode 0644로, 모든 디렉터리를 mode 0755로 만들고 원본 파일의 바이트를 쓴다. 소유자가 읽을 수 없는 mode로 파일을 만들지 않는다. Linux container(Apple `container`)의 virtiofs bind mount는 그런 생성을 `EACCES`로 거부하고, Node의 `fs.cpSync`는 대상 파일을 mode 0200으로 만들기 때문이다. mode는 process의 umask에 의존하지 않는다. 복사가 만드는 각 파일과 디렉터리는 만든 뒤에 그 mode로 설정하므로, 다른 사용자의 process가 모든 출력을 읽는다. `tests/scripts/output-files.test.mts`는 모든 platform에서 umask 077에서의 mode를, 그리고 GitHub runner처럼 sudo가 password 없이 `nobody`로 process를 시작하는 곳에서는 다른 사용자의 읽기를 검사한다. Darwin에서만 full suite의 target인(`DARWIN_TARGETS`) `make virtiofs-check`(`tests/virtiofs/output-files.test.mts`)는 출력이 virtiofs bind mount에 있는 Apple `container`에서 두 복사를 실행하고, `container`가 없으면 실패한다.
- **HR-70** asset build, template build, server build는 `@polyspec/hyper-build`가 요구하는 template package에서 package 이름으로 template 언어를 읽는다(HR-96). parser, render runtime, manifest 검사 bundle은 `@polyspec/template`을 쓰고, server build는 compiler module `@polyspec/template-compiler/compiler.mjs`, `ast-artifact.mjs`, `type-manifest.mjs`를 쓴다. asset build는 애플리케이션이 설치한 template package와 상관없이 client bundle의 `@polyspec/template`도 같은 package로 resolve한다. npm은 두 package를 template release의 tarball에서 설치한다. private root `package.json`이 그 URL(`https://github.com/polyspec/template/releases/download/v<version>/<package>-<version>.tgz`)을 밝히고, workspace package를 위해 각각을 같은 URL로 override하며, `.npmrc`에 `allow-remote=root`를 둔다. `package-lock.json`은 각 tarball을 `resolved` URL과 `integrity`로 고정하고, `npm ci`가 설치한다. Composer는 `polyspec/template`을 template release의 zip에서 설치한다. `make hyper-install`이 kit의 `make release-assets-fetch`로 그 zip을 내려받아 `config/release-assets.json`이 pin한 sha256으로 확인하고 private root `composer.json`과 `examples/board/composer.json`의 `artifact` repository인 `var/products/template-php`에 두며, `composer.lock`은 Composer가 확인하는 sha1과 함께 그 `dist`를 기록한다(H23.11). 공개 manifest `packages/client/package.json`, `packages/server/ts/package.json`, `packages/build/package.json`, `packages/server/php/composer.json`은 정확한 template version을 요구한다. 어떤 build도 template 디렉터리를 받지 않으며, 옵션 `--template-dir`는 알 수 없는 옵션으로 실패한다. `tests/scripts/template-dir.test.mts`와 `tests/scripts/template-copy.test.mjs`가 이를 검사한다.
- **HR-77** 옵션 `--tailwind <source>=<output>`이 application의 stylesheet를 가리키면 asset build는 그것을 Tailwind CSS로 compile한다. 두 경로는 application directory 기준 상대 경로다.
  - output은 cascade layer `theme`, `base`, `components`, `utilities`를 이 순서로 선언하고, 최신 stable Tailwind CSS의 theme 변수와 `templates/`와 `client/` 아래 file이 쓰는 utility class를 담으며, source의 rule을 바꾸지 않고 layer `components`에 담는다. 그래서 utility class가 그 rule보다 우선한다.
  - output은 layer `base`의 rule을 담지 않는다. 그래서 element는 Tailwind CSS 없이와 같이 application의 rule과 browser가 주는 모양을 가진다.
  - build는 output을 다른 output과 함께 쓰고, source를 읽을 수 없거나 Tailwind CSS가 거부하면 실패한다. `tests/scripts/build-assets.test.mts`는 template이 utility class를 쓰는 application을 build한다.
- **HR-96** build 명령은 bin `hyper-build-server`(HY-48, HY-73)와 `hyper-build-assets`(HR-34, HYC-16, HR-77)를 가진 npm package `@polyspec/hyper-build`이며, 다른 package와 함께 `polyspec-hyper-build-npm-X.Y.Z.tgz`로 릴리스된다(HR-95). `files`는 `bin`과 `lib`이고 `exports`는 `./package.json`뿐이며, module은 자신이 배포하는 파일, Node의 내장 module, manifest가 정확한 버전으로 요구하는 package만 import한다. manifest 검사, read path, 예약 템플릿 `hyper/data.tpl`(`@polyspec/hyper-client/data-template.json`)을 위한 `@polyspec/hyper-client`, template package(HR-70), esbuild, Tailwind CSS가 그것이다. source는 `packages/build`에 한 번만 있다. Makefile은 bin을 그 파일로 실행하고(HR-79) 이 저장소의 script는 module을 거기서 import하며, pack할 때 복사하거나 고쳐 쓰지 않는다. bin은 애플리케이션의 입력과 출력만 받고, 어떤 옵션도 이 저장소의 경로를 밝히지 않는다. `tests/scripts/package-source.test.mts`가 import를 검사하고, `make release-consumer`는 릴리스 tarball을 consumer처럼 설치하고 설치한 패키지의 두 bin을 첫 인자 검사까지 실행한다.

## package

- **HR-61** npm package `@polyspec/hyper-client`와 `@polyspec/hyper-server`는 type 선언을 가진 JavaScript module을 배포하며, `make packages`가 이를 각 package의 `dist` 디렉터리에 쓴다. 각 package의 `exports`는 entry로 `dist/index.js`와 `dist/index.d.ts`를 가리키고, package는 build 출력 중 `dist`만 담는다. `@polyspec/hyper-client`는 선언 `templates-index.d.ts`(HR-34)와, build가 읽는 예약 템플릿 `hyper/data.tpl`의 source인 data 파일 `data-template.json`(HR-96)도 export한다. 따라서 Node는 type을 제거하지 않는 `node_modules`에서 bundler 없이 이를 실행한다. TypeScript 소스는 지울 수 있는 문법(`erasableSyntaxOnly`)만 쓰며, 선언은 `erasableSyntaxOnly`를 켠 package에서 type 검사를 통과한다. `make package-check`는 두 package를 그 `package-lock.json`에서 `npm ci --offline`으로 `tests/package-install`에 설치하고(HR-89) 이 저장소의 그 디렉터리에 link하며, 그 test를 선언에 대해 type 검사한 뒤 `node`로 실행한다. test는 각 package가 `dist/index.js`를 export하는지, `npm pack`이 나열하는 archive가 build와 선언을 담고 `src`는 담지 않는지 확인한다.
- **HR-79** npm은 자기 기본값으로 설치한다. root `package.json`은 npm workspace `packages/client`, `packages/build`, `packages/server/ts`를 선언하며 npm은 이를 root `node_modules`에 link한다. `@polyspec/template`은 workspace의 의존성에 대한 override와 함께 선언한다. `.npmrc`는 `install-links`와 `bin-links`를 설정하지 않는다. `make packages`는 각 npm package를 그 `dist`에 build하고, link는 이를 바로 보여 준다. recipe는 npm의 bin link(`node_modules/.bin`)로 도구를 절대 경로로 실행하고, 각 npm package는 build를 `tsc -p tsconfig.build.json`으로 선언하므로 `packages/client`나 `packages/server/ts`에서 `npm run build`가 이를 compile한다. `tests/scripts/package-build.test.mts`는 `npm exec tsc`가 compiler를 찾는지 확인하고 각 package를 이렇게 build한다. `tests/package-install`은 npm package를 `npm ci`로 설치하며, 이는 각 package를 그 디렉터리에 link한다(H23.8). private root `composer.json`은 개발용으로 `packages/server/php`를 root `vendor`에 설치한다. autoload는 `packages/server/php/src`와 `packages/server/php/tests`의 namespace를 가리키므로 test는 tree를 실행한다. Composer는 root와 board에 `polyspec/hyper-server`를 path repository `packages/server/php`에서 기본값인 symbolic link로 설치하므로 board는 checkout의 source를 실행한다. root와 board의 path repository가 제공하는 각 polyspec package는 그 project의 `vendor`에서 source 디렉터리를 가리키는 symbolic link다. `make hyper-server-php-install`은 `var/install.lock` 아래에서 board의 `composer install`을 실행한다. `tests/scripts/no-symlinks.test.mts`는 이런 package가 `vendor`에서 디렉터리 사본이거나 다른 디렉터리를 가리키면 실패하며, 제3자 package는 검사하지 않는다.
- **HR-98** 이 저장소의 모든 package 이름은 역할을 밝힌다. browser package는 `hyper-client`, server는 `hyper-server`, build 명령은 `hyper-build`이다. `packages/` 아래 directory는 repository 접두사가 없는 역할이고(kit의 S5), port를 가진 component인 server는 runtime마다 directory 하나를 둔다. npm package `@polyspec/hyper-client`는 `packages/client`에, npm package `@polyspec/hyper-server`는 `packages/server/ts`에, Composer package `polyspec/hyper-server`는 `packages/server/php`에, Python distribution `polyspec-hyper-server`는 `packages/server/python`에(import package는 `polyspec.hyper`로 유지), npm package `@polyspec/hyper-build`는 `packages/build`에 있다. `packages/`에는 다른 directory가 없다. `config/release.json`은 각 npm과 Composer package를 그 directory에서 release하고 git tag로 사용하는 Python distribution의 manifest를 밝히므로, release archive 이름(HR-95)은 `polyspec-hyper-client-npm-X.Y.Z.tgz`처럼 그 package의 역할과 registry를 밝힌다. `tests/scripts/package-names.test.mts`가 각 package의 manifest와 release 항목을 검사한다.

## 도구와 검사

- **HR-55** `make server-parity`는 `examples/board/tests/parity/requests.json`의 단계를 PHP 서버와 board Node 서버에 동시에 실행한다. 각 서버는 자기 빈 데이터베이스와 session을 쓰고, 게시글의 생성 시각(`BOARD_TIME`)은 같다. 단계의 모든 요청에서 HTML 문서, 문서 JSON, 영역 JSON 모두 두 응답의 상태, header, body가 같아야 한다. 비교 전에 session cookie의 session 식별자를 `<session>`으로, 각 응답의 가린 CSRF token(HY-24)을 header와 body에서 `<csrf>`로 바꾸고, body에 가린 token이 들어 있으므로 `ETag` 값이 그 body의 tag인지(HY-53) 확인한 뒤 `<etag>`로 바꾼다. 이 확인에 쓰는 session token은 가린 값의 뒤쪽 절반과 앞쪽 절반의 XOR다. HTTP 서버 프로그램이 스스로 쓰는 header인 `Date`, `Connection`, `Keep-Alive`, `Content-Length`, `Transfer-Encoding`과 PHP 내장 서버의 `Host`, `X-Powered-By`는 비교하지 않는다. header는 이름과 값 쌍의 집합으로 비교하고, `Set-Cookie`는 값마다 비교한다. 같은 실행에서 PHP 서버에 대한 `make parity`의 브라우저 비교도 수행한다.
- **HR-78** 이 저장소는 네이티브 template 확장을 tag `TEMPLATE_TAG`(`v0.0.11`)의 php-ext release archive에서 build하며, 이 archive는 `config/release-assets.json`이 sha256으로 밝힌다(H14.1-7, H23.11-2). `make hyper-install`은 archive를 `$(ONLINE)`으로 내려받아 sha256을 확인하고 `var/products/template-ext`에 푼다(kit의 `make release-assets-fetch`). `make ext`는 풀린 소스를 `PATH`의 PHP의 php-config로 phpize, configure, make해 `build/ext/polyspec_template.so`를 offline으로 build한다(`scripts/build-template-ext.mts`). PHPStan은 풀린 archive의 stub을 읽는다. 어떤 recipe도 확장을 위해 template 저장소를 읽거나 복사하지 않으며, 그 안에서 build하지도 않는다. `tests/scripts/release-assets.test.mts`가 이를 검사한다.
- **HR-80** 릴리즈 선언은 추적 Git commit 대신 template archive와 `TEMPLATE_TAG`(`v0.0.11`)를 고정한다. `TEMPLATE_REPOSITORY`에 선언된 tag가 없으면 `make template-tag`가 기대한 tag와 실제 tag를 밝히며 실패한다. CI는 그 tag를 checkout한다. 로컬 개발은 선언된 설치 소스 link를 사용하고 최종 검증은 무시되는 기본 보고서에 tree와 runtime version을 기록한다. `tests/scripts/template-pins.test.mts`, `tests/scripts/template-version.test.mts`, `tests/scripts/ci-workflow.test.mts`가 이 선언을 확인한다.
- **HR-81** release가 이 저장소의 결과를 바꾸는 모든 도구는 추적 파일에 pin한다. npm은 `package.json`의 `packageManager`(`npm@<version>+sha512.<release tarball의 digest>`)에, PHP는 minor release(`8.4`)로 `.php-version`에, Node.js, Python, Composer와 mise의 다른 도구는 `mise.toml`에 pin하고 모든 플랫폼의 digest는 `mise.lock`에 둔다(kit K127). `make install-tools TOOLS=npm`은 mise, `mise.toml`의 Node.js, npm을, `make install-tools`는 `mise.lock`의 도구를 machine이 아니라 checkout의 무시되는 디렉터리 `var/tools`에 설치한다. machine 전체의 도구는 모든 checkout과 session이 공유하므로 하나를 위한 설치가 다른 것들의 도구를 바꾸기 때문이다. download는 그 digest가 pin과 같을 때만 사용한다. `var/tools/bin`은 `node`, `npm`, `npx`를, `var/tools/mise/shims`는 `python3`과 `composer`를 포함한 mise의 명령을 담고, kit.mk는 모든 recipe와 그것이 시작하는 program에 그 디렉터리들을 `PATH`의 맨 앞에 둔다. recipe와 script는 Node.js, npm, Composer, Python을 그 절대 경로(`$(NODE)`, `$(NPM)`, `$(COMPOSER)`, `$(PYTHON)`)로 시작한다. make 3.81은 shell 문법이 없는 recipe 줄의 program을 export한 `PATH`가 아니라 자기 process의 `PATH`에서 찾기 때문이다. pin한 minor의 PHP patch release는 통과하고, Python은 정확한 release로 pin한다. make는 pin하지 않는다. 모든 target의 전개가 GNU Make 3.81과 4에서 같은 명령을 내고, recipe는 make 3.81이 필요로 하는 절대 경로로 npm과 Composer를 시작하기 때문이다. npm, Composer, PHP를 실행하는 모든 recipe가 먼저 실행하는 `make toolchain-check`(`@polyspec/kit`의 `check-toolchain`)는 Node.js, npm, PHP, Python, Composer가 pin과 다르면 실패하고 각각의 기대값과 실제값을 밝힌다. `make ext`는 검사가 실행하는 PHP인 `PATH`의 PHP의 phpize와 php-config로 네이티브 확장을 build한다. CI job은 `mise.toml`의 Node.js(`node-version-file`)로 bootstrap을 시작하고 `.php-version`(`php-version-file`)에서 PHP를 설정하며 `make install-tools`로 mise의 도구를 설치하며, CI 실행의 기록은 각 도구의 실행 중인 release를 밝힌다. 도구는 kit에서 검사하고, `tests/scripts/toolchain.test.mts`와 `tests/scripts/template-copy.test.mjs`가 recipe를 검사한다.
- **HR-82** 다른 process가 다시 쓰이는 동안 읽을 수 있는 출력은 없는 파일이나 일부만 쓰인 파일 없이 publish한다. 파일 하나는 쓰는 process의 파일에 옆에 쓴 뒤 rename 한 번으로 제자리로 옮긴다(`packages/build/lib/output-files.mjs`의 `writeFileAtomic`). 에셋 build의 템플릿 파일, 색인, manifest, script, `--tailwind`의 스타일시트, 템플릿 build의 색인이 그렇다. 디렉터리는 쓰는 process의 staging 디렉터리(`<target>.next-<pid>`)에 쓰고 `packages/build/lib/publish.mjs`의 `publish`로 publish한다. 각 파일은 rename 한 번으로 대상에 옮기고, reader가 먼저 여는 파일은 마지막에 옮기며, 그다음 새 출력에 없는 파일을 지운다. 선언한 template 복사본(`copy.json`을 마지막에), 서버 프로그램(`program.json`과 그다음 `php/GeneratedProgram.php`를 마지막에), 정적 배포물 `csr/`(`index.html`을 마지막에), 각 npm package의 `dist`를 이렇게 publish한다. reader는 각 파일의 이전 version이나 새 version을 찾고 없는 파일은 찾지 않는다. 한 번의 publish 동안 여러 파일을 읽는 reader는 두 version의 파일을 섞을 수 있다. board의 vendor에 있는 PHP 서버 package는 Composer가 만드는 symbolic link이므로 자체 publish가 없다. `make hyper-server-php-install`이 `var/install.lock` 아래에서 board의 `composer install`을 실행한다(HR-79). 한 출력의 두 writer는 모두 성공한다. `make hyper-install`의 package manager 설치는 lock `var/install.lock`을, full run은 `var/report/full-run.lock`을 잡는다(`@polyspec/kit`의 `holder-lock`). 두 번째 holder는 첫 번째를 밝히며 실패하고, 끝난 process의 lock은 `node node_modules/@polyspec/kit/dist/holder-lock.mjs clear <lock>`이 지울 때까지 남는다. `tests/scripts/publish.test.mts`, `tests/scripts/toolchain.test.mts`가 이를 검사한다.

`ubuntu-26.04-arm`의 하나이고, 각 step이 앞의 step을 필요로 하므로 첫 실패에서 멈춘다. step은 `@polyspec/kit`의 `kit.mk`의 target이며 `config/release.json`을 읽는다. `make release-verify`는 tag된 commit이 `origin/main`의 조상이고 GitHub API에서 읽은 그 commit의 최신 check run `ci-passed`가 결론 `success`로 완료되었는지 확인하며 test를 다시 실행하지 않는다. `make release-versions`는 `package.json`, `packages/client/package.json`, `packages/server/ts/package.json`, `packages/build/package.json`, `packages/server/php/composer.json`, `packages/server/python/pyproject.toml`에 X.Y.Z가 있고 `CHANGELOG.md`와 `CHANGELOG.ko.md`에 section `## X.Y.Z`가 있는지 확인한다. `make release-assets`는 패키지를 빌드하고 `polyspec-hyper-client-npm-X.Y.Z.tgz`, `polyspec-hyper-server-npm-X.Y.Z.tgz`, `polyspec-hyper-build-npm-X.Y.Z.tgz`(`npm pack`), `polyspec-hyper-server-php-X.Y.Z.zip`(tag된 commit의 `packages/server/php`의 `git archive`)을 `var/release/assets`에 쓴다. 각 archive는 tree의 manifest를 그대로 담는다. 공개되는 manifest는 모든 polyspec 패키지를 정확한 버전으로 적는다. 이 저장소의 패키지는 릴리스의 버전으로, `@polyspec/template`, `@polyspec/template-compiler`, `polyspec/template`은 `TEMPLATE_TAG`의 버전으로 적고, `packages/server/php/composer.json`은 `version`을 선언하고 `repositories`가 없다. packed manifest가 polyspec 패키지를 경로, git source, URL, range 또는 `@dev`로 적거나, `repositories`를 선언하거나, 버전이 없거나, source manifest와 다르면 이 step은 실패한다. archive 이름은 `<package>-<language>-<version>.<ext>`이고 `@scope/`와 `vendor/`는 `scope-`와 `vendor-`로 쓰며 language는 `npm` 또는 `php`이다. 릴리스 asset은 npm tarball과 Composer zip뿐이고, Python 패키지 `packages/server/python`은 릴리스가 archive로 빌드하지 않고 git tag로 사용한다. `make release-publish`는 archive와 함께 `gh release create <tag> --verify-tag --title <tag> --notes-file <section X.Y.Z>`를 실행한다. `make release-coverage`는 `config/release.json`이 분류하지 않은 tracked manifest가 있으면 실패하고, `make release-consumer`는 archive를 깨끗한 consumer 프로젝트(`tests/release-install`)에 설치해 패키지마다 smoke 명령을 실행한다. 각 실패는 tag, check나 파일, 두 값을 적는다. step의 test는 kit에 있고, `tests/scripts/ci-workflow.test.mts`는 trigger, 권한, step의 순서를 요구한다. tag는 `ci-passed`가 성공한 commit에 붙인 annotated tag, `git tag -a vX.Y.Z -m vX.Y.Z`이다. git은 release의 tag로 annotated tag를 정의하며, 그것은 tagger와 시각을 기록하고 `git describe`가 읽는다. `make release-verify`는 다른 종류를 거부한다. 공개된 tag는 옮기거나 바꾸지 않으므로, 가벼운 tag v0.0.1부터 v0.0.4까지와 v0.0.9부터 v0.0.11까지는 공개된 그대로 남는다.
