# 성능 측정

[English](benchmark.md).

`make bench`는 게시판 예제를 서버와 브라우저에서 측정한다. 결과는 보고용이며 통과나 실패를 판정하지 않는다. 측정은 한가한 기계에서 실행한다. 다른 바쁜 프로세스는 중앙값보다 평균과 p95를 더 크게 바꾼다.

| 타깃 | 스크립트 | 측정 대상 |
|---|---|---|
| `make bench-server` | `scripts/bench-server.php --app <directory> --iterations <n>` | 네트워크 없이 요청 종류별 `App::handle`, 그리고 10, 100, 1,000행에서 `board/rows.tpl` 렌더, `Bind::value`, `json_encode` 비용. generated PHP 프로그램으로 한 번, 네이티브 템플릿 확장으로 한 번 실행한다(HY-48) |
| `make bench-browser` | `scripts/bench-browser.mjs --ssr <port> --edge <port> --api <port> --runs <n>` | 첫 화면, 영역 이동, 10, 100, 1,000행에서 `hy-set` 변경 1회(시간, 단계, 메인 스레드 부하, 긴 작업), 반복 이동 중 메모리와 두 힙 스냅샷 사이의 증가, 템플릿 로드, 전송 바이트 |

두 스크립트는 `examples/board/var/` 아래에 자체 데이터베이스를 만들고 끝나면 지운다. `bench-browser`는 포트 8085~8087에서 `scripts/serve-demo.mjs`를 실행한다. `make check`는 PHP 측정기를 측정마다 한 번씩 실행하는 `make bench-server-smoke`를 실행하므로, 측정기를 깨는 변경은 검사에서 실패한다. 브라우저 측정기는 몇 분이 걸려 `make check`에 넣지 않았으므로, 변경이 그것을 깨도 다음 `make bench`까지 드러나지 않을 수 있다.

## 방법

- **서버:** PHP 프로세스는 네이티브 확장을 불러왔으면 그 확장으로, 아니면 generated 프로그램으로 렌더한다. 각 표의 마지막 줄이 프로그램을 밝힌다. 요청마다 20회 예열한 뒤 지정한 횟수만큼 한 프로세스 안에서 메모리 세션으로 실행한다. 시간은 `App::handle` 앞뒤의 `hrtime`이다. 라우팅, SQLite 로더, 렌더, 인코딩을 포함하고 네트워크와 PHP 시작은 제외한다.
- **첫 화면:** 페이지 로드 전에 추가한 `MutationObserver`가 목록 제목 `게시판`이 나타난 시각을 내비게이션 시작부터 기록한다. 매 회 새 브라우저 컨텍스트를 쓰므로 캐시가 없다.
- **영역 이동:** 글쓰기 링크 클릭부터 제목 `글쓰기`가 나타날 때까지의 시간이다.
- **`hy-set` 변경:** 호출부터 스왑이 끝날 때까지의 `window.hyper.set('rows', …)` 시간이다. 클릭 뒤와 같게 변경마다 페이지가 프레임 하나를 렌더한다. 두 가지 변경을 잰다.
  - `sort`: 모든 행의 순서를 바꾼다.
  - `compact`: class 하나만 바꾸고 행 순서는 그대로 둔다.
- **변경의 단계:** 템플릿 엔진, `htmx.swap`, `htmx.process`를 타이머로 감싸고, 리스너로 htmx 스왑 이벤트 시각을 기록한다. 단계는 다음과 같다.
  - `hyper`: 렌더와 스왑 밖의 변경 처리(데이터 복사, 보관, 저장)
  - `template`: 템플릿 엔진
  - `parse`: 스왑 호출부터 `htmx:before:swap`까지. 주로 HTML을 fragment로 파싱하는 시간이다.
  - `morph`: `htmx:before:swap`부터 `htmx:before:settle`까지
  - `settle`: `htmx:before:settle`부터 `htmx:after:settle`까지
  - `process`: 새 내용에 대한 `htmx.process`
  - `events`: 스왑의 나머지
- **메인 스레드 부하:** `sort` 변경을 Chromium 트레이스로 기록한다. 스크립트는 렌더러 메인 스레드의 모든 이벤트의 자기 시간을 종류별로 합한다. 그래서 스크립트 안에서 강제된 스타일 계산은 스타일로 센다. 50 ms를 넘는 작업마다 자기 시간이 가장 큰 이벤트를 출력한다.
- **메모리:** 페이지 안에서 `element.click()`으로 링크를 클릭해 `/board` → `/board/create` → `/board/<id>` → `/board`를 200회 반복한다. 50회마다 가비지 컬렉션을 강제한 뒤 JavaScript 힙, DOM 노드, 이벤트 리스너, 문서 수를 기록한다. 100회와 200회의 힙 스냅샷을 비교해 늘어난 객체와, 각 객체 하나의 첫 리테이너를 출력한다.

## 결과

## 발견 사항

- **서버:** 영역 JSON 응답의 비용은 generated 프로그램에서 문서의 약 4분의 1, 네이티브 확장에서 약 3분의 1이다. 렌더를 브라우저가 하기 때문이다.
- **PHP 렌더:** 1,000행을 generated 프로그램은 12.8 ms, 네이티브 확장은 3.6 ms에 렌더한다. 네이티브 확장은 브라우저 엔진(3.3 ms)과 비슷한 속도다. 이전 PHP AST 인터프리터는 한가한 기계에서 16.7 ms였다(2026-10-01). 이 비교는 기계 부하가 다른 측정 사이의 비교이므로 대략적인 참고다.
- **데이터 모델 검사:** `Bind::value`(HY-44)는 1,000행에 2.3~2.4 ms로, 네이티브 렌더 시간의 3분의 2다. 네이티브 확장은 렌더할 때 같은 값을 다시 바인딩하므로 이 검사가 일을 반복할 수 있다. 개선 후보이며, 아직 더 재지 않았다.
- **첫 화면:** SSR은 CSR보다 약 2.7배 빨리 보여준다. CSR은 셸을 받은 뒤 JSON과 템플릿 파일을 요청하기 때문이다.
- **1,000행 `hy-set`:** 변경에 스크립트 시간 23~27 ms가 걸린다. 그중 htmx `innerMorph` 스왑이 14~16 ms, `htmx.process`가 약 3 ms, 템플릿 엔진과 HTML 파싱이 각각 약 3 ms, hyper가 0.3 ms다. htmx는 이 프로젝트의 변경 범위 밖이다. 이번 실행에서 50 ms를 넘는 작업은 없었다.
- **메모리:** DOM 노드와 이벤트 리스너는 200회 동안 일정하다. 처음 50회 이후의 힙 증가는 DevTools 네트워크 기록, 컴파일된 코드, 그리고 Chromium 153이 넣은 `<thead>` 요소마다 보유하는 `MediaQuerySet` 객체이며, 애플리케이션에서 오지 않는다.
