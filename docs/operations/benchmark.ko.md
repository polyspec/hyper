# 성능 측정

[English](benchmark.md).

`make bench`는 게시판 예제를 서버와 브라우저에서 측정한다. 결과는 보고용이며 통과나 실패를 판정하지 않는다. 측정은 한가한 기계에서 실행한다. 다른 바쁜 프로세스는 중앙값보다 평균과 p95를 더 크게 바꾼다.

| 타깃 | 스크립트 | 측정 대상 |
|---|---|---|
| `make bench-server` | `scripts/bench-server.php --app <directory> --iterations <n>` | 네트워크 없이 요청 종류별 `App::handle`, 그리고 10, 100, 1,000행에서 `board/rows.tpl` 렌더, `Bind::value`, `json_encode` 비용 |
| `make bench-browser` | `scripts/bench-browser.mjs --ssr <port> --edge <port> --api <port> --runs <n>` | 첫 화면, 영역 이동, 10, 100, 1,000행에서 `hy-set` 변경 1회(시간, 단계, 메인 스레드 부하, 긴 작업), 반복 이동 중 메모리와 두 힙 스냅샷 사이의 증가, 템플릿 로드, 전송 바이트 |

두 스크립트는 `examples/board/var/` 아래에 자체 데이터베이스를 만들고 끝나면 지운다. `bench-browser`는 포트 8085~8087에서 `scripts/serve-demo.mjs`를 실행한다.

> 이 결과는 2026-10-01에, PHP 서버가 컴파일된 프로그램으로 렌더하기(HY-48) 전, 그리고 유지 값이 `kept`로 옮겨지기(HY-17) 전에 쟀다. 현재 코드의 성능이 아니며, 새 측정으로 교체한다.

## 방법

- **서버:** 요청마다 20회 예열한 뒤 지정한 횟수만큼 한 프로세스 안에서 메모리 세션으로 실행한다. 시간은 `App::handle` 앞뒤의 `hrtime`이다. 라우팅, SQLite 로더, 렌더, 인코딩을 포함하고 네트워크와 PHP 시작은 제외한다.
- **첫 화면:** 페이지 로드 전에 추가한 `MutationObserver`가 목록 제목 `게시판`이 나타난 시각을 내비게이션 시작부터 기록한다. 매 회 새 브라우저 컨텍스트를 쓰므로 캐시가 없다.
- **영역 이동:** 글쓰기 링크 클릭부터 제목 `글쓰기`가 나타날 때까지의 시간이다.
- **`hy-set` 변경:** 호출부터 스왑이 끝날 때까지의 `window.hyper.set('rows', …)` 시간이다. 클릭 뒤와 같게 변경마다 페이지가 프레임 하나를 렌더한다. 두 가지 변경을 잰다.
  - `sort`: 모든 행의 순서를 바꾼다.
  - `compact`: class 하나만 바꾸고 행 순서는 그대로 둔다.
- **변경의 단계:** 템플릿 엔진, `htmx.swap`, `htmx.process`를 타이머로 감싸고, 리스너로 htmx 스왑 이벤트 시각을 기록한다. 단계는 다음과 같다.
  - `hyper`: 렌더와 스왑 밖의 변경 처리(데이터 복사, 보관, 저장)
  - `template`: 템플릿 엔진
  - `parse`: 스왑 호출부터 `htmx:before:swap`까지. 주로 HTML을 fragment로 파싱하는 시간이다.
  - `morph`: `htmx:before:swap`부터 `htmx:before:settle`까지
  - `settle`: `htmx:before:settle`부터 `htmx:after:settle`까지
  - `process`: 새 내용에 대한 `htmx.process`
  - `events`: 스왑의 나머지
- **메인 스레드 부하:** `sort` 변경을 Chromium 트레이스로 기록한다. 스크립트는 렌더러 메인 스레드의 모든 이벤트의 자기 시간을 종류별로 합한다. 그래서 스크립트 안에서 강제된 스타일 계산은 스타일로 센다. 50 ms를 넘는 작업마다 자기 시간이 가장 큰 이벤트를 출력한다.
- **메모리:** 페이지 안에서 `element.click()`으로 링크를 클릭해 `/board` → `/board/create` → `/board/<id>` → `/board`를 200회 반복한다. 50회마다 가비지 컬렉션을 강제한 뒤 JavaScript 힙, DOM 노드, 이벤트 리스너, 문서 수를 기록한다. 100회와 200회의 힙 스냅샷을 비교해 늘어난 객체와, 각 객체 하나의 첫 리테이너를 출력한다.

## 발견 사항

- **서버:** 영역 JSON 응답의 비용은 문서의 약 7분의 1이다. 렌더를 브라우저가 하기 때문이다.
- **첫 화면:** SSR은 CSR보다 약 2.5배 빨리 보여준다. CSR은 셸을 받은 뒤 JSON과 템플릿 파일을 요청하기 때문이다. 이 결과는 권장 배포를 뒷받침한다.
- **1,000행 `hy-set`:** 변경에 스크립트 시간 22~25 ms가 걸린다.
  - 그중 htmx `innerMorph` 스왑이 13~15 ms다. 행 순서가 바뀌지 않아도 마찬가지다. 표의 class 하나만 바뀌어도 morph는 1,000행 전체를 JavaScript로 비교한다.
  - `htmx.process`가 3 ms를 더 쓴다. htmx는 morph 뒤 영역의 모든 자식을 다시 처리하며, 바뀌지 않은 자식도 포함한다.
  - 템플릿 엔진은 3 ms, HTML 파싱은 3 ms다.
  - 변경 뒤 프레임에서 스타일과 레이아웃이 약 12 ms 더 걸린다. 바뀐 표를 다시 배치하는 브라우저 비용이다.
- **긴 작업:** 앞선 실행 한 번에서, 1,000행 변경 15회 중 137 ms 작업이 1회 있었다. 그 구성은 기록하지 못했고, 이후 변경 165회에서는 50 ms를 넘는 작업이 없었다. 원인은 밝히지 못했다. 이제 측정기는 그런 작업마다 구성을 출력한다.
- **메모리:**
  - DOM 노드와 이벤트 리스너는 200회 동안 일정하다. 따라서 교체된 영역은 노드나 리스너를 남기지 않는다.
  - JavaScript 힙은 템플릿을 로드하고 코드를 컴파일하는 처음 50회 동안 늘어난다.
  - 그 뒤의 증가는 DevTools 네트워크 기록, 컴파일된 코드, `MediaQuerySet` 객체다.
  - Chromium 153은 문서에 넣은 `<thead>` 요소마다 `MediaQuerySet` 하나(약 160바이트)를 문서가 닫힐 때까지 보유한다. htmx가 없어도, DevTools 세션이 연결되어 있지 않아도 같다. 목록 템플릿에 `<thead>`가 있으므로 `/board`로 이동할 때마다 하나가 늘어난다. 이 증가는 애플리케이션이 아니라 Chromium에서 오며 상한이 없다.
- **PHP 렌더:** PHP는 1,000행을 브라우저 엔진보다 약 6배 느리게 렌더한다. 이 차이는 첫 문서에 영향을 준다.
