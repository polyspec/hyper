# 영역 프로토콜

<!-- contracts/protocol.json에서 생성됨. 직접 수정하지 않는다. -->

[English](protocol.md).

이 문서는 애플리케이션 매니페스트, 라우팅, 렌더, hyper 서버와 hyper 브라우저 코드 사이의 요청과 응답, 두 렌더 방식을 정의한다. 첫 문서는 서버가 HTML로 렌더하거나(서버 렌더, SSR), 정적 셸이 브라우저에서 렌더할 수 있다(클라이언트 렌더, CSR). 템플릿 문법과 렌더 규칙은 template 언어가 정의하며, 이 문서는 그 규칙을 바꾸지 않는다.

## 애플리케이션 매니페스트

- **HY-1** <a id="HY-1.1"></a> 애플리케이션은 구조를 JSON 파일 하나(매니페스트)에 선언한다. <a id="HY-1.2"></a> 서버와 브라우저는 같은 매니페스트를 읽는다.

```json
{
  "layout": "layout.tpl",
  "title": "title.tpl",
  "regions": [
    { "name": "left", "template": "left.tpl", "uses": ["posts", "path"] },
    { "name": "content", "page": true }
  ],
  "routes": [
    { "name": "board.list", "path": "/board", "title": "Board", "template": "board/list.tpl", "regions": [{ "name": "rows", "template": "board/rows.tpl" }] },
    { "name": "board.create", "path": "/board/create", "title": "Write", "template": "board/create.tpl", "post": true },
    { "name": "board.show", "path": "/board/{id}", "title": "Post", "template": "board/show.tpl",
      "representations": [{ "type": "application/vnd.example.post+json", "parameters": { "version": ["1"] }, "methods": ["GET", "PUT"], "vary": ["Authorization"] }] }
  ]
}
```

- **HY-2** <a id="HY-2.1"></a> `regions`와 `routes`는 순서가 있는 목록이다. <a id="HY-2.2"></a> 영역 이름과 라우트 이름은 문자열이며 각각 고유하다. <a id="HY-2.3"></a> 영역 이름은 `[A-Za-z][A-Za-z0-9_-]*`에 맞고, `layout`, `title`, `data`, `build`가 아니다. <a id="HY-2.4"></a> `"page": true`인 영역은 정확히 하나이며 `template`이 없고, 다른 모든 영역은 `template`과 사용 주제 목록을 가진다. <a id="HY-2.5"></a> `"post": true`인 라우트는 `POST` 액션을 받는다. <a id="HY-2.6"></a> 라우트는 `representations`를 선언할 수 있다(HY-118). <a id="HY-2.7"></a> 서버는 시작할 때 매니페스트를 이 규칙으로 검사하고, 에셋 빌드는 클라이언트 번들을 쓰기 전에 매니페스트를 검사하며, 브라우저는 번들의 매니페스트를 다시 검사하지 않는다.

- **HY-3** <a id="HY-3.1"></a> 레이아웃은 `<title>` 안에서 제목 정의를 `{# title}`로, 데이터 정의를 `{# data}`로(HY-31), build 정의를 `<head>` 안에서 `{# build}`로(HY-125) 렌더하고, 각 영역은 `id`가 영역 이름인 요소 안에서 `{# name}`으로 렌더한다(예: `<main id="content">{# content}</main>`). <a id="HY-3.2"></a> 영역 배치에는 블록 인자가 없다. <a id="HY-3.3"></a> 브라우저는 영역 요소를 `id`로 찾으며, 다른 표시는 없다.

## 라우팅

- **HY-4** <a id="HY-4.1"></a> 라우트 경로는 `/`로 시작한다. <a id="HY-4.2"></a> 그 뒤의 segment는 `/`로 구분한다. <a id="HY-4.3"></a> segment는 문자 `A-Z a-z 0-9 . _ ~ -`로 된 리터럴이거나 매개변수 `{name}`이며, `name`은 `[A-Za-z_][A-Za-z0-9_]*`에 맞는다. <a id="HY-4.4"></a> 경로 `/`는 segment가 없다. <a id="HY-4.6"></a> 라우터는 이 규칙이나 HY-49에 맞지 않는 route path, 예를 들어 parameter 이름을 반복하는 path를 거절하므로, 그런 path를 매니페스트에 선언한 애플리케이션은 열리지 않는다.

- **HY-5** <a id="HY-5.1"></a> 요청 경로가 라우트와 일치하려면 `/`로 시작하고, segment 수가 같으며, 모든 리터럴 segment가 요청 segment와 바이트 단위로 같고, 모든 매개변수 segment가 비어 있지 않아야 한다. <a id="HY-5.2"></a> 쿼리 문자열은 경로에 포함하지 않는다. <a id="HY-5.3"></a> 매칭의 parameter는 각 parameter 이름을 그 값에 대응시키는 map이며, route path에서 parameter의 순서대로 놓인다.

- **HY-6** <a id="HY-6.1"></a> 매개변수 값은 요청 segment의 모든 `%XX` 시퀀스(16진수 두 자리)를 해당 바이트로 디코딩한 값이다. <a id="HY-6.2"></a> 두 자리 16진수가 뒤따르지 않는 `%`를 가진 segment, 또는 디코딩한 바이트가 유효한 UTF-8이 아닌 segment는 일치하지 않는다.

- **HY-7** <a id="HY-7.1"></a> 라우트는 매니페스트 순서대로 시도하며, 처음 일치한 라우트가 결과다. <a id="HY-7.2"></a> 어떤 라우트와도 일치하지 않는 경로는 결과가 없다.

- **HY-8** <a id="HY-8.1"></a> 애플리케이션은 `/api` 같은 기본 경로 아래에서 실행될 수 있다. <a id="HY-8.2"></a> 요청 경로는 기본 경로를 제거한 뒤 라우팅하며, 기본 경로 뒤에 `/`나 경로의 끝이 오지 않는 요청 경로는 결과가 없다. <a id="HY-8.3"></a> `Location` 헤더는 기본 경로를 포함한다.

- **HY-49** <a id="HY-49.1"></a> 라우트 경로의 마지막 segment는 나머지 매개변수 `{name*}`일 수 있으며, `name`은 HY-4와 같고 경로의 다른 매개변수와 달라야 한다. <a id="HY-49.2"></a> 이 segment는 남은 요청 segment 0개 이상에 대응하며, 그 segment가 모두 비어 있거나 HY-6으로 decode될 때 맞는다. <a id="HY-49.3"></a> 값은 decode하지 않은 요청 경로의 나머지로, `/` 뒤에 남은 segment를 `/`로 이은 것이며 남은 segment가 없으면 `/`다.

## 데이터와 주제

- **HY-10** <a id="HY-10.1"></a> 공유 데이터는 레이아웃, 제목, 모든 영역이 받는 맵 하나다. <a id="HY-10.2"></a> 라우트 제목 `title`과 이 응답을 위해 가린 HY-24의 세션 토큰 `csrf`로 시작하고, 애플리케이션이 context를 선언하면 그다음에 애플리케이션의 context인 `context`(HY-124)가 오며, 그 뒤에 애플리케이션이 추가하는 값이 온다. <a id="HY-10.3"></a> 라우트의 read path(HY-73)가 `csrf`를 빼면 `context`는 `title` 바로 뒤에 오고, 둘 다 빼면 맨 앞에 온다. context의 자리와 출처는 하나이므로, 이미 member `context`를 가진 공유 데이터에 context를 넣으면 서버에서는 HY-43으로, 브라우저에서는 오류로 실패한다.

- **HY-11** <a id="HY-11.1"></a> 페이지 영역이 아닌 모든 영역은 사용하는 주제를 선언한다. <a id="HY-11.2"></a> 주제는 바뀔 수 있는 데이터의 이름이다(예: `posts`). <a id="HY-11.3"></a> `path` 주제는 내장 주제이며, 요청 경로가 `HX-Current-URL` 요청 헤더의 경로(기본 경로 제거 후)와 다르면 바뀐다.

## 렌더

- **HY-12** <a id="HY-12.1"></a> 문서는 루트 데이터가 공유 데이터와 같고 `html` 정의를 가진 레이아웃을 렌더한 결과이며, 정의는 `title`(단독으로 렌더한 제목), `data`(HY-31), `build`(HY-125)와 매니페스트 영역마다 그 영역을 단독으로 렌더한 결과다. <a id="HY-12.2"></a> 페이지 영역 템플릿은 라우트 템플릿이다.

- **HY-13** <a id="HY-13.1"></a> 단독으로 렌더하는 영역은 영역 템플릿과 루트 데이터 `merge(shared, region data)`를 쓰며, 같은 이름이면 영역 데이터 값이 공유 값을 대체한다. <a id="HY-13.2"></a> 페이지 영역은 자기 라우트의 모든 라우트 영역을 단독으로 렌더한 결과를 `html` 정의로 받는다. <a id="HY-13.3"></a> 제목을 단독으로 렌더하면 제목 템플릿과 공유 데이터를 쓴다. <a id="HY-13.4"></a> 서버와 브라우저는 문서와 영역 부분을 이 같은 방법으로 조립하므로 같은 바이트를 출력한다. <a id="HY-13.5"></a> 문서나 영역 응답은 자기 루트를 각각 template engine의 bound map(VAL-22)으로 한 번 bind하며, 그 루트는 공유 데이터, 모든 영역의 데이터, 그리고 데이터를 내장하는 문서에서는 내장 데이터(HY-31)다. <a id="HY-13.6"></a> 응답의 모든 렌더는 그 bound map과 `merge`를 쓰므로 bind 횟수는 렌더 횟수에 따라 늘지 않으며, 공유 값은 공유 데이터에서 한 번, 데이터를 내장하는 문서의 내장 데이터에서 한 번 더 bind되는데, 내장 데이터가 공유 데이터를 담기 때문이다.

- **HY-14** <a id="HY-14.1"></a> 서버와 브라우저는 같은 환경으로 렌더한다. <a id="HY-14.2"></a> 서버는 모든 JSON 응답에 시간대를 담아 보낸다.

- **HY-48** <a id="HY-48.1"></a> 서버는 자기 런타임의 템플릿 엔진으로, 빌드(HR-96)의 출력 곧 매니페스트, 애플리케이션의 템플릿, 읽기 경로 `reads.json`(HY-73), build id `build.json`(HY-125)에서 HY-12와 HY-13이 정한 대로 문서와 영역을 렌더한다. <a id="HY-48.2"></a> 서버는 필요한 출력이 모두 있을 때만 애플리케이션을 열며, 하나라도 없으면 `open`이 처음 없는 출력의 절대 경로와 함께 실패하므로 빠진 빌드는 애플리케이션을 열 때 실패하고 빠진 파일을 밝힌다. <a id="HY-48.3"></a> 빌드는 먼저 레이아웃 밖의 `hx-*` 속성을 거부하고([애플리케이션 작성 규칙](../operations/composition.ko.md)의 HC-6), `make templates-check`와 같은 HY-3(배치 `{# build}` 포함, HY-125), HY-30, HY-75 규칙으로 템플릿을 검사하며, 위반이 있으면 출력을 지우거나 쓰기 전에 모든 문제와 함께 실패하므로 서버 프로그램은 이 규칙을 어기는 템플릿을 제공하지 않는다.

  - <a id="HY-48.4"></a> PHP: PHP 서버는 빌드가 애플리케이션 템플릿에서 컴파일한 프로그램으로, 같은 템플릿의 generated PHP 프로그램을 template package의 API를 통해 렌더하며, PHP가 네이티브 템플릿 확장 `polyspec_template`을 불러왔으면 확장이 같은 이름으로 그 API를 등록하므로 서버에는 확장에 대한 분기가 없다. <a id="HY-48.5"></a> 프로그램은 확장이 있을 때와 없을 때 같은 테스트와 `make parity`를 통과한다. <a id="HY-48.6"></a> 빌드는 generated 프로그램을 애플리케이션이 고른 PHP namespace로 컴파일하여, 클래스마다 그 이름을 딴 파일 하나인 PSR-4 파일로 프로그램 디렉터리의 디렉터리 `php`에 쓰며, 그래서 전역 이름을 선언하지 않고 여러 애플리케이션의 프로그램이 한 PHP 프로세스에서 불러와진다. <a id="HY-48.7"></a> 애플리케이션은 `composer.json`의 `autoload.psr-4`에서 그 namespace를 그 디렉터리에 연결하고, 서버는 `program.json`이 밝힌 namespace의 클래스 `GeneratedProgram`을 Composer의 autoload로 얻으며 프로그램의 파일을 직접 require하지 않는다. <a id="HY-48.8"></a> `App::open`은 프로그램 디렉터리에 디렉터리 `php`, `program.json`, `reads.json`(HY-73), `build.json`(HY-125), 디렉터리 `templates` 중 하나가 없으면, 처음 없는 것의 절대 경로와 함께 실패한다. <a id="HY-48.9"></a> autoload가 그 클래스를 불러오지 못할 때도 실패하며, 그 클래스와 `autoload.psr-4`가 그 namespace에 연결해야 하는 디렉터리 `php`를 밝힌다.
  - <a id="HY-48.10"></a> Python: 프로그램 디렉터리에는 `reads.json`, `build.json`, 디렉터리 `templates`가 있고, `App.open`은 처음 없는 것을 밝히는 `ValueError`(HY-106)로 실패한다.
  - <a id="HY-48.11"></a> Node: `App.open`은 매니페스트, 템플릿 index, 템플릿 파일, build id 파일을 절대 경로로 읽으며, 마지막은 에셋 출력의 `build.json`의 절대 경로인 option `build`로 받고(HY-125), 없는 파일은 그 경로를 밝히는 오류로 실패한다.

## 요청

- **HY-15** <a id="HY-15.1"></a> `application/vnd.hyper+json`(HY-116)을 선택하고 htmx가 모든 요청에 보내는 `HX-Request: true`를 가진 요청은 영역 요청이고, `HX-Request` 없이 이를 선택한 요청은 문서 요청이다. <a id="HY-15.2"></a> `text/html`을 선택한 요청은 HTML 요청이며 HTML 문서를 받는다. <a id="HY-15.3"></a> JSON 응답은 `Content-Type: application/vnd.hyper+json`을 가진다. <a id="HY-15.4"></a> 영역 요청은 언제나 페이지 영역을 갱신한다(HY-18). <a id="HY-15.5"></a> `application/json`은 hyper의 media type이 아니므로, 애플리케이션은 representation에서 그것에 자기 의미를 줄 수 있다(HY-118).

- **HY-56** <a id="HY-56.1"></a> 요청의 원본 쿼리는 요청 대상에서 첫 `?` 뒤부터 첫 `#` 앞까지이며, `?`가 없으면 빈 텍스트다. <a id="HY-56.2"></a> 그 값은 중첩 없이 읽으며, 원본 쿼리를 모든 `&`에서 나누고 빈 부분은 건너뛴다. 부분의 이름은 첫 `=` 앞의 텍스트이고 값은 그 나머지이며, `=`가 없으면 값은 빈 텍스트다. 둘 다 `+`는 공백이고 16진수 두 자리가 붙은 `%XX`는 그 바이트이며 그 밖의 `%`는 그대로 둔다. <a id="HY-56.3"></a> `roles[]`나 `a[b]`처럼 괄호가 있는 이름은 쓴 그대로의 이름이고, 빈 이름도 이름이다. <a id="HY-56.4"></a> 쿼리 값은 각 이름을 처음 나온 순서대로 그 값들의 요청 순서 목록에 대응시키는 순서 있는 map이며, 유효한 UTF-8이 아닌 이름이나 값은 HY-42로 실패한다. <a id="HY-56.5"></a> `Request`는 원본 쿼리와 쿼리 값을 제공하고, `queryInt`는 이름의 마지막 값을 읽는다. <a id="HY-56.7"></a> 요청의 `query()`, `form()`, `files()`는 세 server에서 이름과 값 목록의 쌍 목록을 반환하므로 십진수 이름도 문자열로 남는다.

- **HY-57** <a id="HY-57.1"></a> 요청의 폼 값은 원본 body에서 중첩 없이 읽으며, HY-56의 쿼리 값처럼 순서 있는 map이다. <a id="HY-57.2"></a> `application/x-www-form-urlencoded` body는 원본 쿼리처럼 읽는다. <a id="HY-57.3"></a> `multipart/form-data` body는 `Content-Disposition`이 `form-data`이고 `name` 매개변수가 있으며 `filename` 매개변수가 없는 part마다 값 하나를 준다. 이름은 그 매개변수이고 값은 part의 내용 그대로다. `filename`이 있는 part는 파일이며 폼 값이 아니다. <a id="HY-57.4"></a> 다른 type의 body에는 폼 값이 없다. <a id="HY-57.5"></a> 유효한 UTF-8이 아닌 이름이나 값은 HY-42로 실패한다. <a id="HY-57.6"></a> PHP 서버는 대괄호 이름을 중첩하는 `$_POST`가 아니라 `php://input`에서 body를 읽으며, PHP는 `enable_post_data_reading`이 꺼져 있을 때만 `multipart/form-data` 요청의 body를 `php://input`에 준다. <a id="HY-57.7"></a> `Request`는 폼 값을 제공하고, `formString`은 이름의 마지막 값을 읽는다. <a id="HY-57.10"></a> content type이 대소문자를 구분하지 않고 그 media type으로 시작하고, 공백이나 tab 뒤에 `;`이나 content type의 끝이 오면 body는 `application/x-www-form-urlencoded`다.

- **HY-113** <a id="HY-113.1"></a> `multipart/form-data` body의 file part는 `Content-Disposition`이 `form-data`이고 `name` 매개변수와 `filename` 매개변수를 모두 가진 part다(HY-57). <a id="HY-113.2"></a> 요청은 그 file들을 `files()`로 제공하며, 이는 이름과 요청 순서의 file 목록의 쌍 목록(HY-56.7)으로 HY-57이 폼 값의 순서를 정하듯 따르고, `file(name)`은 이름의 마지막 file을 돌려주고 없으면 null(Python에서는 `None`)을 돌려주는데 `formString`이 마지막 값을 읽는 것과 같다. <a id="HY-113.3"></a> file은 네 부분으로 이루어진다. 이름은 `name` parameter이고, filename은 보낸 그대로의 `filename` parameter로 디코딩하지 않으며, content type은 보낸 그대로의 `Content-Type` header 값이고 없으면 빈 text이며, bytes는 part의 내용 그대로다. <a id="HY-113.4"></a> filename이 빈 file도 file이다. <a id="HY-113.5"></a> 이름, 파일 이름, content type은 유효한 UTF-8이어야 하며, 그렇지 않은 part는 HY-42가 이름에 주는 것과 같이 상태 400을 받는다. <a id="HY-113.6"></a> `name` 매개변수가 없는 part는 폼 값도 file도 아니며, 어떤 규칙도 이를 애플리케이션에 주지 않는다. <a id="HY-113.7"></a> `filename*`(RFC 5987)는 읽지 않는다. <a id="HY-113.8"></a> file API는 HY-106의 공개 API의 일부로 각 runtime 형태에서 제공되며, PHP `Request::files()`와 `Request::file()`, Python `files()`와 `file()`, Node `files()`와 `file()`은 각각 클래스 `UploadedFile`을 쓰고, 그 method `name()`, `filename()`, `contentType()`(Python에서는 `content_type()`), `content()`는 HY-113.3의 네 부분을 돌려준다. <a id="HY-113.11"></a> `multipart/form-data` body의 boundary는 첫 `;` 앞의 text가 둘레의 공백과 tab을 빼고 대소문자를 구분하지 않아 `multipart/form-data`인 content type의 parameter `boundary`(HY-113.13)이며, 그 parameter가 없거나 비어 있는 content type은 boundary가 없다. <a id="HY-113.12"></a> part의 header 줄은 CRLF로 나뉘며, 이름의 header는 첫 `:` 앞의 text가 대소문자를 구분하지 않고 그 이름인 첫 줄이고, 그 값은 줄의 나머지에서 둘레의 공백과 tab을 뺀 것이다. <a id="HY-113.13"></a> `Content-Disposition`은 첫 `;` 앞의 text가 둘레의 공백과 tab을 빼고 대소문자를 구분하지 않아 `form-data`일 때 `form-data`이며, 각 parameter는 `;`과 공백이나 tab 뒤에 오고 `=`까지가 대소문자를 구분하지 않는 이름, 그 뒤가 따옴표를 뺀 quoted string이거나 다음 `;`, 공백, tab까지의 text인 값이다. 같은 이름의 parameter는 첫 번째가 쓰이고, quoted string 안의 text는 parameter가 아니며, no-break space 같은 다른 공백은 아무것도 나누지 않는다. <a id="HY-113.14"></a> quoted 값은 첫 `"`와 다음 `"` 사이의 text이고 다음 것이 없으면 text의 나머지이며 backslash를 모두 그대로 둔다. browser는 filename의 backslash를 그대로 보내고 `"`는 `%22`로 보내기 때문이다. 따옴표로 감싸지 않은 값은 text 그대로이며 `"`를 담아도 그렇다. <a id="HY-113.15"></a> HY-42로 실패하는 part는 body 전체를 실패시키므로 body의 form 값과 file이 함께 실패한다. <a id="HY-113.16"></a> part의 header 줄은 delimiter 줄의 끝부터 빈 줄까지이며 8192 byte 이하이고, 더 긴 것을 가진 body는 HY-42로 실패한다.

- **HY-114** <a id="HY-114.1"></a> 애플리케이션은 파일 제한, 즉 한 file(HY-113)의 최대 바이트 수를 선언할 수 있으며, 이는 body 제한(HY-59) 옆에 있는 애플리케이션의 옵션이다. <a id="HY-114.2"></a> 기본값은 8 MiB로 기본 body 제한과 같다. <a id="HY-114.3"></a> 파일 제한을 선언하지 않은 애플리케이션은 8 MiB와 body 제한 중 작은 값을 파일 제한으로 쓰므로, 어떤 body 제한으로도 열리며 body 제한이 요청을 거절할 때에만 파일을 거절한다. <a id="HY-114.4"></a> 선언한 파일 제한에 대한 아래의 검사는 선언한 값에만 적용한다. <a id="HY-114.5"></a> 이 제한은 file 하나의 임시 저장소를 묶는다(HY-131.17). <a id="HY-114.6"></a> 양의 정수가 아니거나 body 제한보다 큰 파일 제한은 HY-59가 다른 제한에 대해 정하는 것과 같이 애플리케이션을 열 때 실패한다. <a id="HY-114.7"></a> server는 body를 읽는 동안 각 file part의 byte를 검사한다(HY-131.11). byte가 file 제한보다 많은 file은 HY-59.4처럼, 그리고 HY-59.3의 순서에서 그 자리에서 text `Content Too Large`와 함께 status 413으로 요청을 실패시키며 action은 실행되지 않는다. <a id="HY-114.8"></a> 서버는 file을 자르지 않으며 file의 일부를 넘기지도 않고, 제한 안의 file은 전부 넘긴다.

- **HY-131** <a id="HY-131.1"></a> form type에 `multipart/form-data`가 있는 application(HY-59.1)에서 server는 `multipart/form-data` body를 도착하는 대로 조각으로 읽고 body도 file part의 내용도 한 값으로 두지 않으며, 조각 하나 외에 두는 것은 delimiter, part 하나의 header 줄(HY-113.16), value 제한 안의 text 값, 읽은 part들의 이름과 filename과 content type이 전부다. <a id="HY-131.2"></a> delimiter는 `--`와 boundary다(HY-113.11). <a id="HY-131.3"></a> 첫 delimiter는 body의 처음이거나 CRLF 뒤에 오고 그 앞의 byte는 무시하며, 그 뒤의 모든 delimiter는 part의 내용을 끝내는 CRLF 뒤에 오고 그 CRLF는 내용이 아니다. <a id="HY-131.4"></a> delimiter 뒤에는 part의 header 줄을 시작하는 CRLF나 body를 끝내는 `--`가 오며, 그 `--` 뒤의 byte는 무시한다. <a id="HY-131.5"></a> delimiter 뒤에 다른 byte가 있는 body, body를 끝내는 `--` 전에 끝나는 body, 빈 줄 전에 delimiter로 시작하는 줄이 header 줄에 있는 part는 HY-42처럼 status 400으로 실패하며, 형식 때문에 건너뛰는 part는 없다. <a id="HY-131.6"></a> 결과는 조각에 달려 있지 않아서, body를 어떤 조각으로 나눠 읽어도 한 조각으로 읽은 body의 값, file, 실패와 같다. <a id="HY-131.7"></a> application은 server가 한 값으로 두는 byte의 최대인 value 제한을 선언할 수 있으며, 조각으로 읽지 않는 body와 조각으로 읽는 body의 text 값들의 이름과 내용의 합이 그 대상이다. <a id="HY-131.8"></a> value 제한을 선언하지 않은 application은 8 MiB와 body 제한 중 작은 것을 쓴다. <a id="HY-131.9"></a> application은 body의 part 수의 최대인 part 제한을 선언할 수 있으며 기본값은 1000이다. <a id="HY-131.10"></a> 양의 정수가 아닌 value 제한이나 part 제한, 그리고 body 제한보다 큰 value 제한은 HY-59.2가 정하듯 application이 열릴 때 실패한다. <a id="HY-131.11"></a> body 제한, value 제한, part 제한, file 제한(HY-114)을 넘는 body는 text `Content Too Large`와 함께 status 413을 받고, 모든 server는 제한을 넘는 순간 body 읽기를 멈춘다. <a id="HY-131.12"></a> part 제한은 값도 file도 아닌 part(HY-113.6)를 포함해 모든 part를 센다. <a id="HY-131.13"></a> server는 file part의 내용을 도착하는 대로 system의 임시 directory 아래에 요청을 위해 만든 directory의 file에 쓰며, 자신의 user만 접근하게 한다. <a id="HY-131.14"></a> server는 요청의 response hook(HY-60)이나 disconnect hook(HY-67)이 반환한 뒤에 그 directory를 지우며 실패한 요청도 그렇고, application이 옮긴 file은 그 안에 없다. <a id="HY-131.15"></a> `UploadedFile`은 file의 byte 수를 `size()`로 주고 `moveTo(path)`(Python에서는 `move_to`)로 file을 옮기며, rename으로 하거나 다른 file system으로는 복사와 삭제로 한다. <a id="HY-131.16"></a> `moveTo`는 path가 있거나 file이 이미 옮겨졌으면 HY-46.2의 class로 실패하고, `content()`는 file을 한 값으로 읽으며 옮긴 뒤에는 마찬가지로 실패한다. <a id="HY-131.17"></a> file 제한은 file 하나의 메모리가 아니라 임시 저장소를 묶으므로(HY-114.5), application은 요청의 메모리가 늘지 않으면서 body 제한까지 file 제한을 선언할 수 있다. <a id="HY-131.18"></a> 검사는 HY-59.3의 순서를 유지하여, body 제한보다 큰 `Content-Length`는 body를 읽기 전에 413을 받고, 이 rule의 제한과 HY-42의 실패는 body를 읽는 동안 답하며, 그 뒤에 routing, form type(HY-59.7), CSRF token(HY-59.8)이 답하고 그것들이 거부한 요청은 임시 file을 남기지 않는다. <a id="HY-131.19"></a> 느린 client나 끝나지 않는 요청은 application 앞단 server의 일이며 이 rule은 시간 제한을 두지 않는다. <a id="HY-131.21"></a> Node server는 file의 내용을 그 file의 stream으로 쓰고, 그 stream이 buffer를 비운 뒤에 body의 다음 조각을 읽으며, file들이 닫힌 뒤에 요청의 directory를 지우므로 file 쓰기가 다른 요청을 멈추지 않고, PHP와 Python server는 조각 하나를 쓴 뒤에 다음 조각을 읽는다. <a id="HY-131.22"></a> application이나 test가 body의 byte로 만든 요청은 그 body를 한 값으로 두며, value 제한이 그 byte를 묶고, form type에 `multipart/form-data`가 있는 application에서는 part 제한과 file 제한이 요청이 거기서 읽는 part와 file을 묶는다.

## Media type과 representation

라우트는 resource 하나와 그 resource의 representation 하나 이상을 가진다(RFC 9110, 3.2절). 페이지는 `text/html`로, 페이지 데이터는 `application/vnd.hyper+json`으로, 그리고 라우트가 선언하는 media type들로 나타난다. hyper는 이 모든 representation을 선택하고, 요청을 검사하고, 응답을 쓴다. 그래서 애플리케이션은 다른 client를 위한 JSON 계약을 페이지와 같은 router, 같은 제한, 같은 응답 규칙으로 제공한다.

- **HY-116** <a id="HY-116.1"></a> 서버는 `<base path>/_hyper/keep`(HY-40)을 뺀 모든 요청의 media type을 `text/html`, `application/vnd.hyper+json`, 그 라우트의 representation type(HY-118) 가운데에서 선택하며, 이는 HY-62의 선택, 선택이 고른 요청의 데이터 기본 경로 제거(HY-62.19), 경로의 라우팅(HY-27, 404) 뒤에 한다. type이 라우트에 따라 다르기 때문이다. <a id="HY-116.2"></a> 서버는 한 번 선택하고, 요청은 선택한 type과, representation이면 그 매개변수 값을 가진다. HY-15의 요청 종류, 그것을 알려 주는 요청 method, 그 뒤의 모든 단계는 그것을 요청에서 읽으며 `Accept`를 다시 읽지 않는다. <a id="HY-116.3"></a> `Accept`가 없는 요청은 `Accept: */*`로 읽는다(RFC 9110, 12.5.1절). <a id="HY-116.4"></a> 여러 `Accept` field line은 `, `로 이은 하나의 값이다(RFC 9110, 5.3절). <a id="HY-116.5"></a> RFC 9110 12.5.1절의 문법을 따르지 않는 `Accept` 값과, `q=1.5`나 `q=x`처럼 qvalue(12.4.2절)가 아닌 weight를 가진 값은 텍스트 `Bad Request`와 함께 상태 400을 받는다. 빈 `Accept`는 빈 목록이며 어떤 type에도 맞지 않는다. <a id="HY-116.6"></a> type, subtype, 매개변수 이름, `q`는 대소문자를 구분하지 않고 비교한다. <a id="HY-116.7"></a> 서버는 각 type에, 그 type에 맞는 가장 구체적인 `Accept` range의 weight를 준다. 구체적인 순서는 매개변수를 가진 type, type, `type/*`, `*/*`다. weight 0은 그 type을 받을 수 없게 한다. <a id="HY-116.8"></a> 선언된 type은 HY-119로 자기에게 맞는 range에서만, 그 가운데 weight가 가장 높은 range에서 weight를 얻는다. `type/*`, `*/*`, 필수 매개변수가 없는 range는 그 type에 weight를 주지 않는다. <a id="HY-116.9"></a> `q`는 weight이며 매개변수가 아니다. range에서 `q` 뒤에 오는 것은 accept extension이며, hyper는 그것을 정의하지 않고 읽지 않는다. <a id="HY-116.10"></a> `text/html`과 `application/vnd.hyper+json`은 매개변수가 없다. 둘 가운데 하나를 지정한 range는 다른 매개변수가 무엇이든 그 type에 맞으며, type의 구체성으로 친다. 그런 range가 여럿이면 weight가 가장 높은 range가 weight를 준다. <a id="HY-116.11"></a> 서버는 weight가 가장 높은 type을 고른다. weight가 같으면 `text/html`, `application/vnd.hyper+json`, 그다음 선언 순서에서 먼저 오는 type을 고른다. <a id="HY-116.12"></a> 그다음 서버는 선택한 type에 대해 method를 검사한다. representation에는 `methods`(HY-121)로, 페이지에는 HY-27로 검사한다. <a id="HY-116.13"></a> 어떤 type에도 맞지 않는 요청은 상태 406, `Content-Type: text/plain; charset=utf-8`, `Vary: Accept`, 그리고 그 경로가 제공하는 type을 한 줄에 하나씩, 각 줄을 line feed로 끝내어 나열한 body를 받는다. 순서는 `text/html`, `application/vnd.hyper+json`, 선언 순서다. 선언된 type은 모든 필수 매개변수의 제공 값 하나씩으로 이루어진 조합마다 한 번 나열하며, 조합은 `parameters`의 첫 매개변수의 값 순서, 그다음 매개변수의 값 순서로 정렬하고, HY-119의 `Content-Type`으로 쓴다. <a id="HY-116.14"></a> HY-62의 선택이 고른 요청에서 HY-62.19의 경로는 `text/html`을 제공하지 않고, HY-62.22의 경로는 `text/html`만 제공한다. <a id="HY-116.15"></a> representation은 데이터 기본 경로 아래(HY-62.19)에서만 응답한다. HY-62.22의 요청은 선택 전에 HY-62.23의 404와 405를 받으므로, `GET`이 아닌 method의 HY-62.22 요청은 라우트의 어떤 type도 받을 수 없을 때에도 405를 받는다.

- **HY-117** <a id="HY-117.1"></a> `text/html`이나 `application/vnd.hyper+json` 응답은 `Vary: Accept, HX-Request, HX-Current-URL`을 가지며, 애플리케이션이 context를 선언하면(HY-124) 그 뒤에 `, Hyper-Context`가 온다. HY-62의 셸도 같은 `Vary`를 가진다. <a id="HY-117.2"></a> representation 요청이 선택 뒤에 받는 모든 응답, 곧 HY-121의 405, 415, 400, handler의 응답과 그 304(HY-122), HY-107의 404와 412는 `Vary: Accept` 뒤에 그 항목의 `vary` 이름들(HY-118)을 가진다. <a id="HY-117.3"></a> HY-116의 400과 406, HY-62.20과 HY-62.34의 406은 `Accept`가 정하므로 `Vary: Accept`를 가진다. <a id="HY-117.4"></a> 그 밖의 모든 plain text 응답은, representation 요청의 HY-43과 HY-66의 500을 포함해, `Vary`가 없다. `Cache-Control: no-store`를 가지고(HY-65) `Accept`가 그것을 정하지 않기 때문이다. <a id="HY-117.5"></a> cache는 나열한 header가 같은 요청에만 저장한 응답을 준다(RFC 9110, 12.5.5절; RFC 9111, 4.1절). 그래서 응답은 다른 응답을 받았을 요청에 전달되지 않는다.

- **HY-118** <a id="HY-118.1"></a> 라우트는 순서 있는 목록 `representations`를 선언할 수 있다. <a id="HY-118.2"></a> 각 항목은 `type`(media type), `parameters`(type의 필수 매개변수 이름마다 그 항목이 제공하는 값의 목록을 대응시킨 map, 예: `{"version": ["1"]}`, 또는 빈 map), `methods`(`GET`, `POST`, `PUT`, `DELETE`의 비어 있지 않은 부분집합), `vary`(응답이 `Accept` 말고도 의존하는 요청 header 이름, 예: `Authorization`, 또는 빈 목록)를 가진다. <a id="HY-118.3"></a> `GET`을 가진 항목은 `HEAD`에도 그 `GET` 응답의 header와 body 없이 응답한다(RFC 9110, 9.3.2절). <a id="HY-118.4"></a> 애플리케이션은 항목마다 representation handler 하나를 라우트 이름과 type으로 제공한다. <a id="HY-118.5"></a> 매니페스트 검사(HY-2)는 대소문자를 구분하지 않고 비교하여 다음을 거부한다: 한 라우트 안의 중복 type, `text/html`이나 `application/vnd.hyper+json`과 같은 type, type이나 subtype이 `*`인 type, 이름이 `q`인 매개변수, 유효하지 않은 type, 매개변수 이름, 값(RFC 9110, 8.3.1절), 빈 `methods`, 빈 값 목록, field name이 아닌 `vary` 이름(RFC 9110, 5.1절), `vary` 이름 `Accept`나 `Cookie`, 같은 `vary` 이름 둘; handler가 없는 항목과, 라우트가 선언하지 않은 type의 handler가 있으면 애플리케이션 열기가 실패한다.

- **HY-119** <a id="HY-119.1"></a> 선언된 type은, 그 type을 지정하고 모든 필수 매개변수에 제공하는 값을 가지며 `q` 앞에 다른 매개변수가 없는 `Accept` range에 맞는다. <a id="HY-119.2"></a> 따옴표로 싼 값은 따옴표 없는 같은 값과 같다(RFC 9110, 5.6.6절). <a id="HY-119.3"></a> 한 type에 맞는 range 가운데 서버는 weight가 가장 높은 range를, 그다음 `Accept` 순서에서 먼저 오는 range를 고르고, handler는 그 매개변수 값을 받는다. <a id="HY-119.4"></a> 응답의 `Content-Type`은 type 뒤에, `parameters`의 순서로 필수 매개변수마다 `; <name>=<value>`를 붙인 것이다. 이름은 소문자로 쓰고, 값은 token이면 따옴표 없이, 아니면 따옴표로 싸서 쓴다.

- **HY-120** <a id="HY-120.1"></a> 애플리케이션은 host가 넘기는 session store(HY-97, HY-100)로 요청의 session을 연다. 여는 것은 `<base path>/_hyper/keep`(HY-40)과 `text/html`이나 `application/vnd.hyper+json`을 선택한(HY-116) 요청뿐이다. <a id="HY-120.2"></a> 요청에 적용되는 HY-116, HY-62(그 405, 406, 셸), HY-127, HY-59.7, HY-114의 검사 뒤, HY-24의 token 검사와 첫 handler 앞에서 연다. token 검사가 session을 읽는 첫 단계이기 때문이다. <a id="HY-120.3"></a> 그 검사 가운데 하나가 거부한 요청은 session을 열지 않고 HY-104의 잠금을 기다리지 않는다. <a id="HY-120.4"></a> 그래서 representation 요청은 session을 열지 않고, HY-104의 잠금을 잡지 않으며, session cookie를 설정하지 않는다.

- **HY-121** <a id="HY-121.1"></a> representation 요청은 자기 handler를 실행하며, context handler, loader, action, 공유 데이터 handler는 실행하지 않는다. handler는 loader처럼 자기 요청에서 HY-62의 선택 값을 읽는다. <a id="HY-121.2"></a> 서버는 session과 cookie를 읽지 않고, cookie를 설정하지 않으며, `csrf`를 보내지 않는다. handler가 받는 요청에는 `Cookie` header가 없다. 그래서 응답은 request line, `Cookie`가 아닌 header, body, handler가 읽는 저장된 데이터에만 의존한다. <a id="HY-121.3"></a> session으로 쓰는 요청은 action이다(HY-24). <a id="HY-121.4"></a> HY-116의 method 검사는 이 규칙의 415와 400보다 먼저 한다. <a id="HY-121.5"></a> `GET`을 가진 항목의 `HEAD` 요청은 요청 method `GET`으로 handler를 실행한다. `App.handle`는 그 `GET` 응답을 body와 함께 돌려주며, 응답 hook(HY-60), 응답 제한(HY-66), `around`(HY-97)가 그것을 받는다. host는 그 상태와 header를 그 body의 `Content-Length`와 함께 쓰고 body는 쓰지 않는다. <a id="HY-121.6"></a> `methods`가 나열하지 않은 method는, `GET`을 가진 항목의 `HEAD`를 빼고, `Allow`와 함께 405를 받는다. `Allow`는 항목이 응답하는 method를 `GET`, `HEAD`, `POST`, `PUT`, `DELETE` 순서로 `, `로 구분해 나열한다. <a id="HY-121.7"></a> body의 크기(HY-59.5)가 0이 아닌 `GET`, `HEAD`, `DELETE`는 텍스트 `Bad Request`와 함께 400을 받는다. 이 method는 handler가 읽는 body를 싣지 않기 때문이다. <a id="HY-121.8"></a> `Content-Type`이 없거나, `Content-Type` media type을 매개변수를 빼고 대소문자 구분 없이 비교해 `application/json`이 아닌 `POST`나 `PUT`은 415를 받는다. HY-59의 body 제한이 적용된다. 유효한 UTF-8이 아니거나, HY-54가 kept 값을 decode하듯 데이터 모델의 값의 JSON 텍스트가 아닌 body는 텍스트 `Bad Request`와 함께 400을 받는다. 정수 literal은 정수이고 그 밖의 수 literal은 float이며, ±(2^53 − 1) 밖이거나 유한하지 않은 수, 512단계의 중첩 container, 짝 없는 surrogate escape, U+0000으로 시작하는 key는 실패한다. <a id="HY-121.9"></a> handler는 decode된 값을 요청의 `json()`(PHP `Request::json()`, Node와 Python `request.json()`)으로 읽는다.

- **HY-122** <a id="HY-122.1"></a> representation handler는 상태, body, header를 가진 응답을 돌려준다. body는 null이 아닌 데이터 모델의 값이거나, 응답에 body가 없음을 뜻하는 null이다. <a id="HY-122.2"></a> 상태는 200, 201, 204, 400, 401, 403, 404, 406, 409, 412, 415, 422, 428 가운데 하나다. 401은 `WWW-Authenticate`를, 201은 `Location`을 요구하고, body를 가진 204와 body가 없는 200은 HY-43으로 실패한다. <a id="HY-122.3"></a> body가 없는 응답은 `Content-Type`이 없다. <a id="HY-122.4"></a> handler는 `Location`, `WWW-Authenticate`, `Cache-Control`만 설정할 수 있다(HY-130). <a id="HY-122.5"></a> 애플리케이션 경로(HY-46)인 `Location`은 애플리케이션의 모든 `Location`처럼(HY-8) 요청의 기본 경로, 선택이 고른 요청에서는 데이터 기본 경로(HY-62.19)를 붙인다. 절대 URI(RFC 3986, 4.3절)인 `Location`은 그대로 보내고, `//host/path`나 `posts/8` 같은 다른 값은 HY-43으로 실패한다. <a id="HY-122.6"></a> handler가 `Cache-Control`을 주지 않은 응답은 `Cache-Control: no-cache`를 가지며, `Authorization`이 있는 요청에서는 `private, no-cache`를 가진다. 그런 요청에서 지시어 `private`이나 `no-store`가 없거나 `public`이나 `s-maxage`를 가진 handler 값은 HY-52가 페이지에 요구하듯 HY-43으로 실패한다(RFC 9111, 3.5절). 지시어 이름은 대소문자를 구분하지 않고 비교한다(RFC 9111, 5.2절). <a id="HY-122.7"></a> 상태가 400 이상인 응답은 `Cache-Control: no-store`를 가지며(HY-65), 그 응답에 `Cache-Control`을 설정하는 handler는 HY-43으로 실패한다. <a id="HY-122.8"></a> 그 밖의 header나 상태는 HY-43으로 실패한다. <a id="HY-122.9"></a> 서버는 body를 HY-54의 JSON 텍스트로, HY-119의 `Content-Type`과 함께 쓴다. <a id="HY-122.10"></a> `GET`이나 `HEAD`에 대한 상태 200 응답은 strong `ETag` `"<digits>"`를 가진다. digits는 `Content-Type`, line feed, body의 SHA-256 digest의 첫 16진수 32자리다. `If-None-Match`가 그 tag와 같은 `GET`이나 `HEAD`는 HY-53이 정하는 대로 304를 받는다. 304는 200 응답의 header에서 `Content-Type`을 뺀 header를 가지며 body가 없다. 이 tag는 HY-53의 tag와 달리 strong이다. 어떤 token도 그 바이트를 바꾸지 않기 때문이다. 다른 상태의 응답은 `ETag`가 없고, `If-None-Match`는 그것을 바꾸지 않는다. <a id="HY-122.11"></a> 서버는 handler에 함수 `etag(body)`를 준다. 이 함수는 선택한 type의 body에 대해 그 tag를 돌려주므로, `PUT`이나 `DELETE` handler는 `If-Match`를 그것과 비교한다(RFC 9110, 13.1.1절). <a id="HY-122.12"></a> 응답 hook(HY-60, 새 빈 reply와 함께), frame 정책(HY-45), 응답 제한(HY-66), ORM의 오류(HY-107: `NO_ROWS`는 텍스트 `Not Found`와 함께 404, `REVISION_CHANGED`는 텍스트 `Precondition Failed`와 함께 412이며, 둘 다 `Cache-Control: no-store`를 가진 plain text다), HY-43의 오류는 페이지처럼 적용된다. HY-52, weak tag에 대한 HY-53, HY-103은 적용되지 않는다. handler에는 reply가 없기 때문이다.

## JSON 응답

- **HY-17** <a id="HY-17.1"></a> JSON 응답은 다음 형태다. <a id="HY-17.2"></a> 키는 순서를 유지한다. <a id="HY-17.3"></a> 모든 서버는 응답의 JSON 텍스트를 쓰고, HY-54가 밝힌 대로 HY-38과 HY-40의 유지 값을 decode한다.

```json
{
  "env": { "timezone": "+09:00" },
  "route": "board.show",
  "params": { "id": "7" },
  "build": "<build id>",
  "context": { "hash": "<context hash>", "value": { "name": "Board" } },
  "shared": { "title": "Post", "csrf": "token" },
  "regions": {
    "content": { "post": { "id": 7 } },
    "reader": { "large": false },
    "left": { "count": 3 }
  },
  "kept": {
    "reader": { "large": true }
  }
}
```

`build`는 build id다(HY-125). `context`는 context가 있는 애플리케이션에만 있으며, `value`는 HY-128이 정하는 경우에만 담는다. `regions`는 로더 데이터를 담는다. `kept`는 서버가 `regions`의 영역에 대해 읽었고 영역 데이터에 맞는(HY-38) `server`와 `cookie` 유지 값을 영역과 경로별로 담는다. 그런 값이 없는 영역은 항목이 없다.

- **HY-18** <a id="HY-18.1"></a> 문서 요청이면 `regions`는 없는 라우트 영역(HY-75)을 뺀 모든 영역을 매니페스트 순서로 담는다. <a id="HY-18.2"></a> 영역 요청이면 페이지 영역을 먼저 담고, 그 뒤에 바뀐 주제를 사용하는 다른 영역을 매니페스트 순서로 담는다.

- **HY-19** <a id="HY-19.1"></a> 요청의 바뀐 주제는 직전 액션이 기록한 주제(HY-25)와 `path`(HY-11)다.

## 애플리케이션 context

애플리케이션은 모든 JSON 응답에, 설정과 build에만 따라 바뀌는 값, 예를 들어 message, asset URL, 이름을 보낸다. context는 그 값을 담는다. 공유 데이터의 일부로, 브라우저가 hash로 보관하며, JSON 응답은 바뀌었을 때만 그것을 담는다.

- **HY-124** <a id="HY-124.1"></a> 애플리케이션은 context handler를 선언할 수 있다. <a id="HY-124.2"></a> 서버는 `text/html`이나 `application/vnd.hyper+json`을 선택한(HY-116) 요청 가운데 공유 데이터 handler에 이르는 모든 요청, 곧 action이 없는 요청, action이 라우트 페이지를 돌려주는 요청(HY-26, HY-58), action이 `REVISION_CHANGED`를 내보내 서버가 상태 409의 페이지로 응답하는 요청(HY-107)에 대해, 요청의 action 뒤, 공유 데이터 handler와 어떤 loader보다 먼저, HY-62의 선택 값(클라이언트 렌더가 없는 애플리케이션에서는 null)으로 이 handler를 한 번 호출한다. 그래서 context는 action이 쓴 것을 담는다. handler는 데이터 모델(HY-44)의 map, 곧 context를 돌려준다. <a id="HY-124.3"></a> 그 뒤에 loader나 공유 데이터 handler가 요청을 멈추거나 실패시켜도 호출은 되돌려지지 않는다. <a id="HY-124.4"></a> action이 redirect하거나(HY-25, HY-50), 멈추거나(HY-51, HY-58), HY-43으로 실패한 요청과, hyper가 어떤 handler도 실행하기 전에 응답하는 요청에서는 서버가 context handler를 호출하지 않는다. <a id="HY-124.5"></a> handler는 요청의 어떤 값도 읽지 않는다: 경로, 매개변수, query, header, session, cookie를 읽지 않는다. <a id="HY-124.6"></a> 그래서 context는 선택 값, build, handler가 읽는 저장된 데이터에만 의존하며, 그 hash(HY-125)가 그것을 식별한다. <a id="HY-124.7"></a> context는 공유 데이터(HY-10)의 member `context`다. 템플릿은 그것을 `context.<name>`으로 읽는다. <a id="HY-124.8"></a> key `context`를 돌려주는 공유 데이터 handler는 HY-43으로 실패한다. <a id="HY-124.9"></a> 이 선언이 없는 애플리케이션에는 member `context`가 없다. <a id="HY-124.10"></a> Node에서 context는 `Map`이다(HY-54). 일반 객체는 정수 같은 key를 먼저 정렬하므로 PHP와 Python과 다른 JSON 텍스트를 내기 때문이다. Node의 context handler는 그 promise를 돌려줄 수도 있으며, 서버는 그것을 기다린다. 다른 값은 HY-43으로 실패한다.

- **HY-125** <a id="HY-125.1"></a> build id는 브라우저가 실행하는 출력의 소문자 16진수 SHA-256 digest다. 출력은 client entry, 그 chunk, `manifest.json`, 에셋 build(HYC-16)의 템플릿 파일과 index이며, id를 담는 HY-62의 정적 셸은 뺀다. <a id="HY-125.2"></a> 출력의 경로는, `public/assets` 아래 파일(entry, 그 chunk, 템플릿 파일)이면 앞의 slash를 뺀 URL 경로(예: `assets/hyper-<hash>.js`)이고, `manifest.json`과 `templates.index.json`이면 `--output` 디렉터리 안의 이름이다. <a id="HY-125.3"></a> build는 경로를 바이트로 비교한 순서로 출력을 hash한다. 각 출력마다 UTF-8로 쓴 경로와 NUL 바이트 하나, 8바이트 big-endian으로 쓴 파일 길이, 파일의 바이트를 넣는다. <a id="HY-125.4"></a> build는 id를 `{"build":"<build id>"}`로, hash에서 빠지는 에셋 출력의 `build.json`과 프로그램 디렉터리(HY-48)의 `build.json`에 쓴다. 모든 서버는 애플리케이션을 열 때 id를 읽으며, `build.json`이 없거나 소문자 16진수 64자의 build id를 가진 key `build` 하나만 담지 않으면 `open`이 그 절대 경로와 함께 실패한다. <a id="HY-125.5"></a> 서버 build(HY-48)는 option `--build`로 에셋 출력의 `build.json` 경로를 받아 같은 파일을 프로그램 디렉터리에 쓴다. 파일이 없거나 64자의 소문자 16진수 build id를 담지 않으면 그 경로와 함께 실패한다. <a id="HY-125.7"></a> 문서는 `html` 정의 `build`를 가진다. 그 텍스트는 `<meta name="hyper-build" content="<build id>">`이며, 레이아웃은 그것을 `<head>` 안에서 `{# build}`로 한 번 렌더한다(HY-3, HY-12). `{# title}`과 `{# data}`처럼(HY-48), `{# build}`를 정확히 한 번 배치하지 않는 레이아웃은 build를 실패시킨다. 검사는 배치를 세며, 그것이 `<head>` 안에 있는지는 검사하지 않는다. <a id="HY-125.8"></a> 정적 셸도 같은 요소를 가진다. <a id="HY-125.9"></a> 서버는 context handler를 호출하는 모든 요청에서 context를 HY-44로 검사한다. <a id="HY-125.10"></a> 그다음 서버는 JSON 응답과 데이터를 내장하는 문서(HY-31)에서만 context의 HY-54 JSON 텍스트를 한 번 쓰고 그것으로 context hash를 계산하며, 그 밖의 응답에서는 그 텍스트를 쓰지 않는다. 그 텍스트가 HY-128의 member `value`의 텍스트이고 아래 hash의 텍스트다. <a id="HY-125.11"></a> 데이터를 내장하지 않는 문서는 hash도 `value`도 담지 않으므로, 서버는 그것을 context map으로 렌더하고 그 텍스트를 쓰지 않는다. <a id="HY-125.12"></a> context hash는 바이트 `{"build":"<build id>","context":`, 그 텍스트, `}`의 소문자 16진수 SHA-256 digest다. 이 바이트는 그 map의 HY-54 JSON 텍스트다. 그래서 모든 서버는 같은 context에 같은 hash를 계산하고, 새 build는 새 hash를 준다.

- **HY-126** <a id="HY-126.1"></a> HY-73의 읽기 경로는 `context`에 적용하지 않는다: 서버는 그것을 통째로 보내는데, context 하나가 모든 라우트에 쓰이고 그 hash가 전체를 덮기 때문이다. <a id="HY-126.2"></a> HY-71은 모든 공유 데이터와 같이 context에도 적용한다.

- **HY-127** <a id="HY-127.1"></a> 영역 요청과 문서 요청은 브라우저가 보관한 context hash를 header `Hyper-Context`로 보낼 수 있다. <a id="HY-127.2"></a> context가 있는 애플리케이션은 `text/html`이나 `application/vnd.hyper+json`을 선택했고 HY-62가 그 405, 406, 셸로 응답하지 않는 모든 요청의 이 header를, HY-116의 method 검사 바로 뒤, HY-59.7과 HY-59.8, HY-114의 파일 제한, HY-24의 token 검사, context handler, 어떤 loader나 action보다 먼저 검사한다: 소문자 16진수 64자가 아닌 값이면 서버는 상태 400과 텍스트 `Bad Request`로 응답한다(HY-58). <a id="HY-127.3"></a> context가 없는 애플리케이션은 이 header를 읽지 않는다. <a id="HY-127.4"></a> 유효한 값을 가진 HTML 요청은 그 값이 없을 때처럼 응답한다. 문서는 context 전체를 담기 때문이다.

- **HY-128** <a id="HY-128.1"></a> 모든 JSON 응답(HY-17)은 `params` 뒤에 build id인 member `build`를 담는다. <a id="HY-128.2"></a> context가 있는 애플리케이션의 JSON 응답은 그 뒤에 member `context`를 담는다. 그 값은 `{"hash": <context hash>}`이며, 요청에 `Hyper-Context`가 없거나 다른 hash를 지정했으면 그 뒤에 `"value": <context>`가 온다. <a id="HY-128.3"></a> `shared`의 member `context`는 JSON 응답에 없다. 브라우저 코드는 렌더하기 전에 context를 HY-10의 위치에 맞춰 `shared`에 넣는다. 응답에 `value`가 있으면 그 값이고, 없으면 보관한 context다. <a id="HY-128.4"></a> Node 서버는 context map으로 같은 코드(HY-54)를 써서 문서를 렌더하며, `hash`와 `value`를 가진 member `context`는 데이터를 내장하는 문서에서만 렌더하는 값에 넣는다. <a id="HY-128.5"></a> 데이터를 내장하는 문서(HY-31)는 `build`와, `value`를 가진 `context`를 내장한다.

## 브라우저

- **HYC-1** <a id="HYC-1.1"></a> 브라우저 코드는 응답 URL 경로(기본 경로 제거 후)를 매니페스트 라우트로 라우팅한다. <a id="HYC-1.2"></a> 라우트 이름은 응답의 `route`와 같아야 하며, 다르면 렌더가 실패한다. <a id="HYC-1.3"></a> 페이지 영역 템플릿은 그 라우트의 템플릿이다. <a id="HYC-1.4"></a> 브라우저 코드는 요청 path를 HY-4부터 HY-8까지와 HY-49로 라우팅한다.

- **HYC-2** <a id="HYC-2.1"></a> htmx 확장은 요청 대상 요소의 `id`가 페이지 영역의 이름일 때만 JSON(`Accept: application/vnd.hyper+json`)을 요청한다. <a id="HYC-2.2"></a> JSON 영역 응답은 응답 텍스트 대신 htmx에 넘길 HTML로 바꾼다. 그 HTML은 단독으로 렌더한 제목을 담은 `<title>`, 단독으로 렌더한 페이지 영역, 그리고 다른 영역마다 그 영역을 단독으로 렌더한 결과를 담은 `<hx-partial hx-target="#<name>" hx-swap="innerMorph">`를 이 순서로 이어 붙인 것이다. <a id="HYC-2.3"></a> htmx가 스왑하기 전에 브라우저는 응답의 layout의 stylesheet link를 적용한다(HYC-15). <a id="HYC-2.4"></a> 이후 스왑, 제목 변경, 히스토리 갱신은 htmx가 수행한다. <a id="HYC-2.5"></a> content type이 `application/vnd.hyper+json`이 아닌 응답은 그대로 통과한다.

- **HYC-8** <a id="HYC-8.1"></a> 클라이언트 렌더에서는 정적 셸이 `<meta name="hyper-api" content="/api">`로 서버의 기본 경로를 선언한다. <a id="HYC-8.2"></a> 브라우저 코드는 현재 경로의 문서 JSON을 요청하면서 라우트의 템플릿을 불러오고(HYC-12), 리다이렉트를 따른 뒤의 응답 URL을 라우팅하고(HYC-1), 문서를 렌더하며(HY-12), 렌더한 문서의 head의 stylesheet link를 적용하고(HYC-15), `html` 요소의 속성(HYC-6), 제목, body를 렌더한 것으로 바꾸고, htmx가 새 body를 처리하게 한다. <a id="HYC-8.3"></a> 어떤 라우트와도 일치하지 않는 현재 경로는 body 텍스트로 `Not Found`를 렌더한다.

- **HYC-3** <a id="HYC-3.1"></a> 클라이언트 렌더에서 확장은 모든 영역 요청의 같은 출처 요청 경로 앞에 기본 경로를 붙이고, 히스토리 경로에서 기본 경로를 제거하며, htmx의 히스토리 복원을, 복원할 경로에 대한 HYC-8 동작으로 대체한다. <a id="HYC-3.2"></a> 나중 복원은 아직 불러오는 중인 이전 복원을 취소하며, 가장 마지막 복원만 렌더한다. 복원과 영역 요청의 순서는 HYC-23이 정한다.

- **HYC-15** <a id="HYC-15.1"></a> head의 stylesheet link는 `href` 속성이 있고 `rel` 속성에 ASCII 대소문자를 구분하지 않고 `stylesheet` 토큰이 있는 `link` 요소다. <a id="HYC-15.2"></a> link의 키는 페이지 URL을 기준으로 해석한 `href` 속성 값이다. <a id="HYC-15.3"></a> 브라우저는 새 내용을 보일 때 원본 문서의 head의 stylesheet link를 페이지의 head에 적용하며, 원본 문서는 다음과 같다:

  - <a id="HYC-15.4"></a> 클라이언트 렌더의 문서(HYC-8, HYC-3): 렌더한 문서;
  - <a id="HYC-15.5"></a> JSON 영역 응답(HYC-2): 응답의 공유 데이터에 HY-128의 context를 member `context`로 넣은 것을 루트 데이터로, 단독으로 렌더한 제목을 정의 `title`로, 페이지의 build의 정의 `build`(HYC-22)와 빈 정의 `data`와 매니페스트 영역마다 빈 정의를 주어 렌더한 layout;
  - <a id="HYC-15.6"></a> 서버 렌더에서 htmx가 히스토리에서 페이지를 복원하려고 요청한 HTML 문서(HYC-4): 그 문서.

  <a id="HYC-15.7"></a> 브라우저는 세 단계로 link를 적용한다:

  1. <a id="HYC-15.8"></a> 원본의 stylesheet link를 순서대로 살핀다. 다시 나오는 키는 첫 link에서만 센다. <a id="HYC-15.9"></a> link마다 마지막으로 유지한 link 뒤에 있는 같은 키의 첫 페이지 stylesheet link를 유지하고, 그렇지 않으면 마지막으로 유지하거나 넣은 link 뒤에 원본 link의 복사본을 넣는다. 아직 유지한 link가 없으면 페이지의 첫 stylesheet link 앞에, 페이지에 stylesheet link가 없으면 head의 끝에 넣는다.
  2. <a id="HYC-15.10"></a> 넣은 모든 link와, 앞선 적용이 넣어 아직 불러오는 중인 유지한 link가 모두 불러와질 때까지 기다린다. <a id="HYC-15.11"></a> 그 뒤에야 내용을 보인다.
  3. <a id="HYC-15.12"></a> 내용을 보인 뒤 페이지의 다른 stylesheet link를 모두 제거하므로, 페이지의 stylesheet link는 원본의 link와 그 순서가 된다.

  <a id="HYC-15.13"></a> `style` 요소 같은 head의 다른 요소는 그대로 둔다. <a id="HYC-15.14"></a> 앞선 적용이 내용을 보이기 전에 나중 적용이 시작되면 나중 적용만 link를 제거한다. <a id="HYC-15.15"></a> link 불러오기가 실패하면 브라우저는 이 적용에서 넣은 link를 제거하고, 내용을 보이지 않으며, 실패를 HYC-14대로 알린다. <a id="HYC-15.16"></a> 서버 렌더의 첫 문서는 이미 stylesheet link를 가지므로 적용이 필요 없다.

- **HYC-22** <a id="HYC-22.1"></a> 페이지의 build는 그 문서의 `hyper-build`(HY-125)이며, 브라우저는 그것으로 정의 `build`를 렌더한다. <a id="HYC-22.2"></a> 브라우저는 context와 그 hash를 보관한다: 내장 데이터에서, 또는 `Hyper-Context` 없이 요청한 첫 JSON 응답에서 얻는다. <a id="HYC-22.3"></a> `#hy-data`가 없는 문서는 context를 보관하지 않으므로, 그다음 JSON 요청에는 `Hyper-Context`가 없다. <a id="HYC-22.4"></a> 브라우저는 모든 영역 요청과 문서 요청에 보관한 hash를 보낸다(HY-127). <a id="HYC-22.5"></a> `value`가 있는 응답은 브라우저가 렌더하기 전에 보관한 context를 교체한다. <a id="HYC-22.6"></a> `build`가 페이지의 build와 다른 응답이 오면 브라우저는 렌더하지 않고, 응답의 페이지 URL(HYC-1, HY-62의 데이터 기본 경로 제외)을 `GET`으로 새 문서로 불러온다. 페이지가 다른 build의 client 코드를 실행하고 있기 때문이다. <a id="HYC-22.7"></a> htmx가 HTML을 요청해 히스토리에서 페이지를 복원할 때(HYC-4), `hyper-build`가 페이지의 build와 다른 문서는 swap하지 않고 새 문서로 불러온다. <a id="HYC-22.8"></a> `value`가 없고 `hash`가 보관한 hash와 다른 응답은 요청의 오류다(HYC-14).

- **HYC-23** <a id="HYC-23.1"></a> 브라우저는 가장 마지막 영역 요청의 응답만 렌더한다. 나중 복원이 이전 복원을 취소하듯(HYC-3), 이전 영역 요청의 응답은 렌더하지 않는다. <a id="HYC-23.2"></a> 복원(HYC-3, HYC-8)은 이 규칙에서 영역 요청으로 센다. HYC-7의 문서 요청은 세지 않는다. HYC-7은 다른 응답이 보관 데이터를 교체했을 때 자기 응답을 버리기 때문이다. <a id="HYC-23.3"></a> 렌더하지 않은 응답은 실패가 아니다(HYC-14).

- **HYC-24** <a id="HYC-24.1"></a> 브라우저 코드의 `HyperOptions`는 이름에서 함수로 가는 map인 `functions`를 받아 template engine에 등록한다(template FUN-43). <a id="HYC-24.2"></a> 모든 서버의 `App`은 애플리케이션을 열 때 같은 map을 option `functions`(HY-106)로 받고, Node 서버는 브라우저 코드의 `createApplication`으로 그것을 등록하므로, 서버와 브라우저는 같은 이름을 등록한다(template FUN-47). 등록이 실패하면(template FUN-44) 열기가 실패한다. <a id="HYC-24.5"></a> 함수가 아닌 entry는 template RT-5의 인자 오류로 open을 실패시킨다. <a id="HYC-24.6"></a> built-in이 아니고 등록되지도 않은 이름을 호출하는 render는 HY-43으로 실패한다.

## 서버의 클라이언트 렌더

- **HY-62** <a id="HY-62.1"></a> 애플리케이션은 클라이언트 렌더를 선언할 수 있으며, 그러면 한 서버가 한 매니페스트의 클라이언트 렌더 페이지와 서버 렌더 페이지를 같은 handler로 응답한다. <a id="HY-62.2"></a> 선언은 정적 셸, 데이터 기본 경로, 선택으로 이루어진다:

  - <a id="HY-62.3"></a> 셸은 `<meta name="hyper-api" content="<데이터 기본 경로>">`(HYC-8)를 담은 HTML 파일의 절대 경로다. <a id="HY-62.4"></a> 서버는 애플리케이션을 열 때 이 파일을 읽는다.
  - <a id="HY-62.5"></a> 데이터 기본 경로는 HY-8을 따르며 비어 있지 않다. <a id="HY-62.6"></a> 어떤 라우트 경로도 데이터 기본 경로와 같거나, 데이터 기본 경로 뒤에 `/`가 오는 것으로 시작하지 않는다.
  - <a id="HY-62.7"></a> 선택은 모든 요청을 받아 choice를 반환하며, 그 choice는 요청이 클라이언트 렌더 페이지의 것인지(예를 들어 `Host` header로 고른다)와, host에 저장된 service 같은 값을 담는다. <a id="HY-62.8"></a> PHP에서 choice는 `new Choice(chosen: <bool>, value: <value>)`이고, Node에서는 `chosen`이 `true` 또는 `false`이고 `value`가 `undefined`가 아닌 객체 `{ chosen, value }`다. <a id="HY-62.9"></a> 서버는 요청마다 HY-59.4와 HY-42 뒤, 라우팅 전에 `Cookie` header를 뺀 요청으로 선택을 한 번 호출한다. choice가 셸 응답과 representation의 경로를 정하고, 둘 다 `Cookie`에 따라 달라지지 않기 때문이다(HY-117). <a id="HY-62.10"></a> Node 서버에서는 선택이 choice의 promise를 반환할 수도 있고, 서버는 그 promise를 기다린다. 저장된 데이터를 읽는 선택은 Node에서 그 데이터를 비동기로 읽기 때문이다. <a id="HY-62.11"></a> 예외를 던지거나, 다른 값을 반환하거나, reject되거나 다른 값으로 resolve되는 promise를 반환하는 선택은 HY-43으로 실패한다.
  - <a id="HY-62.12"></a> 요청의 모든 loader와 action은 선택이 요청을 골랐는지와 관계없이 choice의 값을 자기 요청에서 읽으며, PHP에서는 `$request->selection()`, Node와 Python에서는 `request.selection()`이다. <a id="HY-62.13"></a> 그래서 애플리케이션은 선택과 handler가 함께 필요로 하는 저장된 데이터를 요청마다 한 번 읽고, cache 없이 값으로 전달한다. <a id="HY-62.14"></a> 선언이 없는 애플리케이션의 요청은 값 null을 가진다.

  <a id="HY-62.15"></a> 셸 파일을 읽을 수 없거나, 셸이 데이터 기본 경로를 선언하지 않거나, 데이터 기본 경로가 비어 있거나 HY-8을 따르지 않거나, 라우트 경로가 데이터 기본 경로 아래에 있으면 애플리케이션 열기가 실패한다. <a id="HY-62.16"></a> 선택이 고르지 않은 요청에는 선언이 없을 때처럼 애플리케이션의 기본 경로(HY-8)로 응답한다. <a id="HY-62.17"></a> 선택이 고른 요청에는 애플리케이션의 기본 경로 대신 데이터 기본 경로로 다음과 같이 응답한다:

  1. <a id="HY-62.18"></a> `<데이터 기본 경로>/_hyper/keep`은 HY-40을 따른다.
  2. <a id="HY-62.19"></a> 데이터 기본 경로 뒤에 `/`나 경로의 끝이 오는 것으로 시작하는 요청 경로는 데이터 기본 경로를 제거한 뒤 라우팅하며, `Location` header는 데이터 기본 경로를 포함한다(HY-8). <a id="HY-62.20"></a> 선택과 HY-116의 method 검사 뒤에, representation을 선택한 요청은 HY-121로 응답하고, `text/html`을 선택한 요청은 텍스트 `Not Acceptable`, `Vary: Accept`와 함께 상태 406을 받는다. <a id="HY-62.21"></a> 다른 모든 요청에는 HY-15부터 HY-40까지와 HY-42부터 HY-59까지에 따라 응답하며, 문서 요청과 영역 요청은 JSON을 받고 액션은 실행된다.
  3. <a id="HY-62.22"></a> 그 밖의 요청 경로는 그대로 라우팅한다. <a id="HY-62.23"></a> 라우트가 없는 경로는 404를, `GET`이 아닌 method는 405를 받는다(HY-27). <a id="HY-62.34"></a> 그다음 `application/vnd.hyper+json`이나 representation을 선택한(HY-116) 요청은 텍스트 `Not Acceptable`, `Vary: Accept`와 함께 상태 406을 받고, `text/html`을 선택한 요청은 셸의 바이트를 body로 가진 상태 200을 받으며, 그 요청에 대한 애플리케이션의 응답은 `Content-Type: text/html; charset=utf-8`, `Cache-Control: no-cache`, HY-117의 `Vary`, HY-45의 frame policy를 가지고 다른 header는 가지지 않는다. 그 호스트는 HY-130이 허용하는 대로 header를 더할 수 있다. <a id="HY-62.25"></a> 셸은 에셋 build가 쓰는 HY-125의 요소 `hyper-build`를 담는다.

  <a id="HY-62.26"></a> 선택이 고른 요청의 405와 406 응답과 셸 응답은 loader나 액션을 실행하지 않고, 세션을 읽지 않으며(HY-45), 요청 데이터를 담지 않는다. <a id="HY-62.27"></a> 선택이 고른 요청의 모든 응답은 HY-45의 frame 정책을 가지며 HY-60의 응답 hook에 보고된다.

- **HYC-6** <a id="HYC-6.1"></a> 클라이언트 렌더가 렌더한 문서를 붙일 때(HYC-8, HYC-3), 브라우저는 `html` 요소의 속성을 렌더한 문서의 `html` 요소의 속성으로 그 순서대로 바꾸며, 렌더한 요소에 없는 속성은 제거한다. <a id="HYC-6.2"></a> 따라서 `<html lang="{= language}">`를 렌더하는 layout은 서버 렌더 문서처럼 클라이언트 렌더 페이지에도 그 데이터의 언어를 준다. <a id="HYC-6.3"></a> `scripts/build-assets.mjs`가 쓰는 정적 셸은 데이터를 담지 않으므로 `lang` 속성이 없다.

## 액션

- **HY-24** <a id="HY-24.1"></a> 세션 토큰은 세션이 처음 필요로 할 때 서버가 만드는 무작위 32바이트다. <a id="HY-24.2"></a> 응답의 값 `csrf`(HY-10)는 토큰을 가린 값으로, 서버가 응답마다 한 번 뽑는 무작위 32바이트 `r` 뒤에 `r`과 토큰의 XOR를 붙여 128자리 소문자 16진수로 쓴 것이다. <a id="HY-24.3"></a> 응답마다 새 `r`을 뽑으므로 어떤 응답도 토큰의 바이트를 담지 않고, 요청 입력을 함께 담은 응답을 압축해도 그 크기로 토큰을 알아낼 수 없다. <a id="HY-24.4"></a> 액션 요청과 유지 값 저장(HY-40)은 세션 토큰을 가린 값을 폼 필드 `_csrf`로 담아야 한다. 이 값은 128자리 소문자 16진수이고, 뒤쪽 절반과 앞쪽 절반의 XOR가 토큰과 같아야 하며, 이 비교는 constant time으로 한다. <a id="HY-24.5"></a> 그렇지 않으면 서버는 상태 403으로 응답하고 액션을 실행하지 않는다. <a id="HY-24.6"></a> 서버는 토큰 자체를 보내지 않는다. <a id="HY-24.9"></a> 서버는 token을 소문자 16진수 64자리로 가지며, token 자리에 다른 값을 가진 session은 token이 없는 session처럼 새 token을 받으므로(HY-24.1) 그 다른 값을 가린 어떤 값도 올바르지 않다. 다른 형태의 token이나 mask로 가리거나 검증하면 HY-43으로 실패하고, 소문자 16진수 128자리가 아닌 form 값은 올바르지 않다(HY-24.5).

- **HY-72** <a id="HY-72.1"></a> 세션의 주인인 방문자가 바뀔 때, 예를 들어 로그인과 로그아웃에서 액션은 reply의 `renewSession()`으로 세션을 갱신한다. <a id="HY-72.2"></a> 액션이 끝나면 서버는 세션 값을 새 세션 식별자로 옮기고, 예전 세션을 지운 뒤 새 세션 토큰을 만들고 새 세션 cookie를 설정하지만, redirect의 flash 값과 유지 값은 남는다. <a id="HY-72.3"></a> 액션이 렌더하는 페이지는 새 토큰을 가린 값을 담는다. <a id="HY-72.4"></a> `renewSession()`을 부르는 로더나 공유 데이터 핸들러는 그 페이지가 예전 토큰을 담기 때문에 HY-43으로 실패한다.

- **HY-25** <a id="HY-25.1"></a> 성공한 액션은 리다이렉트를 반환한다. <a id="HY-25.2"></a> 서버는 상태 303과 `Location`으로 응답하고, flash 값과 바뀐 주제를 세션에 저장하며, 다음 요청이 읽은 뒤 제거한다. <a id="HY-25.3"></a> 브라우저는 같은 헤더로 리다이렉트를 따라가며, htmx는 최종 URL을 히스토리에 기록한다. <a id="HY-25.4"></a> 결과의 flash 값은 data model의 값이다(HY-44): 그 밖의 값을 저장하면 저장할 때 data model의 오류로 실패한다. <a id="HY-25.5"></a> 같은 이름으로 다시 저장한 flash 값은 그 이름의 자리에서 값을 바꾸고, 다시 기록한 바뀐 topic은 처음 자리를 유지한다. <a id="HY-25.6"></a> flash 이름과 바뀐 topic은 문자열이다: 다른 값은 세 server에서 `TypeError`와 메시지 `a flash name is not a string (HY-25)` 또는 `a changed topic is not a string (HY-25)`로 실패하며, strict types가 없는 PHP 호출자에서도 그렇다.

- **HY-26** <a id="HY-26.1"></a> 입력을 거부한 액션은 오류 데이터를 반환한다. <a id="HY-26.2"></a> 서버는 상태 422로 응답하고, 라우트 데이터에 오류 데이터를 병합해 라우트 페이지를 렌더하되, JSON 요청에는 JSON으로, 그 밖의 요청에는 문서로 응답한다.

## 데이터

- **HYC-10** <a id="HYC-10.1"></a> 영역의 출력은 템플릿, 공유 데이터, 영역 데이터의 함수다. <a id="HYC-10.2"></a> 브라우저는 영역 데이터를 교체하고 렌더하는 방법으로만 페이지를 바꾼다. <a id="HYC-10.3"></a> 폼 컨트롤은 사용자가 입력 중인 값을 가지며, 정렬 순서나 펼친 패널처럼 그 밖의 모든 화면 상태는 영역 데이터다.

- **HY-30** <a id="HY-30.1"></a> 라우트는 예를 들어 `"regions": [{ "name": "rows", "template": "board/rows.tpl" }]`처럼 라우트 영역을 선언할 수 있다. <a id="HY-30.2"></a> 애플리케이션에 요청하지 않고 브라우저에서 바뀌는 페이지의 일부가 라우트 영역이며, 브라우저는 그 변경이 렌더하고 아직 불러오지 않은 템플릿 파일을 불러올 수 있다(HYC-12). <a id="HY-30.3"></a> 라우트 템플릿, 또는 라우트 템플릿이 포함하거나 경로로 배치하는 템플릿은 `id`가 영역 이름인 요소 안에 각 라우트 영역을 블록 인자 없이 `{# name}`으로 배치하며, 그 템플릿 graph의 어떤 템플릿도 라우트 영역을 배치하지 않으면 `make templates-check`가 실패한다. <a id="HY-30.4"></a> 라우트 영역의 로더는 `null`을 돌려줄 수 있으며, 그러면 그 응답에서 영역은 없다(HY-75). <a id="HY-30.5"></a> 영역 이름은 매니페스트 영역과 모든 라우트 영역을 통틀어 고유하다. <a id="HY-30.6"></a> 라우트 영역마다 자기 로더를 가진다. <a id="HY-30.7"></a> 페이지 영역은 모든 라우트 영역을 HTML로 받고(HY-13), 페이지 영역을 담는 모든 JSON 응답은 페이지 영역 바로 뒤에 라우트 영역을 담는다.

- **HY-75** <a id="HY-75.1"></a> 라우트 영역은 로더가 데이터를 돌려주면 응답에 있고, `null`을 돌려주면 없다. <a id="HY-75.2"></a> 없는 라우트 영역은 JSON 응답의 `regions`, 내장 데이터(HY-31), `kept`에 항목이 없고, 페이지 영역은 그 영역의 정의를 받지 않으므로 `{?# name}`은 거짓이며, 없을 수 있는 라우트 영역을 배치하는 템플릿은 그 요소를 `{?# name}…{/}` 안에 둔다. <a id="HY-75.3"></a> 응답은 없는 영역의 유지 값을 담지 않는다. <a id="HY-75.4"></a> 브라우저는 있는 라우트 영역만 보관하므로(HYC-4), 없는 영역에 대한 `data`, `render`, `set`, `hy-set`은 실패한다(HYC-11). <a id="HY-75.5"></a> 브라우저는 페이지 영역을 렌더하거나 교체한 뒤, 보관한 라우트의 있는 라우트 영역마다 그 `id`를 가진 요소가 페이지에 정확히 하나 있고 없는 라우트 영역에는 요소가 없는지 확인하며, 그렇지 않으면 body에 `hy-error="0"`을 둔다(HYC-14). <a id="HY-75.6"></a> 이 규칙으로, 관리자가 조합하는 페이지처럼 한 라우트 아래에서 요청 시점에 화면을 배치하는 페이지도 일부 페이지에만 배치되는 화면을 라우트 영역으로 선언할 수 있다.

- **HY-31** <a id="HY-31.1"></a> 레이아웃은 `</body>` 앞에 `{# data}`를 한 번 배치한다. <a id="HY-31.2"></a> 내장 데이터는 문서 JSON 값(HY-17) 가운데 브라우저가 바꿀 수 있는 부분이며, `env`, `route`, `params`, `build`, `value`를 가진 `context`(HY-128), `shared`는 JSON 응답과 같고(HY-73), `regions`는 그 라우트의 라우트 영역(HY-30)만 그 순서대로, `kept`는 그 영역들의 항목만 담는다. <a id="HY-31.3"></a> 요청의 reply가 내장을 요청하고(HY-92) 그 라우트의 라우트 영역 가운데 있는 영역(HY-75)이 하나라도 있으면 문서는 데이터를 내장한다: 이때 정의 `data`는 예약 템플릿 `hyper/data.tpl`을 렌더하며, 그 소스는 정확히 `<script type="application/json" id="hy-data">{= json(response) | raw}</script>`이고, `response`는 내장 데이터와 같다. <a id="HY-31.4"></a> 그렇지 않으면 정의 `data`는 비어 있고 문서에는 `#hy-data`가 없으므로, 문서의 소스에는 페이지의 HTML만 있다. <a id="HY-31.5"></a> 클라이언트 렌더(HYC-8)의 문서는 브라우저가 자기가 렌더한 JSON 응답의 데이터를 보관하므로 데이터를 내장하지 않는다. <a id="HY-31.6"></a> PHP 서버와 Node 서버가 내장 데이터를 같은 방법으로 계산하고 렌더하므로 문서는 양쪽에서 같은 바이트를 유지한다. <a id="HY-31.7"></a> 영역 요청은 이 템플릿을 렌더하지 않는다. <a id="HY-31.8"></a> JSON 응답은 브라우저가 렌더하므로 모든 영역을 그대로 담는다(HY-18).

- **HY-92** <a id="HY-92.1"></a> 요청의 loader, action, 공유 데이터 핸들러는 reply(HY-52)의 `embedData()`로 그 응답의 HTML 문서가 데이터를 내장하게 하며(HY-31), PHP에서는 `$reply->embedData()`, Node에서는 `reply.embedData()`, Python에서는 `reply.embed_data()`다. <a id="HY-92.2"></a> 호출하지 않으면 문서는 데이터를 내장하지 않는다. <a id="HY-92.3"></a> 이 호출은 JSON 응답(HY-17), 리다이렉트, 멈춤을 바꾸지 않으며, 클라이언트 렌더 요청(HY-62)은 내장 데이터가 없는 셸이나 JSON을 받는다. <a id="HY-92.4"></a> 애플리케이션은 요청마다 정하며, 예를 들어 선택이 읽는 host의 저장된 service로 정한다(HY-62).

- **HY-71** <a id="HY-71.1"></a> 서버가 보내는 데이터는 그 요청의 방문자에게 공개된다. <a id="HY-71.2"></a> 공유 데이터, 영역 데이터, 유지 값은 내장 데이터(HY-31), 모든 JSON 응답(HY-17), 클라이언트 렌더(HYC-8)로 브라우저에 가므로, 템플릿에 넘긴 값은 서버에만 남지 않는다. <a id="HY-71.3"></a> 로더와 공유 데이터 핸들러는 그 요청의 방문자가 봐도 되는 값만 돌려준다. 비밀번호 해시, 세션 토큰, 방문자가 보면 안 되는 개인정보처럼 페이지가 보여 주지 않는 값은 결코 그 일부가 아니다. <a id="HY-71.4"></a> 서버는 템플릿이 읽지 않는 값도 모두 빼지만(HY-73), 그 제거가 값을 돌려줘도 안전하게 만들지는 않는다. <a id="HY-71.5"></a> 페이지가 보여 주는 값은 어차피 HTML로 브라우저에 간다. <a id="HY-71.6"></a> 가린 CSRF 토큰은 브라우저가 모든 폼과 함께 다시 보내므로 공유 데이터다(HY-10, HY-24). 세션 토큰 자체는 결코 보내지 않는다.

- **HY-73** <a id="HY-73.1"></a> 서버는 라우트의 템플릿이 읽는 데이터만 보내며, 다만 `context`는 통째로 보낸다(HY-126). <a id="HY-73.2"></a> 읽기 경로는 요청 전에 템플릿 AST로 계산하고 렌더가 읽는 모든 값을 적어도 포함하므로, 남긴 데이터를 렌더하면 로더 데이터를 렌더한 것과 같은 바이트가 나온다.

  - <a id="HY-73.3"></a> 경로는 루트 데이터에서 시작하는 단계의 목록이다. 단계는 맵 키, 10진수로 쓴 목록 인덱스, 또는 맵의 모든 항목이나 목록의 모든 원소를 뜻하는 `*`다. <a id="HY-73.4"></a> 통째로 읽는 경로는 그 값을 그대로 남기고, 일부만 읽는 경로는 그 아래에서 읽는 경로만 남긴다.
  - <a id="HY-73.5"></a> 식은 경로의 집합을 가진다. <a id="HY-73.6"></a> 변수는 그 이름의 루트 경로와, 같은 이름의 지역 변수가 가진 경로를 가진다. 지역 변수는 자기 범위에 있는 모든 대입 `{:x = e}`의 경로를 합친 것을 가진다. <a id="HY-73.7"></a> `{@ v = e}`의 반복 변수는 그 반복의 본문 안에만 있으며, 본문 안에서 `v`는 `e`의 모든 경로 뒤에 `*`를 붙인 것과 `v`에 대한 대입의 경로를 가지고, 루트 경로나 같은 이름의 바깥 반복 변수의 경로는 가지지 않는다. <a id="HY-73.8"></a> 본문 밖에서 반복 변수는 `v`에 경로를 더하지 않으므로, `{:p = page.x}{@ page = p.items}`처럼 반복 변수의 이름을 읽는 반복 앞의 대입은 반복 전에 가진 경로를 유지한다. <a id="HY-73.9"></a> `v.value_`는 `v`의 경로를 가지고, 다른 반복 메타 필드는 경로가 없다. <a id="HY-73.10"></a> 멤버와, 키가 문자열이나 숫자 리터럴인 인덱스는 모든 경로에 그 키를 붙인다. <a id="HY-73.11"></a> 다른 인덱스는 그 객체와 키를 통째로 읽고 경로가 없다. <a id="HY-73.12"></a> `a ?? b`는 `a`와 `b`의 경로를, 삼항 연산은 두 결과의 경로를 가지며, 다른 식은 경로가 없다.
  - <a id="HY-73.13"></a> 식의 값이 출력될 때, `{? }`, `{:? }`, 삼항 연산의 조건일 때, `??`가 아닌 연산자의 피연산자일 때, 함수, 멤버 호출, 클래스 호출의 인자일 때, 멤버 호출의 객체일 때, 목록이나 맵 리터럴의 항목, 키, 값, 펼침일 때, 인덱스의 키일 때 그 식은 자기 경로를 통째로 읽는다. <a id="HY-73.14"></a> 반복 `{@ v = e}`는 `e`의 모든 경로 뒤에 `*`를 붙인 경로를 일부만 읽으므로, 반복은 모든 항목을 남긴다.
  - <a id="HY-73.15"></a> 포함 `{+ path}`는 포함하는 템플릿의 범위에서 읽는다. <a id="HY-73.16"></a> 경로가 있는 블록은 새 범위에서 그 템플릿을 읽으며, 이 범위에서 루트 이름은 자기 루트 경로를 가지고 각 범위 인자는 호출하는 범위에서 계산한 자기 식의 경로를 가진다. 위에서 이미 배치하고 있는 템플릿을 다시 배치하는 블록은 렌더가 거기서 실패하므로(템플릿 언어의 RT-22) 아무것도 읽지 않는다. <a id="HY-73.17"></a> 정의를 배치하는 블록은 아무것도 읽지 않는다.
  - <a id="HY-73.18"></a> 라우트의 공유 데이터 읽기 경로는 레이아웃, 제목, 모든 매니페스트 영역 템플릿, 라우트 템플릿, 모든 라우트 영역 템플릿의 읽기 경로이고, 라우트 영역이 서버에 값을 남기면(HYC-13) `csrf`를 통째로 더한다. <a id="HY-73.19"></a> 영역 데이터의 읽기 경로는 그 영역 템플릿의 읽기 경로이며, 페이지 영역은 라우트 템플릿의 것이고, 라우트 영역은 유지 경로를 통째로 더한다. <a id="HY-73.20"></a> `hyper/data.tpl`은 아무것도 읽지 않는다.
  - <a id="HY-73.29"></a> 서버는 페이지를 렌더하거나 인코딩하기 전에 공유 데이터와 모든 영역 데이터에서 읽기 경로만 남기며, map은 경로가 지정한 키를 데이터에서의 순서대로, 그 값을 같은 방식으로 남기고 `*` 아래에서는 모든 키를 남기고, 목록은 길이를 유지하고 각 원소를 `*`와 그 인덱스의 경로로 남기며 어떤 경로도 지정하지 않은 인덱스에는 `null`을 두고, 다른 값은 그대로 둔다. <a id="HY-73.22"></a> 비게 된 맵은 맵으로 남는다.
  - <a id="HY-73.23"></a> 빌드는 모든 라우트의 읽기 경로를 서버 프로그램의 `reads.json`(HY-48)에 쓰고, Node 서버는 애플리케이션을 열 때 브라우저 패키지로 읽기 경로를 계산한다. <a id="HY-73.25"></a> `data(region)`(HYC-11)은 남긴 데이터를 돌려주므로, 어떤 템플릿도 읽지 않는 경로는 거기에 없다.

  <a id="HY-73.28"></a> 남긴 데이터는 데이터와 같은 바이트로 렌더된다.

## 브라우저 데이터

- **HYC-4** <a id="HYC-4.1"></a> 브라우저는 마지막으로 렌더한 응답의 데이터, 즉 환경, 라우트, 매개변수, 공유 데이터, 그 라우트의 라우트 영역(HY-30)의 데이터를 보관한다. <a id="HYC-4.2"></a> 서버 렌더 페이지가 브라우저 코드의 `open()`으로 열릴 때와, htmx가 페이지 HTML을 요청해 히스토리에서 복원할 때 브라우저는 `#hy-data` 요소에서 내장 데이터(HY-31)를 읽어 보관 데이터 전체를 교체하고, 라우트의 템플릿 불러오기를 시작한다(HYC-12). <a id="HYC-4.3"></a> `#hy-data`가 없는 문서는 보관 데이터를 남기지 않으며, 브라우저는 데이터가 처음 필요할 때 HYC-7으로 데이터를 얻는다. <a id="HYC-4.4"></a> 페이지가 열릴 때 데이터가 필요한 경우는 라우트의 라우트 영역의 유지 경로에 `localStorage`나 `sessionStorage` 값이 저장되어 있을 때뿐이므로(HY-37, HY-38), 보기만 하고 그런 값이 없는 페이지는 문서 외에 요청을 보내지 않는다. <a id="HYC-4.5"></a> 영역 응답(HYC-2)은 공유 데이터, 페이지 영역, 있는 모든 라우트 영역(HY-17, HY-18, HY-30)을 담고 이것이 브라우저가 보관하는 전부이므로, 보관 데이터 전체를 자기 데이터로 교체한다. <a id="HYC-4.6"></a> 브라우저는 애플리케이션의 context와 페이지의 build도 보관한다(HYC-22). <a id="HYC-4.7"></a> `render`(HYC-11)는 보관한 영역 데이터를 교체한다.

- **HYC-7** <a id="HYC-7.1"></a> 브라우저는 보관하지 않은 데이터를 현재 페이지의 URL, 즉 경로와 query에 대한 `Accept: application/vnd.hyper+json` 문서 요청(HY-15) 하나로 얻는다. <a id="HYC-7.2"></a> 브라우저는 데이터를 보관하지 않은 동안 `data`, `render`, `set`, `hy-set`(HYC-11, HYC-5)이 현재 페이지 라우트의 라우트 영역을 가리킬 때와, 저장된 브라우저 유지 값이 있는 페이지가 열릴 때(HYC-4) 데이터를 얻는다. <a id="HYC-7.3"></a> 다른 영역을 가리키는 호출은 요청을 보내지 않는다. `data`는 아무것도 반환하지 않고, 다른 호출은 실패한다. <a id="HYC-7.4"></a> 요청이 진행 중일 때 데이터가 필요한 호출은 같은 요청을 기다린다. <a id="HYC-7.5"></a> 응답은 상태 200의 JSON 응답이어야 하고, 그 URL은 현재 페이지의 라우트로 라우팅되어야 한다(HYC-1). <a id="HYC-7.6"></a> 그러면 브라우저는 브라우저 유지 값을 적용하고(HY-38), 데이터를 보관하며, 그것으로 그 라우트의 있는 라우트 영역을 내장 문서의 영역처럼 HY-38대로 모두 렌더해, 서버가 HTML을 렌더한 뒤에 데이터가 바뀌었더라도 페이지가 브라우저가 보관한 데이터를 보여 주게 하고, 이어서 호출은 보관 데이터로 계속한다. <a id="HYC-7.7"></a> 요청이 진행 중일 때 응답(HYC-2, HYC-4)이 보관 데이터를 교체했으면 브라우저는 그 요청의 응답을 버리고, 호출은 보관 데이터로 계속한다. <a id="HYC-7.8"></a> 다른 응답, network 실패, decode할 수 없는 응답은 보관 데이터를 남기지 않고, 호출의 영역(페이지가 열릴 때는 body)을 응답의 상태나 `0`으로 표시하며(HYC-14) 호출을 실패시키고, 데이터가 필요한 다음 호출은 요청을 다시 보낸다. <a id="HYC-7.9"></a> 이 요청은 HTML 요청과 같이 페이지의 loader를 다시 실행하므로, `GET` 요청의 loader는 저장된 상태를 바꾸지 않으며(RFC 9110, section 9.2.1), 제자리에서 렌더한 액션의 페이지(HY-26, HY-58, HY-69)는 자기 URL의 `GET` 요청 데이터를 받는다.

- **HYC-11** <a id="HYC-11.1"></a> 브라우저 코드는 `data(region)`, `render(region, data)`, `set(region, path, value)`를 제공한다. `data`는 영역의 보관 데이터의 promise를 반환하고, `render`는 영역의 보관 데이터를 교체하며, `set`은 영역의 보관 데이터에서 점으로 구분한 경로(맵 키와 목록 인덱스)의 값 하나를 교체한다. <a id="HYC-11.2"></a> 영역은 보관한 라우트의 라우트 영역(HY-30)이어야 하며, 다른 영역은 실패한다. <a id="HYC-11.3"></a> 데이터에 없는 경로는 실패한다. <a id="HYC-11.4"></a> `render`와 `set`은 이어서 영역을 단독으로 렌더해(HY-13) 영역 요소에 `innerMorph`로 스왑한다. <a id="HYC-11.5"></a> 페이지 영역은 보관한 라우트의 템플릿과 보관한 라우트 영역을 쓴다(HY-13). <a id="HYC-11.6"></a> 이 함수들은 데이터를 보관하지 않은 동안의 HYC-7 문서 요청 외에는 요청을 보내지 않는다. <a id="HYC-11.7"></a> 변경 추적은 없다. 데이터를 바꾸는 코드가 렌더를 요청한다. <a id="HYC-11.8"></a> 호출은 호출 순서대로 하나씩 실행되며, 각 호출은 앞 호출이 남긴 보관 데이터에서 시작한다. <a id="HYC-11.9"></a> 호출은 자기 영역의 보관 데이터를 확인하며, 스왑 전에 응답(HYC-4)이 그 데이터를 교체했으면 스왑, 보관, 저장 없이 끝나고, 스왑 중에 교체했으면 보관과 저장을 하지 않고 보관 데이터로 영역을 다시 렌더한다. <a id="HYC-11.10"></a> 그 영역을 바꾸지 않은 응답은 호출에 영향을 주지 않는다.

- **HYC-5** <a id="HYC-5.1"></a> 템플릿은 요소에 `hy-set="path=value; path=value"` 속성을 줄 수 있으며, 각 값은 JSON 리터럴이고 각 경로는 HYC-11을 따른다. <a id="HYC-5.2"></a> 요소나 그 안의 요소를 클릭하면, `id`가 보관한 라우트의, 데이터를 보관하지 않은 동안에는 현재 페이지 라우트의(HYC-7) 라우트 영역 이름인 가장 가까운 상위 요소의 보관 데이터에서 모든 대입을 실행하고 그 영역을 한 번 렌더한다. <a id="HYC-5.3"></a> 템플릿은 대입할 값을 계산하며, 예를 들어 `hy-set="service.close.flag={? service.close.flag}0{:}1{/}"`처럼 쓴다. <a id="HYC-5.4"></a> `hy-set`은 JavaScript가 있을 때만 동작한다.

## 클라이언트 stream 구독

- **HYC-17** <a id="HYC-17.1"></a> `packages/client`의 TypeScript 클라이언트 `Hyper`는 `subscribe(url, listener, options)`를 제공하며, 이는 `url`의 event stream을 열고 `close()`를 가진 구독을 돌려준다. <a id="HYC-17.2"></a> 요청은 클라이언트의 `options.fetch`(HyperOptions의 `fetch`, 옵션이 없으면 전역 `fetch`)로 `GET` 메서드, 헤더 `Accept: text/event-stream`, `credentials: 'same-origin'`을 써서 보내며, HYC-7의 문서 요청과 같은 방식이다. <a id="HYC-17.3"></a> listener는 `onEvent(event)`와 `onError(error)`를 가진다. `onEvent`는 각 event를 `event`, `data`, `id`와 함께 받고(HYC-18), `onError`는 HYC-20의 각 실패를 받는다. <a id="HYC-17.4"></a> 옵션은 `watchdogMs`다(HYC-20). <a id="HYC-17.5"></a> 클라이언트가 dispose되었으면(HYC-21) `subscribe`는 throw하며, `watchdogMs`가 양의 유한한 수가 아니어도 throw한다. <a id="HYC-17.6"></a> 이 구독은 TypeScript 클라이언트만 가지며, PHP, Python, Node 서버에는 클라이언트가 없고 이 저장소의 다른 클라이언트에도 stream이 없다.

- **HYC-18** <a id="HYC-18.1"></a> 응답 본문은 WHATWG HTML의 "server-sent events" event stream으로 읽는다. 필드는 `data`, `event`, `id`, `retry`이고, 줄은 CRLF, LF 또는 CR로 끝나며, `:`로 시작하는 줄은 주석이고, 빈 줄마다 event를 발생시킨다. <a id="HYC-18.2"></a> event의 `event`는 그 `event` 필드이고 필드가 없으면 `message`이며, 그 `data`는 event의 `data` 필드들을 LF로 이어 붙인 값이다. <a id="HYC-18.3"></a> event의 `id`는 표준이 보관하는 마지막 event ID, 즉 stream이 보낸 마지막 `id` 필드의 값이며, `id` 필드가 없는 event도 이 값을 가진다. <a id="HYC-18.4"></a> 값이 잘못된 `id` 또는 `retry` 필드와 이름을 모르는 필드는 표준이 말하는 대로 무시하며, 실패가 아니다. <a id="HYC-18.5"></a> 구현은 stream을 npm 패키지 `eventsource-parser`로 파싱하며, 손으로 쓴 파서로 파싱하지 않는다: 줄 끝, byte order mark, 완성되지 않은 마지막 줄은 표준이 정하고 그 유지보수되는 파서가 이미 구현하고 있다(S1). <a id="HYC-18.6"></a> 이 패키지는 이 규칙의 TypeScript 클라이언트에서의 선택이며, 정확한 버전과 그 이유는 HYC-17의 구현 row가 끝날 때 `docs/operations/dependencies.md`에 고정해 기록한다. <a id="HYC-18.7"></a> UTF-8이 아닌 본문은 파싱 실패다. 구현은 본문을 fatal decoder로 decode하며, 이 실패는 HYC-20의 오류다.

- **HYC-19** <a id="HYC-19.1"></a> 구독은 표준이 정한 대로 마지막 event ID와 재연결 지연을 보관한다. <a id="HYC-19.2"></a> 마지막 event ID는 `id` 필드를 가진 마지막 event의 `id`이며 재연결 사이에도 보관하고, 재연결 지연은 마지막 `retry` 필드의 값(밀리초)이며 서버가 보내지 않았으면 1000이다. <a id="HYC-19.3"></a> stream이 끝나거나, HYC-20의 오류로 실패하거나, 2xx가 아닌 상태로 응답하면, 클라이언트는 실패를 `onError`에 보고한 뒤 재연결 지연만큼 기다렸다가 다시 연결한다. <a id="HYC-19.4"></a> 재연결 요청은 마지막 event ID가 비어 있지 않을 때 헤더 `Last-Event-ID`에 그 값을 담으며, stream의 위치를 나타내는 query 매개변수나 다른 헤더 같은 다른 커서는 보내지 않는다. <a id="HYC-19.5"></a> 1000 ms 기본값은 서버가 지연을 정하지 않은 클라이언트의 재연결 빈도를 제한한다. <a id="HYC-19.6"></a> 클라이언트는 `close()` 또는 `dispose()`(HYC-21)가 호출될 때까지 재연결한다.

- **HYC-20** <a id="HYC-20.1"></a> 구독에는 byte watchdog이 있다. <a id="HYC-20.2"></a> 본문의 byte가 `watchdogMs` 밀리초 동안 하나도 도착하지 않으면, stream은 원인에 URL과 시간이 담긴 오류로 실패하고, 클라이언트는 이어서 재연결한다(HYC-19). <a id="HYC-20.3"></a> watchdog은 byte가 도착할 때마다 다시 시작하며, event가 아니라 byte를 센다. 따라서 완성된 event 없이 byte만 보내는 stream은 실패하지 않는다. <a id="HYC-20.4"></a> `watchdogMs`의 기본값은 30000이다. 그러면 byte가 오지 않는 연결은 일반적인 역방향 proxy가 기본으로 적용하는 60초 idle timeout보다 먼저 실패한다. 그 timeout은 클라이언트에 알리지 않고 연결을 닫는다. <a id="HYC-20.5"></a> 구독의 모든 실패는 원인과 함께 `onError`에 보고하며, 여기에는 watchdog timeout, 2xx가 아닌 응답(상태와 URL을 담음), 네트워크 실패, HYC-18의 파싱 실패가 포함된다. <a id="HYC-20.6"></a> 어떤 실패도 조용히 버리지 않는다(P8). <a id="HYC-20.7"></a> close와 dispose는 실패가 아니며 아무것도 보고하지 않는다.

- **HYC-21** <a id="HYC-21.1"></a> 클라이언트의 `dispose()`는 모든 구독과 모든 대기 요청을 중단한다. <a id="HYC-21.2"></a> 각 구독에 대해 요청을 중단하고, watchdog timer와 재연결 timer를 지우며, 구독을 닫힘으로 표시하고, 클라이언트의 모든 대기 중인 영역 요청과 문서 요청을 중단한다(HYC-3, HYC-7). <a id="HYC-21.3"></a> `dispose()`가 반환된 뒤에는 클라이언트에 실행 중인 timer가 없고 listener를 호출하지 않으며, 나중에 도착하는 응답은 버린다. <a id="HYC-21.4"></a> `dispose()`는 여러 번 호출할 수 있고, 첫 호출 뒤의 호출은 효과가 없다. <a id="HYC-21.5"></a> `dispose()` 뒤의 `subscribe`는 throw하여, 클라이언트가 dispose된 뒤에 구독이 시작되지 않게 한다.

## 템플릿 전달

- **HYC-12** <a id="HYC-12.1"></a> 브라우저는 렌더가 템플릿에 닿을 때 그 템플릿을 불러온다. <a id="HYC-12.2"></a> 브라우저는 렌더하고, 렌더가 불러오지 않은 템플릿을 요청했으면 그 템플릿들을 색인의 URL로 각각 불러온 뒤 다시 렌더하며, 렌더가 끝나거나 다른 이유로 실패할 때까지 반복한다. <a id="HYC-12.3"></a> 데이터가 고르지 않은 분기의 템플릿처럼 어떤 렌더도 닿지 않는 템플릿은 불러오지 않는다. 그래서 여러 화면 가운데 하나를 고르는 라우트 템플릿은 보여 주는 화면만 불러온다. <a id="HYC-12.4"></a> 라우트의 진입 템플릿은 레이아웃, 제목, 페이지가 아닌 모든 영역 템플릿, 라우트 템플릿, 모든 라우트 영역 템플릿이며, 영역 요청이면 진입 템플릿 불러오기를 요청과 동시에 시작하고, 응답 URL이 다른 라우트로 라우팅되면(예: 리다이렉트 뒤) 그 라우트의 진입 템플릿을 불러온다. <a id="HYC-12.5"></a> 서버가 렌더한 페이지를 열 때는 템플릿을 불러오지 않는다. 브라우저가 그 페이지의 영역을 처음 렌더할 때 필요한 템플릿을 불러온다. <a id="HYC-12.6"></a> 클라이언트 렌더 문서는 데이터를 내장하지 않으므로(HY-31) 브라우저는 `hyper/data.tpl`을 결코 렌더하지 않으며, 그것을 렌더하는 Node 서버가 색인에 그것이 있는지 확인한다. <a id="HYC-12.7"></a> 색인에 없는 이름은 렌더를 실패시킨다(HYC-14). <a id="HYC-12.8"></a> 불러온 템플릿은 페이지가 unload될 때까지 유지된다. <a id="HYC-12.9"></a> 모든 페이지를 렌더하는 Node 서버는 열 때 색인의 모든 템플릿을 읽는다.

- **HYC-16** <a id="HYC-16.1"></a> 페이지는 자기가 쓰는 자원만 요청하고, 페이지가 열려 있는 동안 각 자원을 많아야 한 번 요청한다. <a id="HYC-16.2"></a> 자원은 템플릿 파일, 스타일시트, 스크립트 파일이다. <a id="HYC-16.3"></a> 브라우저는 렌더가 템플릿에 닿을 때 그 템플릿을 불러온다(HYC-12). <a id="HYC-16.4"></a> 레이아웃은 자기가 렌더하는 내용의 스타일시트만 링크하고, 브라우저는 렌더한 head마다 그 스타일시트 링크를 적용하며 이미 적용한 링크는 그대로 둔다(HYC-15). 애플리케이션이 모든 페이지에 링크하는 스타일시트는 모든 페이지가 쓰는 스타일시트다. <a id="HYC-16.5"></a> 에셋 빌드는 클라이언트 진입 파일 `public/assets/hyper-<hash>.js`를 쓰고, 진입 파일이 정적으로 불러오지 않고 `import()`로만 불러오는 코드는 조각 파일 `public/assets/hyper-chunk-<hash>.js`로 쓴다. 브라우저는 그 코드가 처음 실행될 때 `/assets/` 아래의 절대 URL로 조각을 불러온다. 그래서 정적 셸이 인라인한 진입 파일도 조각을 불러오고, 브라우저는 모듈 하나를 한 번만 불러온다. <a id="HYC-16.6"></a> 에셋 빌드는 애플리케이션이 이름을 정하는 파일을 쓰지 않는다. 템플릿 파일과 색인(HR-34), 진입 파일, 조각 파일, 진입 파일의 URL을 유일한 멤버 `hyper`로 담은 `--output` 디렉터리의 `manifest.json`, 정적 셸을 쓴다. <a id="HYC-16.7"></a> 애플리케이션은 자기 스타일시트를 두고 링크하며, 레이아웃이 링크하는 스타일시트처럼 정적 배포물이 같은 경로에 담을 `public/` 아래 파일을 `--static`으로 밝힌다. `public/assets`에는 이전 build의 파일이 남으므로, 에셋 빌드는 `public/assets`의 다른 파일을 배포물에 추가하지 않는다. <a id="HYC-16.8"></a> 정적 셸은 `<meta name="hyper-api">`와 인라인한 진입 파일을 담고 스타일시트는 담지 않는다. 브라우저는 페이지를 보이기 전에 렌더한 레이아웃의 스타일시트 링크를 적용하기 때문이다(HYC-8, HYC-15). <a id="HYC-16.9"></a> `tests/scripts/build-assets.test.mts`는 진입 파일이 `import()`로 모듈을 불러오는 애플리케이션을 빌드한다.

## 유지 데이터

- **HY-37** <a id="HY-37.1"></a> 라우트 영역은 유지 경로를 선언할 수 있으며, 브라우저에서 바뀌는 것은 라우트 영역뿐이므로(HY-30) 매니페스트 검사는 매니페스트 영역의 `keep`을 거부한다. <a id="HY-37.2"></a> 예: `"keep": { "notice.closed": "server", "sort": "localStorage" }`. <a id="HY-37.3"></a> 경로는 점으로 이은 경로로, 첫 항은 맵 키 `[A-Za-z_][A-Za-z0-9_]*`이고 그 뒤로 `.`과 맵 키 또는 10진수 목록 인덱스가 몇 번이든 이어진다. <a id="HY-37.4"></a> 유지 값은 종류가 가리키는 저장소에 남아 새로고침 후에도 유지된다:

| 종류 | 저장소 | 값이 바뀔 때의 요청 | 첫 SSR 문서 |
| --- | --- | --- | --- |
| `server` | 서버 세션 | 렌더가 기다리지 않는 백그라운드 요청 1회 | 값이 들어 있음 |
| `cookie` | 브라우저 코드가 쓰는 쿠키 `hy-keep`. `HttpOnly`일 수 없다 | 없음 | 값이 들어 있음 |
| `localStorage` | 브라우저 `localStorage` | 없음 | 로더 값이 들어 있음. 브라우저가 불러온 뒤 유지 값을 렌더한다 |
| `sessionStorage` | 탭의 브라우저 `sessionStorage` | 없음 | 로더 값이 들어 있음. 브라우저가 불러온 뒤 유지 값을 렌더한다 |

- **HY-38** <a id="HY-38.1"></a> 사용자가 브라우저에서 마지막으로 정한 값이 우선한다. 로더 데이터는 기본값이다. <a id="HY-38.2"></a> 유지 값은 영역 데이터에 그 경로가 있고, 유지 값이 template 데이터 모델의 값이며(±(2^53 − 1) 밖의 수는 아니다), 다음을 만족할 때 그 경로의 값에 맞는다:

  - <a id="HY-38.3"></a> null, 불리언, 숫자, 문자열은 같은 타입이다;
  - <a id="HY-38.4"></a> 맵은 맵을 대체하며, 데이터 맵에 키가 있으면 유지 맵은 같은 키를 가지고 모든 키의 값이 같은 키의 값에 맞는다;
  - <a id="HY-38.5"></a> 목록은 목록을 대체하며, 데이터 목록에 항목이 있으면 모든 유지 항목이 그 첫 항목에 맞는다.

  <a id="HY-38.6"></a> 빈 데이터 맵이나 목록은 형태를 알려 주지 않으므로 어떤 맵이나 목록도 맞으며, 그런 값은 아래의 렌더 확인이 다룬다.

  <a id="HY-38.7"></a> 맞지 않는 유지 값은 무시한다.

  - <a id="HY-38.8"></a> 서버는 `server`와 `cookie` 값을 읽어 맞는 값을 `kept`로 보낸다(HY-17). <a id="HY-38.9"></a> 이 값은 `regions`를 바꾸지 않는다. <a id="HY-38.10"></a> 서버는 요청이 HTTPS를 쓰거나 애플리케이션이 HTTPS를 선언하면(HY-45) `cookie` 값을 쿠키 `__Host-hy-keep`에서, 그렇지 않으면 `hy-keep`에서 읽으며, HTTPS에서는 호스트 전용 쿠키만 인정한다. 형제 서브도메인 같은 다른 호스트는 이 쿠키를 설정할 수 없기 때문이다. <a id="HY-38.11"></a> 쿠키 값은 URL 인코딩한 JSON 객체 `{ "<region>": { "<path>": <value> } }`다.
  - <a id="HY-38.12"></a> 영역은 유지 값을 적용한 데이터로 렌더하며, 적용 순서는 `kept`의 값, `localStorage`와 `sessionStorage` 값, 저장이 끝나지 않은 `server` 값(HYC-13)이다. <a id="HY-38.13"></a> 서버는 `kept`의 값만 적용한다. <a id="HY-38.14"></a> 브라우저는 모두를 자기가 보관하고 렌더하는 데이터에 적용하며, 서버와 동기화하지 않는다. <a id="HY-38.15"></a> 서버가 렌더한 문서에서는 브라우저가 내장 데이터를 보관한 뒤에, 또는 브라우저 값이 저장되어 있어 데이터를 얻은 뒤에(HYC-4, HYC-7) 적용하고, 데이터가 바뀐 영역을 모두 렌더한다.
  - <a id="HY-38.16"></a> 유지 값을 적용한 영역이 단독으로(HY-13) 렌더되지 않으면, 그 영역은 로더 데이터로 렌더하고 그 유지 값을 `kept`와 보관 데이터에서 뺀다. <a id="HY-38.17"></a> 서버는 내장 데이터를 렌더하기 전에(HY-31) 그 값을 빼므로, 서버와 브라우저는 같은 문서를 렌더한다. <a id="HY-38.18"></a> 로더 데이터로도 영역이 렌더되지 않으면 렌더가 실패한다(HY-43, HYC-14).

  <a id="HY-38.19"></a> 유지 값은 그 경로의 값을 대신하므로, 데이터의 모든 map은 키를 그 순서대로 유지하고, 유지 map은 자신의 순서대로 키를 유지한다.

- **HYC-13** <a id="HYC-13.1"></a> `set`, `render`, `hy-set`이 경로를 바꾸면, 브라우저는 영역을 먼저 렌더한 뒤, 바뀐 경로와 같거나, 그 아래에 있거나, 그 경로를 포함하는 모든 유지 경로를 저장하며, 각각 그 유지 경로에 지금 있는 값을 저장한다. <a id="HYC-13.2"></a> `server` 값은 서버가 그 값에 204로 응답하거나 같은 경로의 이후 변경이 저장될 때까지 대기 상태이며, 대기 중에는 HY-38대로 적용한다. <a id="HYC-13.3"></a> 한 경로의 저장은 한 번에 하나씩 보낸다. 그 경로의 저장이 진행 중일 때 생긴 변경은 그 저장이 끝난 뒤에 보내며, 가장 최근 값만 보낸다. <a id="HYC-13.4"></a> 저장에 실패하면 값을 계속 대기 상태로 두고, 그 경로의 이후 변경이 없으면 영역을 실패로 표시한다(HYC-14). <a id="HYC-13.5"></a> `server`이면 폼 필드 `_csrf`(보관한 `shared.csrf`, HY-10), `region`, `path`, `value`(값의 JSON 텍스트)로 `POST <base path>/_hyper/keep`을 보내고 응답을 기다리지 않는다. <a id="HYC-13.6"></a> `cookie`이면 쿠키 `hy-keep`을 `Path=/`, `SameSite=Lax`, 1년의 `Max-Age`로 쓴다. HTTPS에서는 쿠키 이름이 `__Host-hy-keep`이고 `Secure`도 붙는다. 그래서 형제 서브도메인 같은 다른 호스트가 이 쿠키를 설정할 수 없다. <a id="HYC-13.7"></a> 쿠키 값은 URL 인코딩한 JSON 객체 `{ "<region>": { "<path>": <value> } }`다.

- **HY-40** <a id="HY-40.1"></a> 서버는 `POST <base path>/_hyper/keep`에 값을 세션에 저장한 뒤 상태 204로, CSRF 토큰이 맞지 않으면 상태 403으로, 영역이 그 경로를 `server`로 선언하지 않았거나, 값이 JSON이 아니거나, JSON 텍스트가 4,096바이트보다 길거나, 값이 template 데이터 모델의 값이 아니면 상태 400으로 응답한다. <a id="HY-40.2"></a> 경로 `/_hyper/keep`은 예약되어 있다. 라우트 경로는 `/_hyper`로 시작할 수 없다.

## 요청 boundary와 실패

- **HY-42** <a id="HY-42.1"></a> 요청 경로는 요청 대상의 경로다: 요청 대상에서 첫 `?`나 `#` 앞까지의 부분이며, absolute-form 대상(`http://host/path`)에서는 authority 뒤의 부분이다. <a id="HY-42.2"></a> 그 이상 디코드하지 않는다. <a id="HY-42.3"></a> 경로는 RFC 9112가 요청 대상에 요구하는 `!`부터 `~`까지의 출력 가능한 ASCII 문자로 이루어져야 하며, 모든 query와 form의 이름 및 값(HY-56, HY-57)과 `HX-Current-URL` header는 올바른 UTF-8이어야 한다; 그렇지 않으면 서버는 어떤 loader나 action도 실행하기 전에 상태 400으로 응답한다. <a id="HY-42.4"></a> Cookie는 검사하지 않는다: 서버는 JSON 객체가 아닌 `hy-keep` cookie를 무시하고, 그 cookie의 값 가운데 맞지 않는 값(HY-38)을 무시하며, 자기가 만든 identifier가 아닌 session cookie에는 새 session을 시작한다(HY-45). <a id="HY-42.5"></a> 디코드한 query나 form 이름이나 값(HY-56), route parameter(HY-5), cookie 값(HY-129) 앞의 U+FEFF는 그 문자이며, 어떤 server와 브라우저 코드도 그것을 지우지 않는다.

- **HY-43** <a id="HY-43.1"></a> 애플리케이션이 처리하지 않은 예외는 텍스트 `Internal Server Error`와 함께 상태 500을 만든다. <a id="HY-43.2"></a> 응답에는 예외 메시지, 파일 경로, 스택 트레이스가 없으며, 서버는 그것을 로그에 쓴다. <a id="HY-43.3"></a> PHP 설정 `display_errors`는 PHP가 요청을 시작하기 전에 꺼져 있어야 하는데, PHP는 애플리케이션이 실행되기 전에 시작 경고(예: `max_input_vars`)를 쓰기 때문이다.

- **HY-74** <a id="HY-74.1"></a> 서버가 요청에 응답하는 동안 그 서버의 런타임이 발생시키는 경고는 오류가 되며, 그 요청은 HY-43으로 실패한다. <a id="HY-74.2"></a> 그렇지 않으면 런타임은 계속 실행되고, 메시지는 로그나 출력에만 전달되는 반면 서버는 잘못된 page를 상태 200으로 보내게 된다. <a id="HY-74.3"></a> 표현식이 억제한 오류는 억제된 상태로 남는다. <a id="HY-74.4"></a> 서버는 자기 처리를 요청에 대해서만 설치하고, 그 뒤에 이전 처리를 복원한다.

  - <a id="HY-74.5"></a> PHP: 정의되지 않은 변수, 정의되지 않은 배열 키, 잘못된 인자처럼 PHP가 발생시키는 모든 경고, 알림, 폐기 예정 알림은 오류 handler를 통해 예외가 된다; `@`가 억제한 오류는 `error_reporting()`에 들어 있지 않고 억제된 상태로 남는다.
  - <a id="HY-74.6"></a> Python: 요청에 응답하는 동안 발생하는 `warnings` 모듈의 모든 경고(예: `DeprecationWarning`, `RuntimeWarning`)는 예외로 발생한다: 요청이 진행되는 동안 필터 `error`가 설정된다.
  - <a id="HY-74.7"></a> Node: 요청에 응답하는 동안 `process.emitWarning`으로 발생한 경고는 호출한 곳에서 그 오류를 던진다.

- **HY-44** <a id="HY-44.1"></a> 공유 데이터와 영역 데이터는 template 데이터 모델의 값이다. <a id="HY-44.2"></a> ±(2^53 − 1) 밖의 수는 정수든 아니든 HY-43으로 실패하며, 문서든 JSON이든 마찬가지다. <a id="HY-44.3"></a> 서버는 템플릿이 읽지 않는 값을 제거(HY-73)하기 전에 context handler(HY-124), 공유 데이터 핸들러, 모든 로더가 돌려준 모든 값을 검사하므로, 데이터 모델 밖의 값은 어떤 템플릿도 읽지 않아도 실패한다. <a id="HY-44.4"></a> context handler(HY-124), 공유 데이터 핸들러, 모든 로더는 맵을 돌려준다: PHP에서는 비어 있거나 목록이 아닌 배열이고, Python에서는 `dict`이며, Node에서는 context handler가 `Map`이고 공유 데이터 핸들러와 모든 로더는 일반 객체나 `Map`이다. <a id="HY-44.5"></a> 목록 같은 다른 값은 HY-43으로 실패한다. <a id="HY-44.6"></a> 검사는 template 데이터 모델의 host binding(VAL-13, VAL-14)에 이어, 바인딩된 값에 native object가 없는지 확인하는 것(VAL-19)이다: binding이 데이터 모델의 값으로 바꾸는 값(예: PHP `stdClass`나 `JsonSerializable`, Node 일반 객체)은 통과하고, binding이 native object로 두는 애플리케이션 객체(예: PHP `DateTimeImmutable`, Node `Date`, Python `datetime`)는 모든 서버에서 HY-43으로 실패한다. <a id="HY-44.7"></a> JSON 응답은 요청의 매개변수만 다시 검사하는데, 이 검사가 공유 데이터와 영역 데이터를 이미 다뤘고 kept 값은 데이터 모델의 값일 때만 응답에 들어가기 때문이다(HY-38). <a id="HY-44.8"></a> data model 밖의 값은 HY-46.2의 클래스로 실패하며 그 메시지는 실패의 종류를 나타낸다: `a number outside ±(2^53 − 1) is not a value of the data model (HY-44)`, `a number that is not finite is not a value of the data model (HY-44)`, `a string that is not UTF-8 text is not a value of the data model (HY-44)`, `lists and maps that nest deeper than 64 levels are not a value of the data model (HY-44)`, 그리고 그 밖의 값이나 map key에는 `a value or a map key of another type is not a value of the data model (HY-44)`이다.

- **HY-45** <a id="HY-45.1"></a> 서버 session cookie의 이름은 요청이 HTTPS를 쓰거나 애플리케이션이 HTTPS로 제공된다고 선언하면 `__Host-hy-session`이고(TLS를 종료하는 proxy 뒤의 서버는 반드시 이 선언을 해야 한다), 그 밖에는 `hy-session`이다; 애플리케이션은 이름을 고르지 않는다. <a id="HY-45.2"></a> 브라우저는 `__Host-` cookie를 자기 host에서 온 것만 받으므로, 형제 subdomain 같은 다른 host는 방문자에게 자기가 아는 token의 session을 줄 수 없다. <a id="HY-45.3"></a> cookie는 `Path=/`, `Domain` 없음, `HttpOnly`, `SameSite=Lax`를 가지며, prefix와 같은 조건에서 `Secure`다. <a id="HY-45.4"></a> 서버는 자기가 만든 session identifier만 받으며, 요청이 session 데이터를 읽거나 쓸 때만 session을 시작한다: 라우팅 전에 서버가 거절하는 요청(HY-42)이나 path가 어떤 route와도 맞지 않는 요청은 session을 만들지 않는다. <a id="HY-45.5"></a> 모든 응답은 `Content-Security-Policy: frame-ancestors <sources>`를 담으며, sources는 애플리케이션이 정하고 기본값은 `'self'`다.

- **HY-46** <a id="HY-46.1"></a> 리다이렉트 위치는 애플리케이션 경로다: `/`로 시작하고 두 번째 문자가 `/`나 `\`가 아니며, 제어 문자(C0, DEL, C1), 공백, `\`를 담지 않는 올바른 UTF-8이고, 점이 percent-encode된 경우(`%2e`)를 포함해 path에 `.`이나 `..` segment가 없어야 한다. <a id="HY-46.2"></a> 애플리케이션 경로가 아닌 위치로 리다이렉트를 만들면 오류 `a redirect location is not an application path (HY-46)`로 실패하며, 그 클래스는 PHP에서 `InvalidArgumentException`, Node에서 `RangeError`, Python에서 `ValueError`다.

- **HYC-14** <a id="HYC-14.1"></a> 영역 요청이 JSON이 아닌 응답을 받거나, 렌더, 보관된 값 저장, 템플릿 로드, 스타일시트 로드(HYC-15)가 실패하면, 브라우저는 교체하지 않고 히스토리도 바꾸지 않는다. <a id="HYC-14.2"></a> 영역 요소에 `hy-error` 속성을 응답 상태로 설정하고, 네트워크나 렌더 실패면 `0`으로 설정한다; 그 뒤 성공적으로 렌더된 모든 영역에서는 그 속성을 지운다. <a id="HYC-14.3"></a> 취소된 요청은 실패가 아니다; 제한 시간(`hx-timeout`이나 `htmx.config.defaultTimeout`)이 지나 htmx가 중단시킨 요청은 네트워크 실패다. <a id="HYC-14.4"></a> `render`, `set`, `hy-set`은 영역이 렌더된 뒤에만 보관된 데이터를 바꾸며, 실패하면 보관된 데이터는 그대로다. <a id="HYC-14.5"></a> 클라이언트에서 문서 렌더가 실패하거나, 서버 렌더의 히스토리 복원에서 스타일시트 로드가 실패하면, 브라우저는 body에 `hy-error`를 설정한다.

- **HY-129** <a id="HY-129.1"></a> 요청의 cookie는 그 `Cookie` header를 한 번 파싱한 결과이며, 모든 서버에서 같다. <a id="HY-129.2"></a> header는 받은 그대로의 field value 바이트다. <a id="HY-129.3"></a> 클라이언트는 `Cookie` 줄을 하나만 보내며(RFC 6265 section 5.4), HTTP/2에서는 서버가 cookie 줄들을 `; `로 잇는다(RFC 9113 section 8.2.3). <a id="HY-129.4"></a> 줄을 따로 받는 host는 파싱 전에 `; `로 잇는다: Node 서버는 `; `로 잇는 `node:http`의 `cookie`를 쓰고, Python `create_server`는 모든 `Cookie` 줄을 읽으며, Python ASGI callable은 scope의 `cookie` header들을 `; `로 잇는다. <a id="HY-129.5"></a> 이어진 header를 받는 host는 받은 그대로 쓴다: PHP는 SAPI가 주는 `$_SERVER['HTTP_COOKIE']`를 쓰고, Python WSGI callable은 `HTTP_COOKIE`를 Latin-1로 encode해 바이트로 되돌린다. <a id="HY-129.6"></a> PHP built-in server는 HTTP/1.1의 여러 `Cookie` 줄을 `, `로 잇는다; 그래서 RFC 6265 section 5.4를 어긴 그런 요청은 그 이어진 값의 cookie를 준다. <a id="HY-129.7"></a> header는 `;`마다 쌍으로 나뉘고, 쌍 양끝의 space와 tab은 지워지며, 쌍은 첫 `=`에서 이름과 값으로 나뉜다. <a id="HY-129.8"></a> `=`가 없거나, 이름이 비었거나, 이름이 올바른 UTF-8이 아니거나, percent-decoding한 값이 올바른 UTF-8이 아닌 쌍은 cookie가 되지 않는다; 이름은 decode하지 않고, 값은 percent-decode하며, `%`와 16진수 두 자리는 그 자리의 바이트이고 `+`를 포함한 다른 모든 바이트는 그 자신이다. <a id="HY-129.9"></a> cookie가 되는 쌍 가운데 한 이름의 첫 쌍이 쓰인다. <a id="HY-129.10"></a> PHP 서버의 어느 부분도 `$_COOKIE`를 읽지 않는데, PHP가 그 이름을 변수 이름처럼 바꾸기 때문이다(`a.b`는 `a_b`가 되고, `a[x]`는 배열이 된다): native session은 `session.use_cookies`를 false로 둔 채 실행되고, 이 파싱에서 나온 HY-45의 identifier를 `session_start()` 전에 `session_id()`로 받으며, 파싱에서 identifier가 나오지 않으면 아무것도 받지 않고, 서버는 HY-45의 session cookie를 직접 전송한다. <a id="HY-129.12"></a> 요청의 cookie는 각 이름을 그 값에 대응시키는 map이다.

- **HY-130** <a id="HY-130.19"></a> 애플리케이션의 응답은 이 문서의 규칙이 그 응답에 대해 밝힌 header를 가지며, 규칙이 다른 header가 없다고 밝히지 않는 한 다른 header를 가질 수 있다. 서버의 호스트는 어떤 응답에든 header를 더할 수 있다. <a id="HY-130.20"></a> header 이름은 대소문자를 구분하지 않는다. ASCII 대소문자만 다른 이름은 같은 이름이다(RFC 9110 5.1절).

## Node 서버

- **HY-54** <a id="HY-54.1"></a> Node 서버 패키지 `@polyspec/hyper-server`는 이 문서의 서버 규칙을 PHP 서버와 같은 방식으로 구현하며, 그 테스트는 PHP 서버 테스트의 case를 같은 fixture에 대해 실행한다. <a id="HY-54.2"></a> PHP 서버와의 차이는 다음뿐이다:

  - <a id="HY-54.3"></a> 문서는 브라우저가 문서 JSON 값을 렌더하는 방식대로(HY-12, HY-31, HY-38) asset build의 브라우저 코드와 템플릿 파일(HR-34)로 렌더하며, reply가 요청하면 그 데이터를 내장한다(HY-92).
  - <a id="HY-54.4"></a> JSON 텍스트는 PHP `json_encode`에 `JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES`를 준 것과 같은 바이트다. <a id="HY-54.5"></a> 문자열은 `"`, `\`, U+0020 아래의 제어 문자(`\b`, `\f`, `\n`, `\r`, `\t`, 나머지는 `\u00xx`), U+2028과 U+2029(`\u2028`, `\u2029`)를 이스케이프하며, 다른 문자는 이스케이프하지 않는다. <a id="HY-54.6"></a> ±(2^53 − 1) 안의 정수는 10진수로 쓴다. <a id="HY-54.7"></a> 다른 수는 다시 읽으면 같은 수가 되는 가장 짧은 자릿수로 쓴다: 소수점 위치 p(수는 0.d × 10^p)가 −3과 17 사이이면 위치 표기로, 그 밖이면 소수 자리를 하나 이상 가진 `d.ddde±x`로 쓰며; 음의 0은 `-0`이다. <a id="HY-54.8"></a> kept 값(HY-38, HY-40)은 PHP `json_decode`처럼 decode한다: 정수 literal은 정수이고 다른 literal은 float이며, ±(2^53 − 1) 밖의 수나 유한하지 않은 수는 데이터 모델의 값이 아니고, 512단계로 중첩된 container, 짝 없는 surrogate escape, U+0000으로 시작하는 key는 실패한다.
  - <a id="HY-54.12"></a> JavaScript에서 데이터 모델의 값은 null, boolean, ±(2^53 − 1) 안의 number나 bigint, 문자열, 배열, 문자열 key의 `Map`, 또는 일반 객체다. <a id="HY-54.13"></a> 짝 없는 surrogate를 가진 문자열(UTF-8 형태가 없다)과 그 밖의 모든 값은 HY-43으로 실패한다.
  - <a id="HY-54.14"></a> loader와 action은 요청, reply(HY-52), 애플리케이션이 key로 바인딩한 서비스를 담은 context 인자 하나를 받는다.
  - <a id="HY-54.15"></a> session 저장소는 각 session을 한 디렉터리의 파일에 두며, 파일 이름은 저장소가 만든 64자리 16진수 identifier다. <a id="HY-54.16"></a> session cookie는 PHP session cookie의 속성과 순서로 쓰며(`<name>=<id>; path=/; secure; HttpOnly; SameSite=Lax`, `secure`는 HY-45의 조건에서), 한 session의 요청들은 차례로 실행한다.

- **HY-97** <a id="HY-97.1"></a> 모든 서버는 선택 요청 hook `around`를 받는다: `create_server`, `create_wsgi`, `create_asgi`(Python)의 인자, `App.listener`와 `App.server`(Node)의 옵션, `App::open`(PHP)의 인자다. <a id="HY-97.2"></a> 서버는 애플리케이션에 넘기는 모든 요청마다 서버가 만든 그대로의 요청과 함수 `answer`로 `around`를 한 번 호출하고, `around`가 돌려주는 응답을 전송한다. <a id="HY-97.3"></a> `answer(request)`는 `around`가 없을 때 서버가 하듯이 요청에 대해 애플리케이션을 실행한다: 요청과 서버의 session 저장소로 `App.handle`을 호출하며, `App.handle`은 HY-120이 정하는 대로 요청의 session cookie로 그 session을 열고, 응답 hook(HY-60)을 호출하고, session을 닫는다; `answer`는 새 session의 cookie를 맨 앞에 둔 응답을 돌려준다(HY-45). <a id="HY-97.4"></a> `around`는 요청 또는 바꾼 복사본으로 `answer`를 호출할 수 있다. 복사본의 예는 `Request.with_header(name, value)`(Python), `request.withHeader(name, value)`(Node), `Request::withHeader($name, $value)`(PHP)로 header를 설정한 복사본이다(이름은 요청이 header를 읽을 때처럼 대소문자를 무시하고 비교한다). `around`는 `answer`가 돌려주는 응답을 바꿀 수 있고, `answer`를 호출하지 않고 자기 응답을 돌려줄 수 있으며, 그 경우 서버는 그 요청에 대해 session을 열지 않고 애플리케이션의 loader, action, hook도 실행하지 않는다. <a id="HY-97.5"></a> 클라이언트가 연결을 닫아 응답 쓰기가 실패하면(HY-67), 서버는 마지막 `answer` 호출의 요청과 reply로 disconnect hook을 호출하며, `around`가 `answer`를 호출하지 않았으면 disconnect hook을 호출하지 않는다. <a id="HY-97.6"></a> Python과 Node 서버가 제공하는 public 디렉터리의 파일은 `around` 전에 제공되며 `around`에 도달하지 않는다. <a id="HY-97.7"></a> 호출할 수 없는 `around` 값은 서버를 만들 때 실패한다. <a id="HY-97.8"></a> `around`가 `answer` 밖에서 던지는 오류와 응답이 아닌 반환값은 escape된 오류다(HY-60); PHP에서도 마찬가지이며, 그때 `App::run`은 잡히지 않은 예외의 평문 500을 쓴다: 서버는 그것을 로그에 남기고 평문 500으로 응답하며, 그 500은 write hook이 받는다(HY-99).

  - <a id="HY-97.9"></a> Node 서버는 `app.server()`가 돌려주는 `node:http` 서버를 통해 같은 기능을 제공한다: 소비자는 그 서버의 `request` listener를 애플리케이션의 listener를 호출하는 listener로 바꿔, 각 요청을 자기 context에서 실행하거나, 요청과 응답에 request id header를 붙이거나, 애플리케이션보다 먼저 요청에 직접 응답한다(예: 자기 web server에서 오지 않은 요청에 400). <a id="HY-97.10"></a> `around`는 이를 `http.server` 요청 handler를 바꿀 수 없는 Python 서버의 애플리케이션에 제공한다.

- **HY-99** <a id="HY-99.1"></a> 모든 서버는 선택 write hook `written`을 받는다: `create_server`, `create_wsgi`, `create_asgi`(Python)의 인자, `App.listener`와 `App.server`(Node)의 옵션, `App::open`(PHP)의 인자다. <a id="HY-99.2"></a> 서버는 애플리케이션에 넘기는 모든 요청마다 정확히 한 번 그것을 호출하며, 다음 값들을 넘긴다: `around`에 넘긴 요청(HY-97) 또는 받은 그대로의 요청; 쓰기를 시작한 `Response`, 시작한 응답이 없으면 escape된 오류의 평문 500, 응답이 시작되기 전에 요청이 끝났으면 null; 상태 줄, header, 완전한 body가 오류 없이 쓰였는지를 말하는 `ended`; 요청 도착 뒤 경과한 밀리초(HY-60); 그리고 HY-43이 말하는 escape된 오류의 메시지인 `failure`(다른 모든 응답에는 null)다. <a id="HY-99.3"></a> 서버는 요청의 응답 처리가 끝난 뒤(애플리케이션이 반환했거나, 실패했거나, 닫힌 연결에서 멈춘 뒤, HY-67)와 쓰기가 끝나거나 실패한 뒤 가운데 늦은 시점에, 그리고 disconnect hook 전에 hook을 호출한다. <a id="HY-99.4"></a> 500을 쓸 수 없는 escape된 오류(응답이 이미 시작됐거나 연결이 닫혔기 때문)는 `ended` false와 그 failure로 보고된다. <a id="HY-99.5"></a> 어떤 adapter도 escape된 오류의 평문 500을 응답 hook에 보고하지 않는다. <a id="HY-99.6"></a> PHP는 `App::run`이 escape 함수 뒤에 등록하는 shutdown 함수에서 hook을 호출하며, `connection_aborted()`가 1이거나 header를 보낸 뒤 치명적 오류가 스크립트를 끝냈으면 `ended`는 false이고, true는 PHP가 완전한 출력을 web server에 준 것을 뜻한다. <a id="HY-99.7"></a> 출력 buffering의 두 모드 어느 쪽에서든 `ended`와 응답은 PHP가 보낸 것을 따른다: buffering이 켜져 있고 출력이 flush되지 않았으면 `App::run` 뒤의 치명적 오류가 응답을 평문 500으로 바꾸며, hook은 그것을 `ended` true로 받는다; buffering이 꺼져 있거나 header를 보낸 flush 뒤이면, hook은 시작된 응답을 `ended` false로 받는다. <a id="HY-99.8"></a> Node는 `node:http` 응답의 `close` 이벤트와 요청 응답 처리의 끝 뒤에 hook을 호출하며, `ended`는 `writableFinished`와 같다; `App.listener(sessions, options)`가 돌려주고 `App.server`가 설치하는 listener는 요청의 write hook과 disconnect hook이 실행된 뒤에 확정되는 promise를 돌려준다. <a id="HY-99.9"></a> WSGI: `ended`는 서버가 body iterable 전체를 소비하면 true이고, 끝나기 전에 `close`를 부르면(첫 항목 전이라도) false다; `start_response` 전의 오류는 escape된 오류이며, `start_response`가 던지는 것도 그렇다. <a id="HY-99.10"></a> ASGI: `ended`는 두 send가 모두 반환하면 true이고, send가 예외를 던지거나 task가 취소되면 false다; 오류나 취소는 전파된다. <a id="HY-99.11"></a> 응답이 시작되기 전에 요청이 끝나면(연결이 닫혀서(HY-67), task가 취소되어(HY-100), 또는 PHP `exit()`가 출력 없이 끝내서), hook은 null 응답을 받으며, `ended`는 false이고, 오류가 escape되지 않았다면 `failure`는 null이다. <a id="HY-99.12"></a> hook은 세 경우에 호출하지 않는다: public 디렉터리의 파일, 전송이 보고할 요청을 주지 않은 요청(HY-60), 요청이 끝나기 전에 프로세스가 끝난 경우(kill이나 worker를 끝내는 timeout)다; 그때는 서버의 어떤 코드도 실행되지 않기 때문이다. <a id="HY-99.13"></a> hook이 던지는 오류는 HY-43이 처리하지 않으며, 전송에 전달된다.

- **HY-100** <a id="HY-100.1"></a> 모든 서버는 그 runtime의 표준 host 인터페이스로 제공되며, host는 각 요청에 서버가 하듯이 응답한다(HY-97, HY-99): PHP는 `App::run`을 SAPI(built-in server 또는 php-fpm) 아래에서 호출하는 front controller로, Python은 `create_wsgi`의 WSGI callable, `create_asgi`의 ASGI callable, `create_server`의 `http.server` 서버로, Node는 `App.server`가 설치하는 `App.listener`의 `node:http` request listener로 제공한다. <a id="HY-100.2"></a> host는 요청 body를 애플리케이션의 body 한도까지만 읽고(HY-59), 자기 session 저장소를 `App.handle`에 넘기며(`App.handle`은 HY-120이 정하는 대로 session을 연다), 새 session의 cookie를 맨 앞에 두고(HY-45), 요청 hook `around`(HY-97)를 실행하고, 쓰기를 write hook(HY-99)에, 닫힌 연결을 disconnect hook(HY-67)에 보고하며, target을 줄 수 없는 요청에는 HY-60의 평문 500으로 응답한다.

  - <a id="HY-100.3"></a> Python WSGI: Python 서버 `polyspec-hyper-server`의 `polyspec.hyper.wsgi.create_wsgi(app, sessions, files=None, around=None, written=None)`는 `create_server`의 인자(HY-97, HY-99)를 받고, WSGI 서버가 실행하는 WSGI 애플리케이션 callable(PEP 3333)을 돌려준다. <a id="HY-100.4"></a> callable은 `create_server`처럼 모든 요청에 응답한다: public 디렉터리의 파일을 `around` 전에 제공하고, 요청 body를 애플리케이션의 body 한도까지만 읽고(HY-59), 자기 session 저장소를 `App.handle`에 넘기며(`App.handle`은 HY-120이 정하는 대로 session을 연다), 새 session의 cookie를 맨 앞에 두고(HY-45), 요청 hook `around`(HY-97)를 실행한다. <a id="HY-100.5"></a> 완전한 body의 `Content-Length` header는 callable이 직접 붙인다. <a id="HY-100.6"></a> write hook `written`(HY-99)은 WSGI 서버가 body iterable 전체를 소비하면 쓰기가 끝났다고 보고하고, 서버가 iterable을 끝나기 전에 닫으면(PEP 3333이 premature termination으로 정의하는 경우) 실패했다고 보고한다; 쓰기가 실패하면 callable은 `around`에 넘긴 요청과 마지막 `answer` 호출의 reply로 disconnect hook(HY-67)을 호출한다. <a id="HY-100.7"></a> public 디렉터리의 파일에는 hook을 호출하지 않는다. <a id="HY-100.8"></a> `around`가 `answer` 밖에서 던지는 오류, 또는 `around`가 돌려주는 `Response`가 아닌 값은 escape된 오류다(HY-60): callable은 `start_response`를 호출하기 전에 평문 500으로 응답하고, write hook이 그 500을 받는다. <a id="HY-100.9"></a> `start_response`가 던지는 오류와, callable이 인코딩할 수 없는 status, header, body도 escape된 오류이며, callable은 그 오류의 예외 정보와 함께 평문 500을 `start_response`에 넘기고(PEP 3333), write hook은 그것을 `failure`와 함께 받는다. <a id="HY-100.10"></a> 요청 target은 WSGI 서버가 받은 그것이다. <a id="HY-100.11"></a> PEP 3333에는 raw path가 없으므로 callable은 target을 `RAW_URI`(gunicorn)에서 읽고, 없으면 `REQUEST_URI`(uWSGI, mod_wsgi)에서 읽는다. <a id="HY-100.12"></a> 요청 path는 target에서 첫 `?`까지이고, raw query는 첫 `?` 뒤의 텍스트다(HY-42, HY-56); `create_server`가 target을 나누는 방식과 같이 나눈다. <a id="HY-100.13"></a> callable은 서버가 percent-decode한 `PATH_INFO`를 결코 읽지 않으며, 다시 encode하지도 않는다. <a id="HY-100.14"></a> environ에 두 키가 모두 없으면 요청에는 보고할 target이 없다: callable은 `RAW_URI`와 `REQUEST_URI`를 적은 오류를 로그에 남기고, `start_response`를 호출하기 전에 HY-60의 평문 500으로 응답한다.
  - <a id="HY-100.15"></a> Python ASGI: Python 서버 `polyspec-hyper-server`의 `polyspec.hyper.asgi.create_asgi(app, sessions, files=None, around=None, written=None)`는 `create_server`의 인자(HY-97, HY-99)를 받고, ASGI 서버가 실행하는 ASGI 3 애플리케이션 callable을 돌려준다. <a id="HY-100.16"></a> callable은 scope type `http`의 모든 요청에 `create_server`와 같이 응답한다: public 파일을 `around` 전에 제공하고, 요청 body를 애플리케이션의 body 한도까지만 읽고(HY-59), 새 session의 cookie를 먼저 붙이며(HY-45), 요청 hook `around`(HY-97)를 실행한다. <a id="HY-100.17"></a> callable은 요청의 파이프라인을 worker thread에서 실행하므로, 서버의 event loop는 한 요청이 응답하는 동안 다른 요청에 응답한다. <a id="HY-100.18"></a> callable은 `Response`의 status와 header를 담은 `http.response.start` 하나와 완전한 body를 담은 `http.response.body` 하나를 전송한다: write hook `written`(HY-99)은 두 send가 모두 반환하면 쓰기가 끝났다고 보고하고, send가 예외를 던지면 실패했다고 보고하며, ASGI 서버는 클라이언트가 닫은 연결에 대해 예외를 던진다; 쓰기가 실패하면 callable은 `written`을 호출한 뒤, `around`에 넘긴 요청과 마지막 `answer` 호출의 reply로 disconnect hook(HY-67)을 호출하고, 오류를 서버로 전파한다. <a id="HY-100.19"></a> task가 취소되면 `written`에 `ended` false로 보고하고 취소를 전파하되, disconnect hook은 호출하지 않는다; 취소는 클라이언트가 연결을 닫았다는 것을 말해 주지 않기 때문이다. <a id="HY-100.20"></a> `create_server`처럼(HY-67) callable은 send가 실패할 때만 닫힌 연결을 감지한다; `http.disconnect` 메시지는 확인하지 않는다. <a id="HY-100.21"></a> public 디렉터리의 파일에는 hook을 호출하지 않는다. <a id="HY-100.22"></a> 라이브러리는 어떤 서버의 이름도 대지 않으며, 배포는 callable을 자기가 고른 서버로 실행한다. <a id="HY-100.23"></a> 요청 path는 `scope['raw_path']`를 latin-1로 decode한 것으로, query 없는 target path의 raw 바이트이며 ASGI 명세가 정의한다; HY-42가 target을 나누는 방식으로 나눈다. <a id="HY-100.24"></a> raw query는 `scope['query_string']`을 latin-1로 decode한 것이다(HY-56). <a id="HY-100.25"></a> callable은 서버가 percent-decode한 `scope['path']`로 path를 만들지 않는다. <a id="HY-100.26"></a> 명세가 선택 사항으로 두는 `raw_path`를 ASGI 서버가 생략하면 그 요청에는 보고할 target이 없다: callable은 `raw_path`를 적은 오류를 로그에 남기고, 다른 것을 전송하기 전에 HY-60의 평문 500을 전송한다. <a id="HY-100.27"></a> 그 500의 send가 실패하면 callable은 실패한 쓰기와 함께 `written`을 부르고, 실패한 send에 대해 HY-67이 하듯 오류를 서버로 전파되게 둔다.
  - <a id="HY-100.28"></a> Node: Node 서버의 `App.listener(sessions, options)`는 `App.server`가 설치하는 `node:http` 요청 listener를 돌려준다. <a id="HY-100.29"></a> listener는 요청의 쓰기 hook과 disconnect hook이 실행된 뒤에 확정되는 promise를 돌려준다(HY-99).
  - <a id="HY-100.30"></a> PHP: `App::run`은 front controller의 entry다; `ignore_user_abort`를 끄고, write hook과 disconnect hook(HY-67, HY-99)을 부르는 shutdown 함수를 등록하며, 잡히지 않은 예외나 치명적 오류의 평문 500을 쓴다(HY-60).

## 오류

- **HY-27** <a id="HY-27.1"></a> route가 없는 path나 리소스가 없다고 알리는 loader는 상태 404로 응답한다. <a id="HY-27.2"></a> `GET`도 선언된 `POST`도 아닌 method는 상태 405로 응답하며, representation은 대신 HY-121의 method를 검사한다. <a id="HY-27.3"></a> loader나 action은 없는 자원을 not-found 정지로 보고하며 그 메시지는 `not found`다. HY-51의 forbidden 정지의 메시지는 `forbidden`이고 HY-58의 bad-request 정지의 메시지는 `bad request`다.

- **HY-50** <a id="HY-50.1"></a> loader나 action은 리다이렉트로 요청을 멈출 수 있다: HY-25의 결과의 리다이렉트를 던지며, 그 리다이렉트는 애플리케이션 경로(HY-46)를 지정하고 flash 값과 바뀐 topic을 담을 수 있다. <a id="HY-50.2"></a> 서버는 상태 303과 base path를 담은 `Location`으로 응답하고, HY-25가 하듯 flash 값과 바뀐 topic을 저장하며, 아무것도 렌더하지 않는다. <a id="HY-50.3"></a> 리다이렉트가 아닌 결과로 리다이렉트 정지를 만들면 HY-46.2의 클래스로 오류 `a redirect stop needs a redirect result (HY-50)`를 내며 실패한다. 리다이렉트 정지의 메시지는 `redirect to` 뒤에 공백과 그 위치가 오는 문자열이다.

- **HY-52** <a id="HY-52.1"></a> 요청의 모든 loader와 action은 그 요청의 응답(reply)을 받을 수 있다. <a id="HY-52.2"></a> reply는 `hy-`로 시작하지 않는 `[a-z][a-z0-9_-]*` 이름과 `A-Z a-z 0-9 . _ ~ -` 문자의 값, 선택적 `Max-Age`를 가진 cookie를 추가하거나, `Max-Age=0`으로 cookie를 지운다. <a id="HY-52.3"></a> 그런 cookie는 모두 `Path=/`, `HttpOnly`, `SameSite=Lax`를 가지며, HY-45의 조건에서 `Secure`다. <a id="HY-52.4"></a> 다른 이름이나 값은 HY-43으로 실패한다. <a id="HY-52.5"></a> page 응답은 `Cache-Control: no-store`를 가지며, reply는 상태 200인 page 응답의 `Cache-Control`을 설정할 수 있고, 그 값은 `no-store`를 대신한다. <a id="HY-52.6"></a> page는 방문자의 session token(HY-10, HY-24)을 담으므로, `private`이나 `no-store` 지시어가 없거나 `public`이나 `s-maxage`가 있는 값은 HY-43으로 실패한다; 공유 cache가 한 방문자의 page를 다른 사람에게 주면 안 되기 때문이다. <a id="HY-52.7"></a> 서버 session은 응답에 자기 cookie만 더하며, caching header는 더하지 않는다. <a id="HY-52.8"></a> body가 없는 응답은 HY-53의 304를 포함해 `Content-Type`을 가지지 않는다. <a id="HY-52.9"></a> 요청의 응답은 그 reply의 cookie를 담으며, 그것이 page, 리다이렉트, HY-27, HY-50, HY-51의 실패 가운데 무엇이든 마찬가지다. <a id="HY-52.10"></a> `Max-Age`는 음수가 아닌 data model의 정수다: 소수부가 없는 ±(2^53 − 1) 안의 수이므로 `60.0`은 정수 60이고 bool은 정수가 아니다. <a id="HY-52.11"></a> 문자열이 아닌 cookie 이름, cookie 값이나 `Cache-Control` 값, 그리고 null도 그런 정수도 아닌 `Max-Age`는 `TypeError`와 메시지 `a cookie name is not a string (HY-52)`, `a cookie value is not a string (HY-52)`, `a Cache-Control is not a string (HY-52)` 또는 `a Max-Age is not an integer within ±(2^53 − 1) (HY-52)`로 실패하며, cookie의 타입은 값보다 먼저 parameter 순서로 검사한다. <a id="HY-52.12"></a> 이 타입의 cookie는 그 밖에는 HY-46.2의 class와 메시지 `cookie name <name> is not allowed (HY-52)`, `cookie value of <name> has a character that is not allowed (HY-52)` 또는 `cookie <name> has a negative Max-Age (HY-52)`로 이 순서에 따라 실패하고, `Cache-Control` 문자열은 메시지 `Cache-Control has a character that is not allowed (HY-52)` 또는 `Cache-Control <value> lets a shared cache store the page; it needs private or no-store and neither public nor s-maxage (HY-52)`로 실패하며, `<name>`과 `<value>`는 주어진 문자열이다.

- **HY-60** <a id="HY-60.1"></a> 애플리케이션은 응답 hook을 선언할 수 있다. <a id="HY-60.2"></a> 서버는 애플리케이션의 모든 응답에 대해 한 번 그것을 호출하며, 요청, 응답, 경과 밀리초와 함께 호출하고, hyper가 직접 응답하는 응답도 포함한다: 400(HY-42, HY-58), 403(HY-24, HY-51), 404와 405(HY-27), 406과 정적 shell(HY-62), HY-116의 400과 406, HY-127의 400, HY-121의 400, 405, 415, 413과 415(HY-59), 500(HY-43, HY-66). <a id="HY-60.3"></a> 요청은 받은 그대로의 요청이며 base path를 가진다. <a id="HY-60.4"></a> 응답은 애플리케이션의 응답이며 `Content-Security-Policy`(HY-45)를 가진다; 그 뒤에 session이 더하는 session cookie는 그 일부가 아니다. <a id="HY-60.5"></a> 경과 시간은 요청의 시작부터 단조 시계로 측정한다: PHP의 `App::run`과 `handle`은 시작 시각을 호출자로부터 `hrtime(true)` 값으로 받거나(예: front controller의 첫 문장이 얻는 값), 자기 호출부터 측정한다; Node 서버는 `node:http`가 요청을 준 시각부터 `performance.now()`로 측정한다. <a id="HY-60.6"></a> 어느 서버도 `REQUEST_TIME_FLOAT`나 `microtime(true)` 같은 벽시계 시각을 빼지 않는데, 시스템 시각의 조정이 벽시계를 뒤로 옮겨 음수 경과 시간을 주기 때문이다. <a id="HY-60.7"></a> Node 서버는 `node:http`가 파싱할 수 없는 요청에 대한 400과 431 응답도 보고하며, 그 요청은 요청 줄의 method와 target을 가지고, 패킷에 요청 줄이 없으면 요청은 없다. <a id="HY-60.8"></a> hook은 또한 요청의 reply(HY-52)를 받으므로, loader와 action이 정한 값을 읽는다: 요청이 stop(HY-50, HY-51, HY-58), HY-27의 실패, HY-43의 오류로 끝났어도 그들이 받은 reply를, 그리고 서버가 라우팅 전에(HY-42, HY-59, route가 없는 path, `/_hyper/keep`, `node:http`가 애플리케이션에 줄 수 없는 응답) 응답했거나 loader나 action 없이(HY-62의 405와 406 응답과 shell, HY-116의 406, representation의 모든 응답, HY-121과 HY-122) 응답했다면 새 빈 reply를 받는다. <a id="HY-60.9"></a> loader나 action은 그런 값을 reply의 note(이름과 임의의 값)로 기록하며, 같은 이름의 나중 note는 값을 바꾸고 자리를 유지한다. <a id="HY-60.10"></a> 서버는 note를 읽지 않으며, note는 응답의 일부가 아니다. <a id="HY-60.11"></a> hook은 HY-43 또는 HY-66의 500에 대해 그 실패도 받으므로, 애플리케이션은 원인을 자기 줄로 쓴다: 실패는 HY-43의 오류 메시지(PHP `Throwable`이나 Node `Error`의 메시지, 또는 다른 던져진 값의 텍스트) 또는 HY-66의 `the response to <method> <path> has <size> bytes, more than the response limit of <limit> bytes`이다; 다른 모든 응답에 대해서는 null을 받는다. <a id="HY-60.12"></a> Node 서버의 public 디렉터리 파일은 애플리케이션의 응답이 아니다. <a id="HY-60.13"></a> hook이 던지는 오류는 HY-43이 처리하지 않으며, `handle`의 호출자에게 전달된다.

  - <a id="HY-60.14"></a> 요청의 응답을 빠져나가는 오류는, HY-43이 처리하지 않는 것이므로, body 읽기 실패, public 디렉터리 파일의 stat 실패, session 열기나 닫기 실패, 응답 쓰기 실패, 응답 hook이 던지는 오류, 또는 `around`가 `answer` 밖에서 던지는 오류(HY-97)다. <a id="HY-60.15"></a> 서버는 그것을 HY-43의 메시지와 함께 로그에 남기고, hyper가 직접 쓰는 평문 500으로 응답하며, 이 500은 모든 adapter에서 같다: 상태 500, 텍스트 `Internal Server Error`, `Cache-Control: no-store`(HY-65), `Content-Security-Policy: frame-ancestors <policy>`(HY-45). <a id="HY-60.16"></a> 어떤 서버도 그 500을 응답 hook에 보고하지 않는다. <a id="HY-60.17"></a> 쓰기 hook(HY-99)은 그것을 한 번, 서버가 받은 그대로의 요청과 함께 받는다. <a id="HY-60.18"></a> 받은 그대로의 요청은 요청의 target, header, cookie를 가지며, 읽지 않은 body는 비어 있고 그 크기는 클라이언트가 선언한 Content-Length다. <a id="HY-60.19"></a> 전송이 target을 주지 않는 요청(`RAW_URI`와 `REQUEST_URI`가 없는 WSGI environ, 또는 `raw_path`가 없는 ASGI scope)은 보고할 요청이 없으므로 어떤 hook도 그 500을 받지 않는다. <a id="HY-60.20"></a> 500은 응답이 시작되지 않았을 때만 쓰인다. <a id="HY-60.21"></a> 응답이 시작되었거나 500의 쓰기가 실패하면 서버는 연결을 닫으며, 실패한 쓰기는 쓰기 hook에 한 번 보고되므로 한 요청에 어떤 hook도 두 번 호출되지 않는다. <a id="HY-60.22"></a> WSGI와 ASGI callable(HY-100)은 `start_response`나 첫 send 전에 같은 500을 쓴다. <a id="HY-60.23"></a> `App::run`은 header가 보내지지 않았을 때, 잡히지 않은 예외에 대해 `set_exception_handler`로 같은 500을 쓰고, 요청의 치명적 오류에 대해서도 같은 500을 쓴다; 치명적 오류는 shutdown 함수가 `error_get_last()`에서 E_ERROR, E_CORE_ERROR, E_COMPILE_ERROR, E_USER_ERROR로 읽는 오류다(메모리나 시간 한도는 E_ERROR다).
  - <a id="HY-60.24"></a> escape된 오류의 평문 500은 hyper가 요청을 받기 전에 호출자가 설정한 응답 header를 유지하며, 다른 header는 유지하지 않는다. <a id="HY-60.25"></a> PHP는 `App::run`의 호출 때 `headers_list()`의 header를 유지하고, `sendReplacing`이 다른 모든 header를 지운 뒤 500의 header 앞에 그것들을 다시 더한다. <a id="HY-60.26"></a> Node는 `node:http` 응답에 `writeHead`로 500을 쓰며, 이는 hyper의 listener가 실행되기 전에 호출자가 `setHeader`로 설정한 header를 유지한다. <a id="HY-60.27"></a> WSGI와 ASGI callable(HY-100)은 500을 다른 응답과 같이 호출자의 `start_response`나 `send`로 넘긴다.

  <a id="HY-60.28"></a> 문자열이 아닌 note 이름은 `TypeError`와 메시지 `a note name is not a string (HY-60)`로 실패한다. <a id="HY-60.29"></a> `notes()`는 note를 이름과 값의 쌍 목록으로 세 server에서 각 이름의 첫 note 순서대로 반환하며, 이름은 십진수일 때도 문자열로 남는다.

- **HY-65** <a id="HY-65.1"></a> 상태 400 이상의 모든 응답은 `Cache-Control: no-store`를 가지며, 따라서 어떤 cache도 실패를 저장하지 않는다: HY-24, HY-27, HY-40, HY-42, HY-43, HY-51, HY-58, HY-59, HY-62, HY-66, HY-116, HY-127, HY-121의 평문 텍스트 응답, 그런 상태를 가진 representation handler의 응답(HY-122), escape된 오류의 평문 500(HY-60), `node:http`가 파싱할 수 없는 요청에 대한 Node 서버의 400과 431 응답(HY-60), 상태 409 또는 422의 page(HY-58), 상태 403의 page(HY-69)다. <a id="HY-65.2"></a> reply는 이것을 바꾸지 않는다(HY-52). <a id="HY-65.3"></a> 이 header가 없으면 cache는 404나 405 응답을 자기 휴리스틱 신선도로 저장할 수 있다(RFC 9111).

- **HY-66** <a id="HY-66.1"></a> 애플리케이션은 응답 한도를 선언하는데, 이는 응답 body의 최대 바이트 수(기본 8 MiB)이며, 양의 정수가 아닌 한도는 애플리케이션을 열 때 실패한다. <a id="HY-66.2"></a> 한도는 서버가 한 응답을 보내기 위해 보유하는 body를 제한하며, 느린 클라이언트는 그 body를 서버 프로세스의 메모리와 응답을 버퍼링하는 web server의 메모리에 남아 있게 한다. <a id="HY-66.3"></a> body가 한도보다 큰 응답은 보내지지 않는다: 서버는 로그에 `hyper: the response to <method> <path> has <size> bytes, more than the response limit of <limit> bytes`를 쓰고, HY-43이 하듯 상태 500과 텍스트 `Internal Server Error`로 응답하며, 그 500을 요청의 reply와 함께 응답 hook(HY-60)에 보고한다. <a id="HY-66.4"></a> body의 크기는 바이트 단위 길이다. <a id="HY-66.5"></a> 서버는 body를 완전히 렌더한 뒤 크기를 비교하는데, template 프로그램이 문서를 한 문자열로 렌더하기 때문이다.

- **HY-67** <a id="HY-67.1"></a> 애플리케이션은 disconnect hook을 선언할 수 있다. <a id="HY-67.2"></a> 서버는 클라이언트가 완전한 응답을 받기 전에 연결을 닫은 요청에 대해, 받은 그대로의 요청, 경과 밀리초(HY-60), 요청의 reply와 함께 그것을 한 번 호출한다.

  - <a id="HY-67.3"></a> Node 서버는 응답이 쓰이기 전에 연결이 닫혔다고 `node:http`가 보고할 때 닫힘을 감지한다. <a id="HY-67.4"></a> 그러면 Node 서버는 실행 중인 것 다음으로 그 요청의 loader, action, 렌더를 더 실행하지 않고, 응답을 쓰지 않으며, 응답 hook을 호출하지 않고, disconnect hook을 호출한다.
  - <a id="HY-67.5"></a> PHP는 닫힌 연결을 그곳에 대한 쓰기가 실패할 때만 보고하며, 닫힌 연결에 대한 작은 응답의 쓰기는 성공할 수 있다. <a id="HY-67.6"></a> `App::run`은 `ignore_user_abort`를 끄므로, PHP는 응답의 첫 쓰기 실패에서 스크립트를 끝내고, `connection_aborted()`가 1이면 shutdown 함수가 disconnect hook을 호출한다. <a id="HY-67.7"></a> 그러므로 PHP 서버는 닫힘을 감지하기 전에 완전한 응답을 렌더하고 응답 hook(HY-60)을 호출하며, 응답의 모든 쓰기가 성공하면 닫힘을 감지하지 않는다.
  - <a id="HY-67.8"></a> `polyspec-hyper-server`의 Python 서버(`polyspec.hyper.server`의 `create_server`)는 PHP처럼 응답 쓰기가 실패할 때만 닫힌 연결을 감지한다: `http.server`는 클라이언트가 닫은 연결에 쓰면 `BrokenPipeError`, `ConnectionResetError`, `ConnectionAbortedError`를 던진다. <a id="HY-67.9"></a> 서버는 응답을 완전히 렌더하고 응답 hook(HY-60)을 먼저 호출한 뒤 응답을 쓰며; 쓰기가 이들 오류 가운데 하나로 실패하면 응답을 더 쓰지 않고, 받은 그대로의 요청, 경과 밀리초, 요청의 reply와 함께 disconnect hook을 한 번 호출한다. <a id="HY-67.10"></a> 서버는 경과 시간을 요청 handler가 요청을 시작한 때부터 `time.perf_counter_ns()`, 즉 단조 시계로 세며, 응답 hook에서와 같다. <a id="HY-67.11"></a> 응답의 모든 쓰기가 성공하면 닫힘을 감지하지 않는다. <a id="HY-67.12"></a> `App.respond`는 `App.handle`처럼 요청에 응답하고 요청의 reply와 함께 응답을 돌려주므로, 서버는 disconnect hook이 받을 reply를 가진다; `App.handle`은 응답만 돌려준다.

- **HYC-9** <a id="HYC-9.1"></a> 브라우저 코드의 오류는 htmx 응답 hook에서 던져진다. <a id="HYC-9.2"></a> htmx는 그것을 `htmx:error` 이벤트로 보고하며 교체하지 않는다.

## 구현 동등성

PHP, Python, TypeScript는 같은 선언된 프로토콜 단위를 만족해야 하며, 여기에는 매니페스트, 요청, 파일 한도 규칙이 포함된다(HY-1, HY-27, HY-114). CI는 선언 검증과 언어 간 동등성 검사를 `ci.yml`의 `gates` 항목에서 실행하며, 언어별, 렌더, 브라우저 job과는 독립이다. 각 parity 대상은 정확히 한 번 실행되며; 실패한 parity 대상은 `gates` 항목을, 따라서 release가 실행에 요구하는 `ci-passed`를 실패시킨다.

각 CI 그룹은 고정된 도구, 잠긴 의존성, 빌드 입력을 자기가 소유한다. 언어 job은 자기가 실행하는 환경만 설치한다. protocol parity와 브라우저 integration 그룹은 비교하는 모든 구현을 독립적으로 준비하며, 다른 언어 job의 설치나 빌드 산출물을 결코 쓰지 않는다. 도구 선택은 공유된 `make install-tools TOOLS="..."` 인터페이스를 쓰며; 패키지 설치는 npm, Composer, uv가 맡는다. 설치는 잠긴 입력을 내려받을 수 있으나, 빌드와 검사는 오프라인으로 남는다. 선택된 installer는 고정된 Kit release가 제공한다. npm은 자기 별도 bootstrap selector로 준비되며, PHP symbol extractor는 그것을 실행하는 그룹에서 `make kit-install-symbols EXTRACTORS="php"`로 명시적으로 설치된다.

## 인터페이스 용어

string은 텍스트이다. number는 HY-54.8이 JSON 수를 읽는 대로 정수나 float이다. boolean은 `true` 또는 `false`이다. null은 값 `null`이다. bigint는 임의 크기의 정수이다. bytes는 바이트 열이다. value는 HY-54의 데이터 모델의 임의의 값이다. none은 결과가 없음이다.
