# Region protocol

[한국어](protocol.ko.md).

This document defines the application manifest, routing, rendering, the requests and responses between a hyper server and the hyper browser code, and the two rendering modes. The server can render the first document as HTML (server-side rendering, SSR), or a static shell can render it in the browser (client-side rendering, CSR). Template syntax and rendering rules are defined by the template language; this document does not change them.

## Application manifest

- **HY-1** An application declares its structure in one JSON file, the manifest. Server and browser read the same manifest.

```json
{
  "layout": "layout.tpl",
  "title": "title.tpl",
  "regions": [
    { "name": "left", "template": "left.tpl", "uses": ["posts", "path"] },
    { "name": "content", "page": true }
  ],
  "routes": [
    { "name": "board.list", "path": "/board", "title": "Board", "template": "board/list.tpl", "regions": [{ "name": "rows", "template": "board/rows.tpl" }] },
    { "name": "board.create", "path": "/board/create", "title": "Write", "template": "board/create.tpl", "post": true },
    { "name": "board.show", "path": "/board/{id}", "title": "Post", "template": "board/show.tpl" }
  ]
}
```

- **HY-2** `regions` and `routes` are ordered lists. Region names and route names are strings and are unique. A region name matches `[A-Za-z][A-Za-z0-9_-]*` and is not `layout`, `title` or `data`. Exactly one region has `"page": true` and no `template`; every other region has a `template` and a list of used topics. A route with `"post": true` accepts a `POST` action. A server checks its manifest against these rules when it starts, and the asset build checks the manifest before it writes the client bundle; the browser does not check the manifest of its bundle again.
- **HY-3** The layout renders the title definition inside `<title>` with `{# title}`, the data definition with `{# data}` (HY-31), and each region with `{# name}` inside an element whose `id` is the region name, for example `<main id="content">{# content}</main>`. A region placement has no block arguments. The browser finds a region element by its `id`; no other marker exists.

## Routing

- **HY-4** A route path starts with `/`. The segments after it are separated by `/`. A segment is either a literal of the characters `A-Z a-z 0-9 . _ ~ -` or a parameter `{name}` where `name` matches `[A-Za-z_][A-Za-z0-9_]*`. The path `/` has no segments.
- **HY-5** A request path matches a route when it starts with `/`, has the same number of segments, every literal segment is equal to the request segment byte for byte, and every parameter segment is non-empty. The query string is not part of the path.
- **HY-6** A parameter value is the request segment with every `%XX` sequence (two hexadecimal digits) decoded to its byte. A segment with a `%` that is not followed by two hexadecimal digits, or whose decoded bytes are not valid UTF-8, does not match.
- **HY-7** Routes are tried in manifest order, and the first route that matches is the result. A path that matches no route has no result.
- **HY-8** An application may run under a base path such as `/api`. A request path is routed after removing the base path; a request path that does not start with the base path followed by `/` or the end of the path has no result. `Location` headers include the base path.
- **HY-9** `contracts/routes.json` holds routes and request paths with their expected results. The PHP router and the JavaScript router both pass every case.
- **HY-49** The last segment of a route path may be a rest parameter `{name*}`, with `name` as in HY-4 and different from the other parameters of the path. It stands at zero or more remaining request segments and matches when every one of them is empty or decodes by HY-6. Its value is the rest of the request path without decoding: `/` followed by the remaining segments joined with `/`, or `/` when none remains. `contracts/rest.json` holds routes and request paths with their expected results; the PHP router and the JavaScript router both pass every case.

## Data and topics

- **HY-10** Shared data is one map that the layout, the title and every region receive. It starts with `title`, the route title, and `csrf`, the masked session token of HY-24 for this response, followed by the values that the application adds.
- **HY-11** Every non-page region declares the topics it uses. A topic names data that can change, such as `posts`. The topic `path` is built in: it changes when the request path differs from the path of the `HX-Current-URL` request header after removing the base path.

## Rendering

- **HY-12** A document is the layout rendered with root data equal to the shared data and with `html` definitions: `title` (the title rendered alone), `data` (HY-31) and one per manifest region, the region rendered alone. The page region template is the route template.
- **HY-13** A region rendered alone uses the region template and the root data `merge(shared, region data)`, where a region data value replaces a shared value with the same name. The page region receives every route region of its route, rendered alone, as an `html` definition. The title rendered alone uses the title template and the shared data. The server and the browser compose documents and region parts in this same way, so they produce the same bytes. A document or a region response binds each of its roots once with the bound map of the template engine (VAL-22): the shared data, the data of every region and, in a document that embeds its data, the embedded data (HY-31). Every render of the response uses those bound maps and `merge`, so the number of binds does not grow with the number of renders; a shared value is bound in the shared data and once more in the embedded data of a document that embeds its data, because the embedded data carries the shared data.
- **HY-14** Server and browser render with the same environment. The server sends the time zone in every JSON response.
- **HY-48** A server renders documents and regions as HY-12 and HY-13 define, with the template engine of its runtime, from the outputs of the build (HR-96): the manifest, the templates of the application and the read paths `reads.json` (HY-73). It opens the application only when every output that it needs exists: `open` fails with the absolute path of the first missing output, so that a missing build fails when the application opens and names the missing file. The build first checks the templates with the rules of HC-6, HY-3, HY-30 and HY-75, the same rules as `make templates-check`, and a violation fails the build with every problem before it removes or writes any output, so a server program never serves templates that break them.
  - PHP: PHP renders with a program that the build compiles from the application templates: with the native template extension `polyspec_template` when PHP has loaded it, and otherwise with the generated PHP program of the same templates. Both programs pass the same tests and `make parity`. The build compiles the generated program into a PHP namespace that the application chooses and writes it into the directory `php` of the program directory as PSR-4 files, one class per file named after its class, so it declares no global name and the programs of several applications load in one PHP process. The application maps that namespace to that directory in `autoload.psr-4` of its `composer.json`, and the server takes the class `GeneratedProgram` of the namespace that `program.json` names through the autoload of Composer and requires no file of the program itself. `App::open` fails when the program directory has no directory `php`, no `program.json`, no `reads.json` (HY-73) or no directory `templates`, with the absolute path of the first missing one. Without the native extension it also fails when the autoload does not load that class, naming the class and the directory `php` that `autoload.psr-4` must map to its namespace.
  - Python: the program directory holds `reads.json` and the directory `templates`; `App.open` fails with a `ValueError` that names the first missing one.
  - Node: `App.open` reads the manifest, the template index and the template files by absolute paths; a missing file fails with the error that names its path.

## Requests

- **HY-15** A request with `Accept: application/json` and `HX-Request: true`, which htmx sends with every request, is a region request. A request with `Accept: application/json` and no `HX-Request` is a document request. Any other request is an HTML request and receives an HTML document. A region request always updates the page region (HY-18).
- **HY-56** The raw query of a request is the request target after its first `?` up to its first `#`, or empty text without a `?`. Its values are read without nesting: the raw query is split at every `&` and an empty part is skipped; the name of a part is the text before its first `=` and the value is the rest, or empty text when the part has no `=`; in both, `+` is a space, `%XX` with two hexadecimal digits is its byte and any other `%` stays. A name with brackets, such as `roles[]` or `a[b]`, is the name as written, and an empty name is a name. The query values are an ordered map from each name, in the order of its first occurrence, to the list of its values in request order; a name or value that is not valid UTF-8 fails with HY-42. `Request` provides the raw query and the query values, and `queryInt` reads the last value of a name. `contracts/fields.json` holds texts with their values, and both servers pass every case.
- **HY-57** The form values of a request are read from its raw body without nesting, as an ordered map like the query values of HY-56. An `application/x-www-form-urlencoded` body is read as the raw query is. A `multipart/form-data` body gives one value for each part whose `Content-Disposition` is `form-data` with a `name` parameter and no `filename` parameter: the name is that parameter and the value is the content of the part as it is; a part with a `filename` is a file and not a form value. A body of another type has no form values. A name or value that is not valid UTF-8 fails with HY-42. The PHP server reads the body from `php://input`, not from `$_POST`, which nests bracketed names; PHP gives it the body of a `multipart/form-data` request only when `enable_post_data_reading` is off. `Request` provides the form values, and `formString` reads the last value of a name. `contracts/fields.json` holds urlencoded and multipart cases, and both servers pass every case.

## JSON response

- **HY-17** A JSON response has this shape. Keys keep their order.

```json
{
  "env": { "timezone": "+09:00" },
  "route": "board.show",
  "params": { "id": "7" },
  "shared": { "title": "Post", "csrf": "token" },
  "regions": {
    "content": { "post": { "id": 7 } },
    "reader": { "large": false },
    "left": { "count": 3 }
  },
  "kept": {
    "reader": { "large": true }
  }
}
```

`regions` holds the loader data. `kept` holds, by region and path, the `server` and `cookie` kept values that the server read for the regions in `regions` and that conform to the region data (HY-38). A region without such values has no entry.

- **HY-18** For a document request, `regions` contains every region in manifest order, without absent route regions (HY-75). For a region request, it contains the page region first, then every other region that uses a changed topic, in manifest order.
- **HY-19** The changed topics of a request are the topics recorded by the previous action (HY-25) and `path` (HY-11).

## Browser

- **HYC-1** The browser code routes the response URL path (after removing the base path) with the manifest routes. The route name must equal `route` in the response; otherwise rendering fails. The page region template is the template of that route.
- **HYC-2** The htmx extension requests JSON (`Accept: application/json`) only when the `id` of the request target element is the name of the page region. It converts a JSON region response into this HTML and gives it to htmx in place of the response text: `<title>` with the title rendered alone, then the page region rendered alone, then `<hx-partial hx-target="#<name>" hx-swap="innerMorph">` with each other region rendered alone. Before htmx swaps, the browser applies the stylesheet links of the layout of the response (HYC-15). htmx then performs the swap, the title change and the history update. A response whose content type is not `application/json` passes unchanged.
- **HYC-8** In client-side rendering, a static shell declares the base path of the server with `<meta name="hyper-api" content="/api">`. The browser code requests the document JSON for the current path while it loads the templates of the route (HYC-12), routes the response URL after redirects (HYC-1), renders the document (HY-12), applies the stylesheet links of its head (HYC-15), replaces the attributes of the `html` element (HYC-6), the title and the body with the rendered ones, and lets htmx process the new body. A current path that matches no route renders the body text `Not Found`.
- **HYC-3** In client-side rendering, the extension prefixes the same-origin request path of every region request with the base path, removes the base path from history paths, and replaces htmx history restoration with HYC-8 for the restored path. A later restoration cancels an earlier one that is still loading, and only the latest one is rendered.
- **HYC-15** The stylesheet links of a head are its `link` elements that have an `href` attribute and whose `rel` attribute contains the token `stylesheet`, compared without regard to ASCII case. The key of a link is the value of its `href` attribute resolved against the URL of the page. When the browser shows new content, it applies the stylesheet links of the head of a source document to the head of the page:
  - client-side rendering of a document (HYC-8, HYC-3): the rendered document;
  - a JSON region response (HYC-2): the layout rendered with the shared data of the response as root data, the title rendered alone as the definition `title`, and an empty definition `data` and an empty definition for every manifest region;
  - the HTML document that htmx requests to restore a page from history in server-side rendering (HYC-4): that document.

  The browser applies the links in three steps:
  1. It walks the stylesheet links of the source in order; a key that appears again counts only at its first link. For each link it keeps the first stylesheet link of the page with the same key that stands after the last kept link, and otherwise inserts a copy of the source link after the last kept or inserted link, or, before the first kept link, in front of the first stylesheet link of the page, or at the end of the head when the page has none.
  2. It waits until every inserted link, and every kept link that an earlier application inserted and that is still loading, has loaded. Only then does it show the content.
  3. After it shows the content, it removes every other stylesheet link of the page, so that the stylesheet links of the page are those of the source in their order.

  Other elements of the head, such as `style` elements, stay. When a later application starts before an earlier one shows its content, only the later one removes links. When a link fails to load, the browser removes the links that it inserted for this application, does not show the content and reports the failure as HYC-14 defines. The first document of server-side rendering already has its stylesheet links and needs no application.

## Client rendering on the server

- **HY-62** An application may declare client rendering, so that one server answers the client-rendered pages and the server-rendered pages of one manifest with the same handlers. The declaration has a static shell, a data base path and a selection:
  - The shell is the absolute path of an HTML file that contains `<meta name="hyper-api" content="<data base path>">` (HYC-8). The server reads it when the application opens.
  - The data base path follows HY-8 and is not empty. No route path is the data base path or starts with it followed by `/`.
  - The selection receives every request and returns a choice: whether the request is of a client-rendered page, chosen for example by the `Host` header, and a value, such as the stored service of the host. In PHP the choice is `new Choice(chosen: <bool>, value: <value>)`; in Node it is an object `{ chosen, value }` whose `chosen` is `true` or `false` and whose `value` is not `undefined`. The server calls the selection once per request, after HY-59 step 1 and HY-42 and before routing. In the Node server the selection may also return a promise of the choice, which the server awaits, because a selection that reads stored data reads it asynchronously in Node. A selection that throws, returns another value or returns a promise that rejects or resolves to another value fails with HY-43.
  - Every loader and action of the request reads the value of the choice from its request, `$request->selection()` in PHP and `request.selection()` in Node and Python, whether the selection chose the request or not. An application therefore reads the stored data that its selection and its handlers both need once per request and passes it as a value, without a cache. A request of an application without the declaration has the value null.

  The application fails to open when the shell file cannot be read, the shell does not declare the data base path, the data base path is empty or does not follow HY-8, or a route path lies under the data base path. A request that the selection does not choose is answered as without the declaration, with the base path of the application (HY-8). A chosen request is answered with the data base path in place of the base path of the application:
  1. `<data base path>/_hyper/keep` follows HY-40.
  2. A request path that starts with the data base path followed by `/` or the end of the path is routed after the data base path is removed, and `Location` headers include the data base path (HY-8). After HY-27, a request that is not a JSON request (HY-15) receives status 406 with the text `Not Acceptable`. Every other request is answered by HY-15 to HY-59: a document request and a region request receive JSON, and an action runs.
  3. Any other request path is routed as it is. A path without a route receives 404 and a method other than `GET` receives 405 (HY-27). Then a JSON request receives status 406 with the text `Not Acceptable`, and an HTML request receives status 200 with the bytes of the shell as its body and the headers `Content-Type: text/html; charset=utf-8`, `Cache-Control: no-cache` and `Vary: Accept`.

  The 405 and 406 responses and the shell response of a chosen request run no loader or action, read no session (HY-45), and contain no request data. Every response of a chosen request carries the frame policy of HY-45 and is reported to the response hook of HY-60. `contracts/client.json` holds requests, the selection of each request and the expected responses, and both servers pass every case.
- **HYC-6** When client-side rendering mounts a rendered document (HYC-8, HYC-3), the browser replaces the attributes of the `html` element with the attributes of the `html` element of the rendered document, in their order: an attribute that the rendered element does not have is removed. A layout that renders `<html lang="{= language}">` therefore gives a client-rendered page the language of its data, as the server-rendered document has it. The static shell that `scripts/build-assets.mjs` writes has no `lang` attribute, because it holds no data.

## Actions

- **HY-24** The session token is 32 random bytes that the server creates when the session first needs it. The value `csrf` of a response (HY-10) masks it: 32 random bytes `r` that the server draws once per response, followed by `r` XOR the token, written as 128 lowercase hexadecimal digits. Every response draws a new `r`, so no response contains the bytes of the token, and the compressed size of a response that also contains request input does not reveal it. An action request and a save of a kept value (HY-40) must contain the form field `_csrf` with a masked value of the session token: 128 lowercase hexadecimal digits whose second half XOR its first half equals the token, compared in constant time. Otherwise the server responds with status 403 and runs no action. The server never sends the token itself. `contracts/csrf.json` holds tokens, masks and form values with the expected results, and both servers pass every case.
- **HY-72** An action renews the session with `renewSession()` of its reply when the visitor that the session belongs to changes, such as at sign-in and sign-out. After the action returns, the server moves the session values to a new session identifier, deletes the old session, creates a new session token and sets the new session cookie; the flash values of a redirect and the kept values stay. A page that the action renders carries a masked value of the new token. A loader or the shared handler that calls `renewSession()` fails with HY-43, because the page that it renders carries the old token.
- **HY-25** An action that succeeds returns a redirect. The server responds with status 303 and `Location`, stores the flash values and the changed topics in the session, and removes them after the next request reads them. The browser follows the redirect with the same headers, and htmx records the final URL in history.
- **HY-26** An action that rejects its input returns invalid data. The server responds with status 422 and renders the route page with the route data merged with the invalid data, as JSON for a JSON request and as a document otherwise.

## Data

- **HYC-10** The output of a region is a function of its template, the shared data and the region data. The browser changes the page only by replacing region data and rendering it. Form controls hold the values that a user is entering; every other screen state, such as a sort order or an open panel, is region data.
- **HY-30** A route may declare route regions, for example `"regions": [{ "name": "rows", "template": "board/rows.tpl" }]`. A part of a page that changes in the browser without a request to the application is a route region; the browser may load the template files that the change renders and that it has not loaded (HYC-12). The route template, or a template that it includes or places by path, places each route region with `{# name}`, without block arguments, inside an element whose `id` is the region name; `make templates-check` fails when no template of that graph places a route region. A route region loader may return `null`, which makes the region absent from that response (HY-75). Region names are unique across the manifest regions and every route region. Each route region has its own loader. The page region receives every route region as HTML (HY-13), and every JSON response that contains the page region contains the route regions right after it.
- **HY-75** A route region is present in a response when its loader returns data, and absent when it returns `null`. An absent route region has no entry in `regions` of the JSON response, in the embedded data (HY-31) or in `kept`, and the page region receives no definition for it, so `{?# name}` is false; a template that places a route region that may be absent places its element inside `{?# name}…{/}`. A response carries no kept value of an absent region. The browser holds only the present route regions (HYC-4), so `data`, `render`, `set` and `hy-set` fail for an absent one (HYC-11). After it renders or swaps the page region, the browser checks that every present route region of the held route has exactly one element with its `id` in the page and that no absent route region has one; otherwise it sets `hy-error="0"` on the body (HYC-14). This lets a page that places views at request time under one route, such as a page that an administrator composes, declare a route region for a view that only some of its pages place.
- **HY-31** The layout places `{# data}` once, before `</body>`. The embedded data is the part of the document JSON value (HY-17) that the browser can change: `env`, `route`, `params` and `shared` as the JSON response has them (HY-73), `regions` with only the route regions of the route (HY-30) in their order, and `kept` with only the entries of those regions. A document embeds its data when the reply of its request asks for it (HY-92) and a route region of the route is present (HY-75): the definition `data` then renders the reserved template `hyper/data.tpl`, whose source is exactly `<script type="application/json" id="hy-data">{= json(response) | raw}</script>`, with `response` equal to the embedded data. Otherwise the definition `data` is empty and the document has no `#hy-data`, so its source holds only the HTML of the page. A document of client-side rendering (HYC-8) never embeds its data, because the browser holds the data of the JSON response that it rendered. The PHP server and the Node server compute and render the embedded data the same way, so a document keeps the same bytes on both. A region request does not render it. A JSON response keeps every region (HY-18), because the browser renders them.
- **HY-92** A loader, an action or the shared handler of a request makes the HTML document of its response embed its data (HY-31) with `embedData()` of its reply (HY-52): `$reply->embedData()` in PHP, `reply.embedData()` in Node and `reply.embed_data()` in Python. Without the call a document embeds no data. The call changes no JSON response (HY-17), redirect or stop, and a request of client-side rendering (HY-62) receives the shell or JSON, which hold no embedded data. An application decides it per request, for example by the stored service of the host that its selection reads (HY-62).
- **HY-71** The data that the server sends is public to the visitor of the request. Shared data, region data and kept values reach the browser in the embedded data (HY-31), in every JSON response (HY-17) and in client-side rendering (HYC-8), so a value passed to a template does not stay on the server. A loader and the shared handler return only values that the visitor of the request may see: a value that the page does not show, such as a password hash, a session token or personal data that the visitor may not see, is never part of them. The server also removes every value that the templates do not read (HY-73), but that removal does not make a value safe to return. A value that the page shows reaches the browser in the HTML anyway. The masked CSRF token is shared data (HY-10, HY-24), because the browser sends it back with every form; the session token itself is never sent.
- **HY-73** The server sends only the data that the templates of a route read. The read paths are computed from the template ASTs before any request, and they include at least every value that rendering reads, so rendering the kept data gives the same bytes as rendering the loader data.
  - A path is a list of steps from the root data: a map key, a list index written in decimal, or `*`, which stands for every entry of a map or every element of a list. A path read whole keeps its value as it is; a path read in part keeps only the paths below it that are read.
  - An expression has a set of paths. A variable has the root path of its name, together with the paths that a local variable of that name holds; a local variable holds the union of the paths of every assignment `{:x = e}` of its scope. The loop variable of `{@ v = e}` exists only in the body of that loop: there `v` has every path of `e` followed by `*` and the paths of the assignments to `v`, and neither its root path nor the paths of an outer loop variable of the same name. Outside the body the loop variable adds no path to `v`, so an assignment before the loop that reads the name of its loop variable, as in `{:p = page.x}{@ page = p.items}`, keeps the paths that it had before the loop. `v.value_` has the paths of `v`, and another loop meta field has none. A member, and an index whose key is a string or number literal, add the key to every path. Another index reads its object and its key whole and has no path. `a ?? b` has the paths of `a` and `b`, a ternary the paths of its two results, and every other expression none.
  - An expression reads its paths whole when its value is output, is the test of `{? }`, `{:? }` or a ternary, is an operand of an operator other than `??`, is an argument of a function, a member call or a class call, the object of a member call, an item, key, value or spread of a list or map literal, or the key of an index. A loop `{@ v = e}` reads every path of `e` followed by `*` in part, so the loop keeps every entry.
  - An include `{+ path}` reads in the scope of the including template. A block with a path reads its template in a new scope, where the root names hold their root paths and every scope argument holds the paths of its expression in the calling scope; a block that places a template already being placed above it reads nothing, because rendering fails there (RT-22 of the template language). A block that places a definition reads nothing.
  - The read paths of the shared data of a route are those of the layout, the title, every manifest region template, the route template and every route region template, and `csrf` whole when a route region keeps a value on the server (HYC-13). The read paths of the data of a region are those of its template, the route template for the page region, and the kept paths of a route region whole. `hyper/data.tpl` reads nothing.
  - Before it renders or encodes a page, the server keeps of the shared data and of every region's data only their read paths: a map keeps the keys that a path names, with their values kept recursively, and every key under `*`; a list keeps its length, with each element kept under `*` and the paths of its index and with `null` at an index that no path names; any other value stays as it is. A map that becomes empty stays a map.
  - The build writes the read paths of every route to `reads.json` of the server program (HY-48), and the Node server computes them with the browser package when the application opens. `contracts/reads.json` holds templates, data, the read paths and the kept data; the browser package computes the read paths of every case, both servers keep the expected data, and the kept data renders the same bytes as the data. `data(region)` (HYC-11) returns the kept data, so a path that no template reads is not there.

## Browser data

- **HYC-4** The browser holds the data of the last response that it rendered: the environment, the route, the parameters, the shared data and the data of the route regions of the route (HY-30). When a server-rendered page opens with `open()` of the browser code, and when htmx restores a page from history by requesting its HTML, the browser reads the embedded data from the element `#hy-data` (HY-31), replaces all held data with it and starts loading the templates of the route (HYC-12). A document without `#hy-data` leaves no held data, and the browser obtains the data with HYC-7 when it first needs it. It needs the data when the page opens only when a `localStorage` or `sessionStorage` value is stored for a kept path of a route region of the route (HY-37, HY-38), so a page that is only viewed and has no such value sends no request beyond its document. A region response (HYC-2) replaces all held data with its own, because it contains the shared data, the page region and every present route region (HY-17, HY-18, HY-30), which is all that the browser holds; the server therefore needs no signal of the data that the browser holds. `render` (HYC-11) replaces held region data.
- **HYC-7** The browser obtains the data that it does not hold with one document request (HY-15) for the URL of the current page, its path and its query, with `Accept: application/json`. It obtains the data when `data`, `render`, `set` or `hy-set` (HYC-11, HYC-5) names a route region of the route of the current page while it holds no data, and when the page opens with a stored browser kept value (HYC-4). A call that names another region sends no request: `data` returns nothing, and the other calls fail. Calls that need the data while the request is pending wait for the same request. The response must be a JSON response with status 200 whose URL routes to the route of the current page (HYC-1). The browser then applies the browser kept values (HY-38), holds the data and renders every present route region of the route from it as HY-38 renders the regions of an embedded document, so that the page shows the data that the browser holds, also when the data changed after the server rendered the HTML; the call then continues with the held data. When a response (HYC-2, HYC-4) replaced the held data while the request was pending, the browser drops the response of the request, and the call continues with the held data. Another response, a network failure or a response that cannot be decoded leaves no held data, marks the region of the call, or the body when the page opens, with the status of the response or `0` (HYC-14), and fails the call; the next call that needs the data sends the request again. The request runs the loaders of the page again as its HTML request did, so a loader of a `GET` request changes no stored state (RFC 9110, section 9.2.1), and the page of an action that rendered in place (HY-26, HY-58, HY-69) receives the data of the `GET` request of its URL.
- **HYC-11** The browser code provides `data(region)`, which returns a promise of the held data of a region; `render(region, data)`, which replaces the held data of a region; and `set(region, path, value)`, which replaces one value at a dotted path (map keys and list indexes) in the held data of a region. The region is a route region of the held route (HY-30); another region fails. A path that the data does not contain fails. `render` and `set` then render the region alone (HY-13) and swap it into the region element with `innerMorph`. The page region uses the template of the held route and the held route regions (HY-13). These operations send no request, except the document request of HYC-7 while the browser holds no data. There is no change tracking: the code that changes data asks for the rendering. Calls run one after another in call order, and each starts from the held data that the previous call left. A call checks the held data of its own region: when a response (HYC-4) replaced it before the swap, the call ends without swapping, holding or storing; when a response replaced it during the swap, the call does not hold or store and renders the region again from the held data. A response that leaves the region unchanged does not affect the call.
- **HYC-5** A template may give an element the attribute `hy-set="path=value; path=value"`, where each value is a JSON literal and each path follows HYC-11. A click on the element, or on an element inside it, runs every assignment in the held data of the closest enclosing element whose `id` is the name of a route region of the held route, or of the route of the current page while the browser holds no data (HYC-7), and renders that region once. The template computes the assigned values, for example `hy-set="service.close.flag={? service.close.flag}0{:}1{/}"`. `hy-set` works only with JavaScript.

## Template delivery

- **HYC-12** The browser loads a template when rendering reaches it. It renders, and when the rendering requested templates that are not loaded, it loads each of them by its index URL and renders again, until the rendering completes or fails for another reason. A template that no rendering reaches, such as the template of a branch that the data does not select, is not loaded, so a route whose template selects one of many views loads only the views that it shows. The entry templates of a route are the layout, the title, every non-page region template, the route template and every route region template; for a region request the browser starts loading them with the request, at the same time, and when the response URL routes to another route, such as after a redirect, it loads the entry templates of that route. When a server-rendered page opens, the browser loads no template; it loads the templates that it needs when it first renders a region of that page. The browser never renders `hyper/data.tpl`, because a client-rendered document embeds no data (HY-31); the Node server, which renders it, checks that the index holds it. A name that the index does not hold fails the rendering (HYC-14). Loaded templates stay loaded until the page unloads. The Node server, which renders every page, reads every template of the index when it opens.
- **HYC-16** A page requests only the resources that it uses, and each resource at most once while the page is loaded. A resource is a template file, a stylesheet or a script file. The browser loads a template when rendering reaches it (HYC-12). The layout links only the stylesheets of the content that it renders, and the browser applies the stylesheet links of each rendered head and keeps a link that is already applied (HYC-15); a stylesheet that the application links on every page is one that every page uses. The asset build writes the client entry `public/assets/hyper-<hash>.js` and, for code that the entry imports with `import()` and does not import statically, chunk files `public/assets/hyper-chunk-<hash>.js`; the browser loads a chunk when that code first runs, by an absolute URL below `/assets/`, so the entry that the static shell inlines loads it too, and the browser loads a module once. The asset build writes no file that the application names: it writes the template files and the index (HR-34), the entry, its chunks, `manifest.json` in the directory of `--output` with the URL of the entry as its only member `hyper`, and the static shell. The application places and links its own stylesheets and names with `--static` the files below `public/` that the static deployment holds at the same path, such as the stylesheets that its layouts link; the asset build adds no other file of `public/assets` to the deployment, because `public/assets` keeps the files of earlier builds. The static shell contains `<meta name="hyper-api">`, the inlined entry and no stylesheet, because the browser applies the stylesheet links of the rendered layout before it shows the page (HYC-8, HYC-15). `tests/scripts/build-assets.test.mts` builds an application whose entry imports a module with `import()`.

## Kept data

- **HY-37** A route region may declare kept paths, because only route regions change in the browser (HY-30); the manifest check rejects `keep` on a manifest region. An example is `"keep": { "notice.closed": "server", "sort": "localStorage" }`. A path is a dotted path: a map key `[A-Za-z_][A-Za-z0-9_]*`, then any number of `.` each followed by a map key or by a list index of decimal digits. A kept value survives a reload in the storage named by its kind:

| Kind | Storage | Request when the value changes | First SSR document |
|---|---|---|---|
| `server` | the server session | one background request that rendering does not wait for | contains the value |
| `cookie` | the cookie `hy-keep`, written by the browser code; it cannot be `HttpOnly` | none | contains the value |
| `localStorage` | the browser `localStorage` | none | contains the loader value; the browser renders the kept value after it loads |
| `sessionStorage` | the browser `sessionStorage` of the tab | none | contains the loader value; the browser renders the kept value after it loads |

- **HY-38** The value that the user set last in the browser takes precedence; the loader data is the default. A kept value conforms to the value at its path when the region data contains the path, the kept value is a value of the template data model (a number outside ±(2^53 − 1) is not), and:
  - a null, boolean, number or string has the same type;
  - a map replaces a map; when the data map has keys, the kept map has the same keys and the value of every key conforms to the value of the same key;
  - a list replaces a list; when the data list has items, every kept item conforms to its first item.

  An empty data map or list gives no shape, so any map or list conforms to it; the rendering check below covers such values.

  A kept value that does not conform is ignored.
  - The server reads `server` and `cookie` values and sends the conforming ones in `kept` (HY-17). They never change `regions`. It reads the `cookie` values from the cookie `__Host-hy-keep` when the request uses HTTPS or the application declares HTTPS (HY-45), and from `hy-keep` otherwise; on HTTPS the host-only cookie alone counts, because another host, such as a sibling subdomain, cannot set it. The cookie value is the URL-encoded JSON object `{ "<region>": { "<path>": <value> } }`.
  - A region renders with its kept values applied to its data in this order: the values in `kept`, the `localStorage` and `sessionStorage` values, and the `server` values whose saving has not completed (HYC-13). The server applies only the values in `kept`. The browser applies all of them to the data that it holds and renders, and does not synchronize them with the server. For a document rendered by the server, the browser applies them after it holds the embedded data, or after it obtains the data when a browser value is stored (HYC-4, HYC-7), and renders every region whose data changed.
  - When a region does not render alone (HY-13) with its kept values applied, it renders with its loader data, and its kept values are removed from `kept` and from the held data. The server removes them before it renders the embedded data (HY-31), so the server and the browser render the same document. When the region does not render with its loader data either, rendering fails (HY-43, HYC-14).
- **HYC-13** When `set`, `render` or `hy-set` changes a path, the browser renders the region first and then stores every kept path that equals the changed path, lies under it or contains it, with the value now at the kept path. A `server` value stays pending until the server answers 204 for it or a later change of the same path is saved; while it is pending it is applied as in HY-38. Saves of one path are sent one at a time: a change made while a save of its path is in flight is sent after that save completes, and only the latest value is sent. A failed save keeps the value pending and marks the region as failed (HYC-14) when no later change of the path exists. For `server` it sends `POST <base path>/_hyper/keep` with the form fields `_csrf` (the held `shared.csrf`, HY-10), `region`, `path` and `value` (the JSON text of the value) and does not wait for the response. For `cookie` it writes the cookie `hy-keep` with `Path=/`, `SameSite=Lax` and `Max-Age` of one year; on HTTPS the cookie is `__Host-hy-keep` and also `Secure`, so that another host, such as a sibling subdomain, cannot set it. The cookie value is the URL-encoded JSON object `{ "<region>": { "<path>": <value> } }`.
- **HY-40** The server answers `POST <base path>/_hyper/keep` with status 204 after it stores the value in the session, with status 403 when the CSRF token does not match, and with status 400 when the region does not declare the path as `server`, the value is not JSON, the JSON text is longer than 4,096 bytes, or the value is not a value of the template data model. The path `/_hyper/keep` is reserved; a route path may not start with `/_hyper`.
- **HY-41** `contracts/keep.json` holds region data, kept values and the expected data after HY-38. The PHP and JavaScript implementations both pass every case.

## Request boundary and failures

- **HY-42** The request path is the path of the request target: the target up to its first `?` or `#`, and for an absolute-form target (`http://host/path`) the part after the authority. It is not decoded further. The path must consist of the printable ASCII characters `!` to `~`, as RFC 9112 requires of a request target, and every query and form name and value (HY-56, HY-57) and the `HX-Current-URL` header must be valid UTF-8; otherwise the server responds with status 400 before any loader or action runs. Cookies are not checked: the server ignores a `hy-keep` cookie that is not a JSON object, ignores its values that do not conform (HY-38), and starts a new session for a session cookie that is not an identifier that it created (HY-45).
- **HY-43** An exception that the application does not handle produces status 500 with the text `Internal Server Error`. The response contains no exception message, file path or stack trace; the server writes them to its log. The PHP setting `display_errors` must be off before PHP starts the request, because PHP writes startup warnings (for example `max_input_vars`) before the application runs.
- **HY-74** While a server answers a request, a warning that its runtime raises becomes an error, and the request fails with HY-43. The runtime would otherwise continue, and the server would send a wrong page with status 200 while the message reaches only the log or the output. An error that an expression silences stays silent. The server installs its handling for the requests only and restores the previous handling afterwards.
  - PHP: every warning, notice and deprecation that PHP raises, such as an undefined variable, an undefined array key or a wrong argument, becomes an exception through an error handler; an error that `@` silences is not in `error_reporting()` and stays silent.
  - Python: every warning of the `warnings` module that is raised while a request is answered, such as a `DeprecationWarning` or a `RuntimeWarning`, is raised as an exception: the filter `error` is set while a request is in flight.
  - Node: a warning that is emitted with `process.emitWarning` while a request is answered throws its error at the call.
- **HY-44** Shared data and region data are values of the template data model. A number outside ±(2^53 − 1), integer or not, fails with HY-43, for a document and for JSON alike. The server checks every value that the shared handler and the loaders return before it removes the values that no template reads (HY-73), so a value outside the data model fails also when no template reads it. The shared handler and every loader return a map: in PHP an array that is empty or is not a list, in Node a plain object or a `Map`. Another value, such as a list, fails with HY-43. The check is the host binding of the template data model (VAL-13, VAL-14) followed by a check that the bound value holds no native object (VAL-19): a value that binding turns into a value of the data model passes, such as a PHP `stdClass` or `JsonSerializable` and a Node plain object, and an application object that binding keeps as a native object, such as a PHP `DateTimeImmutable` or a Node `Date`, fails with HY-43 on both servers. A JSON response checks only the parameters of the request again, because this check covered the shared data and the region data and a kept value enters a response only when it is a value of the data model (HY-38).
- **HY-45** The server session cookie is named `__Host-hy-session` when the request uses HTTPS or when the application declares that it is served over HTTPS, which a server behind a TLS-terminating proxy must do, and `hy-session` otherwise; the application does not choose the name. The browser accepts a `__Host-` cookie only from its own host, so another host, such as a sibling subdomain, cannot give a visitor a session whose token it knows. The cookie has `Path=/`, no `Domain`, `HttpOnly` and `SameSite=Lax`, and it is `Secure` under the same condition as the prefix. The server accepts only session identifiers that it created, and starts a session only when a request reads or writes session data: a request that the server rejects before routing (HY-42) or whose path matches no route creates no session. Every response carries `Content-Security-Policy: frame-ancestors <sources>`, where the application sets the sources and the default is `'self'`.
- **HY-46** A redirect location is an application path: valid UTF-8 that starts with `/`, whose second character is neither `/` nor `\`, that contains no control character (C0, DEL or C1), no space and no `\`, and whose path has no segment `.` or `..`, also when a dot is percent-encoded (`%2e`).
- **HYC-14** When a region request receives a response that is not JSON, or when rendering, saving a kept value, loading templates or loading a stylesheet (HYC-15) fails, the browser does not swap and does not change history. It sets the attribute `hy-error` on the region element to the response status, or to `0` for a network or rendering failure, and removes the attribute from every region that renders successfully afterwards. A cancelled request is not a failure; a request that htmx aborts because its timeout (`hx-timeout`, or `htmx.config.defaultTimeout`) passed is a network failure. `render`, `set` and `hy-set` change held data only after the region rendered; a failure leaves held data unchanged. When client-side rendering of a document fails, or a stylesheet of a history restoration in server-side rendering fails to load, the browser sets `hy-error` on the body.

## Node server

- **HY-54** The Node server package `@polyspec/hyper-server` implements the server rules of this document as the PHP server does; its tests run the cases of the PHP server tests against the same fixtures. It differs from the PHP server only as follows:
  - It renders a document as the browser renders the document JSON value (HY-12, HY-31, HY-38), with the browser code and the template files of the asset build (HR-34), and embeds its data when the reply asks for it (HY-92).
  - Its JSON text has the bytes of PHP `json_encode` with `JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES`. A string escapes `"`, `\`, the control characters below U+0020 (`\b`, `\f`, `\n`, `\r`, `\t`, and `\u00xx` for the others) and U+2028 and U+2029 (`\u2028`, `\u2029`), and no other character. An integer within ±(2^53 − 1) is written in decimal. Another number is written with the shortest digits that read back as the same number: positionally when its decimal point position p (the number is 0.d × 10^p) is between −3 and 17, and otherwise as `d.ddde±x` with at least one fraction digit; negative zero is `-0`. It decodes kept values (HY-38, HY-40) as PHP `json_decode` does: an integer literal is an integer and other literals are floats, a number outside ±(2^53 − 1) or one that is not finite is not a value of the data model, and 512 nested containers, a lone surrogate escape or a key that starts with U+0000 fail. `contracts/json.json` holds the cases that both servers pass.
  - A JavaScript value of the data model is null, a boolean, a number or a bigint within ±(2^53 − 1), a string, an array, a `Map` with string keys or a plain object. A string with a lone surrogate, which has no UTF-8 form, and any other value fail with HY-43.
  - Loaders and actions receive one context argument with the request, the reply (HY-52) and the services that the application binds by key.
  - Its session store keeps each session in a file of one directory, named by an identifier of 64 hexadecimal digits that the store created. It writes the session cookie with the attributes and the order of the PHP session cookie (`<name>=<id>; path=/; secure; HttpOnly; SameSite=Lax`, `secure` under the conditions of HY-45), and it runs the requests of one session one after another.

- **HY-97** Every server takes an optional request hook `around`: an argument of `create_server`, `create_wsgi` and `create_asgi` (Python), an option of `App.listener` and `App.server` (Node), and an argument of `App::open` (PHP). The server calls it once for every request that it gives to the application, with the request as the server built it and a function `answer`, and sends the response that `around` returns. `answer(request)` runs the application for a request as the server does without `around`: it opens the session of the request by its session cookie, answers with `App.respond`, which calls the response hook (HY-60), closes the session and returns the response with the cookie of a new session first (HY-45). `around` may call `answer` with the request or with a changed copy, such as a copy with a header that `Request.with_header(name, value)` (Python), `request.withHeader(name, value)` (Node) or `Request::withHeader($name, $value)` (PHP) sets (the name is compared without case, as a request reads a header); it may change the response that `answer` returns; and it may return its own response without calling `answer`, and then the server opens no session and runs no loader, action or hook of the application for that request. When a write of the response fails because the client closed the connection (HY-67), the server calls the disconnect hook with the request and the reply of the last call of `answer`, and does not call it when `around` did not call `answer`. The files of the public directory, which the Python and Node servers serve, are served before `around` and do not reach it. A value of `around` that is not callable fails when the server is created. An error that `around` raises outside `answer`, and a return value that is not a response, are escaped errors (HY-60), also for PHP, where `App::run` writes the plain 500 of an uncaught exception: the server logs them and answers the plain 500, which the write hook receives (HY-99).
  - The Node server gives the same through the `node:http` server that `app.server()` returns: a consumer replaces its `request` listener with a listener that calls the listener of the application, so that it runs each request in a context of its own, adds a request id header to the request and the response, or answers a request itself before the application, such as a 400 for a request that did not come from its web server. `around` gives these to an application of the Python server, whose `http.server` request handler is not replaceable.

- **HY-99** Every server takes an optional write hook `written`: an argument of `create_server`, `create_wsgi` and `create_asgi` (Python), an option of `App.listener` and `App.server` (Node), and an argument of `App::open` (PHP). The server calls it exactly once for each request that it gives to the application, with these values: the request that it gave to `around` (HY-97), or the request as received; the `Response` whose write it started, the plain 500 of an escaped error when none started, or null when the request ended before a response started; `ended`, which says whether the status line, the headers and the complete body were written without an error; the elapsed milliseconds since the arrival of the request (HY-60); and `failure`, the message of an escaped error as HY-43 states it, or null for every other response. It calls the hook after the answer of the request has ended (the application returned, failed or stopped on a closed connection, HY-67) and after the write ended or failed, whichever is later, and before the disconnect hook. An escaped error whose 500 cannot be written, because the response has started or the connection is closed, is reported with `ended` false and its failure. No adapter reports the plain 500 of an escaped error to the response hook. PHP calls the hook from a shutdown function that `App::run` registers after its escape function; `ended` is false when `connection_aborted()` is 1 or a fatal error ended the script after the headers were sent, and true means that PHP gave the complete output to the web server. Under either output buffering mode, `ended` and the response follow what PHP sent: with output buffering on and no output flushed, a fatal error after `App::run` replaces the response with the plain 500, which the hook receives with `ended` true; with output buffering off, or after a flush that sent the headers, the hook receives the started response with `ended` false. Node calls it after the `close` event of the `node:http` response and the end of the answer, with `ended` equal to `writableFinished`; the listener that `App.listener(sessions, options)` returns, which `App.server` installs, returns a promise that settles after the write hook and the disconnect hook of the request have run. WSGI: `ended` is true when the server consumes the whole body iterable, and false when it calls `close` before the end, also before the first item; an error before `start_response` is an escaped error, and so is a `start_response` that raises. ASGI: `ended` is true when both sends return, and false when a send raises or the task is cancelled; the error or the cancellation propagates. A request that ends before a response started, because its connection closed (HY-67), its task was cancelled (HY-100), or PHP `exit()` ended it without output, gives the hook a null response, with `ended` false and a null `failure` unless an error escaped. The hook is not called in three cases: for the files of the public directory, for a request that the transport gives no request to report (HY-60), and when the process ends before the request ends (a kill, or a worker timeout that ends the worker), because no code of the server runs then. An error that the hook raises is not handled by HY-43; it reaches the transport.
- **HY-100** Every server is served through the standard host interface of its runtime, and a host answers each request as the server does (HY-97, HY-99): PHP through a front controller that calls `App::run` under a SAPI (the built-in server or php-fpm), Python through the WSGI callable of `create_wsgi`, the ASGI callable of `create_asgi` or the `http.server` server of `create_server`, and Node through the `node:http` request listener of `App.listener`, which `App.server` installs. A host reads the request body up to the body limit of the application and no more (HY-59), opens the session of the request by its session cookie, sets the cookie of a new session first (HY-45), runs the request hook `around` (HY-97), reports the write to the write hook (HY-99) and a closed connection to the disconnect hook (HY-67), and answers a request whose target it cannot give with the plain 500 of HY-60.
  - Python WSGI: `polyspec.hyper.wsgi.create_wsgi(app, sessions, files=None, around=None, written=None)` of the Python server `polyspec-hyper-server` takes the arguments of `create_server` (HY-97, HY-99) and returns a WSGI application callable (PEP 3333) that a WSGI server runs. The callable answers every request as `create_server` does: it serves the files of the public directory before `around`, reads the request body up to the body limit of the application and no more (HY-59), opens the session of the request by its session cookie, answers with `App.respond`, sets the cookie of a new session first (HY-45) and runs the request hook `around` (HY-97). It adds the header `Content-Length` of the complete body itself. The write hook `written` (HY-99) reports that the write ended when the WSGI server consumed the whole body iterable, and that it failed when the server closed the iterable before its end, which PEP 3333 defines as premature termination; when the write failed, the callable calls the disconnect hook (HY-67) with the request that it gave to `around` and the reply of the last call of `answer`. The hook is not called for the files of the public directory. An error that `around` raises outside `answer`, or a value that it returns that is not a `Response`, is an escaped error (HY-60): the callable answers the plain 500 before it calls `start_response`, and the write hook receives it. An error that `start_response` raises, and a status, a header or a body that the callable cannot encode, is an escaped error too: the callable passes the plain 500 to `start_response` with the exception information of the error (PEP 3333), and the write hook receives it with its `failure`. The request target is the one that the WSGI server received. PEP 3333 has no raw path, so the callable reads the target from `RAW_URI` (gunicorn) or else from `REQUEST_URI` (uWSGI, mod_wsgi). The request path is the target up to its first `?`, and the raw query is the text after its first `?` (HY-42, HY-56), split as `create_server` splits its target. The callable never reads `PATH_INFO`, which the server has percent-decoded, and never re-encodes it. When the environ has neither key, the request has no target to report: the callable logs an error that names `RAW_URI` and `REQUEST_URI`, and answers the plain 500 of HY-60 before it calls `start_response`.
  - Python ASGI: `polyspec.hyper.asgi.create_asgi(app, sessions, files=None, around=None, written=None)` of the Python server `polyspec-hyper-server` takes the arguments of `create_server` (HY-97, HY-99) and returns an ASGI 3 application callable that an ASGI server runs. The callable answers every request of the scope type `http` as `create_server` does: the public files before `around`, the request body read up to the body limit of the application and no more (HY-59), the session cookie of a new session first (HY-45) and the request hook `around` (HY-97). It runs the pipeline of a request in a worker thread, so the event loop of the server answers other requests while a request responds. It sends one `http.response.start` with the status and the headers of the `Response` and one `http.response.body` with the complete body: the write hook `written` (HY-99) reports that the write ended when both sends return, and that it failed when a send raises, which an ASGI server does for a connection that the client closed; when the write failed, the callable calls `written`, then the disconnect hook (HY-67) with the request that it gave to `around` and the reply of the last call of `answer`, and lets the error propagate to the server. A cancellation of the task reports `written` with `ended` false and propagates the cancellation, without the disconnect hook, because the cancellation does not state that the client closed the connection. As `create_server` does (HY-67), the callable learns of a closed connection only when a send fails; it does not watch the `http.disconnect` message. The hook is not called for the files of the public directory. The library names no server; a deployment runs the callable with the server that it chooses. The request path is `scope['raw_path']` decoded as latin-1: the raw bytes of the target path without the query, which the ASGI specification defines; it is split as HY-42 splits a target. The raw query is `scope['query_string']` decoded as latin-1 (HY-56). The callable never builds the path from `scope['path']`, which the server has percent-decoded. An ASGI server that omits `raw_path`, which the specification makes optional, makes the request have no target to report: the callable logs an error that names `raw_path`, and sends the plain 500 of HY-60 before it sends anything. When a send of that 500 fails, the callable calls `written` with the failed write and lets the error propagate to the server, as HY-67 does for a failed send.
  - Node: `App.listener(sessions, options)` of the Node server returns the `node:http` request listener that `App.server` installs. The listener returns a promise that settles after the write hook and the disconnect hook of the request have run (HY-99).
  - PHP: `App::run` is the entry of the front controller; it turns `ignore_user_abort` off, registers the shutdown function that calls the write hook and the disconnect hook (HY-67, HY-99), and writes the plain 500 of an uncaught exception or a fatal error (HY-60).

## Errors

- **HY-27** A path without a route, or a loader that reports a missing resource, responds with status 404. A method other than `GET` or a declared `POST` responds with status 405.
- **HY-50** A loader or an action may stop the request with a redirect: it throws the redirect of a result of HY-25, which names an application path (HY-46) and may carry flash values and changed topics. The server responds with status 303 and `Location` with the base path, stores the flash values and the changed topics as HY-25 does, and renders nothing.
- **HY-51** A loader or an action may stop the request as forbidden. The server responds with status 403 and the text `Forbidden`, and runs no other loader or action of the request.
- **HY-52** Every loader and action of a request may receive the reply of the request. The reply adds a cookie with a name of `[a-z][a-z0-9_-]*` that does not start with `hy-`, a value of the characters `A-Z a-z 0-9 . _ ~ -` and an optional `Max-Age`, or removes a cookie with `Max-Age=0`. Each such cookie has `Path=/`, `HttpOnly`, `SameSite=Lax` and `Secure` under the conditions of HY-45. Another name or value fails with HY-43. A page response has `Cache-Control: no-store`; the reply may set the `Cache-Control` of a page response with status 200, and its value replaces `no-store`. A page carries the session token of its visitor (HY-10, HY-24), so a value without the directive `private` or `no-store`, or with `public` or `s-maxage`, fails with HY-43: a shared cache must not give the page of one visitor to another. The server session adds only its cookie to a response, and no caching header. A response without a body, a 304 of HY-53 included, has no `Content-Type`. The response of the request contains the cookies of its reply, whether it is a page, a redirect or a failure of HY-27, HY-50 or HY-51.
- **HY-53** A JSON response with status 200 has a weak `ETag`, `W/"<digits>"`, made of the first 32 hexadecimal digits of the SHA-256 digest of its body after every occurrence of the masked token of the response is replaced by the session token (HY-24). Two responses with the same data and the same session token therefore have the same tag although their masks differ, and the tag is weak because their bytes differ (RFC 9110, section 8.8.1). A renewed session (HY-72) has another token and so another tag. A `GET` request whose `If-None-Match` header equals that tag receives status 304 with the headers of the 200 response except `Content-Type` and no body, because a 304 carries no representation (RFC 9110, section 15.4.5) and php-fpm removes the `Content-Type` of a 304; an action runs whatever tag its request names.
- **HY-103** A loader or an action may set the `Referrer-Policy` of the page and JSON answers of its request with `Reply::referrerPolicy(value)` in PHP, `reply.referrerPolicy(value)` in Node and `reply.referrer_policy(value)` in Python. The value is one of the tokens of the Referrer-Policy specification, compared exactly: `no-referrer`, `no-referrer-when-downgrade`, `origin`, `origin-when-cross-origin`, `same-origin`, `strict-origin`, `strict-origin-when-cross-origin` and `unsafe-url`. Another value fails with HY-43, as a `Cache-Control` value without `private` or `no-store` does (HY-52). A later call replaces the value. Every page and JSON answer of the request, whatever its status, then has the header `Referrer-Policy` with that value, and so does a 304 of HY-53. Without such a call a page or JSON answer has no `Referrer-Policy` from the reply. The method sets no other header, and the redirects, the stops and the plain text failures of HY-27, HY-50, HY-51 and HY-65 have none from the reply.
- **HY-104** Several processes of one server, such as its worker processes, may write one session file at the same time. Each write of a session therefore creates its own temporary file in the session directory, exclusively, and publishes it with one rename: `os.replace` of the Python server (the file of `tempfile.mkstemp`) and `renameSync` of the Node server (the name `<id>.<uuid>.tmp`, created with the flag `wx`). The rename is the only step that the processes share, because the lock of a session store holds the requests of one session within one process only (HY-45). Two writes of one session both succeed, and the file holds the value of the write that renames last. A failed write removes its temporary file and raises its error (HY-60). Both servers create the session file with the mode 0600. `packages/server/python/tests/test_file_sessions.py` and `packages/server/ts/tests/sessions-race.test.ts` check it.
- **HY-58** A loader or an action may stop the request as a bad request. The server responds with status 400 and the text `Bad Request`, and runs no other loader or action of the request. An action may also return the route page with a stated status of 200, 409 or 422 and data: the server renders the route page with the route data merged with that data, as JSON for a JSON request and as a document otherwise, and responds with that status. Another status fails with HY-43. HY-26 is the page with status 422; a page with status 200 follows HY-52 and HY-53.
- **HY-69** A loader or an action may give the page of its request the status 403 with `Reply::status(403)` in PHP and `reply.status(403)` in Node, for a page that shows other data in place of the data that the request may not see, such as a sign-in form in place of a page that needs a session. A page response that has status 200 otherwise, the page of a `GET` request or an action result page with status 200 (HY-58), then has status 403 and is rendered as it is with 200, as JSON for a JSON request and as a document otherwise. As every response with status 400 or more it has `Cache-Control: no-store` (HY-65), and as every response with another status than 200 it has no `ETag` and never receives 304 (HY-53). A page with status 409 or 422, a redirect, a stop and a failure keep their own status. Another status fails with HY-43, because 403 states that the request may not see the page; 401 would require a `WWW-Authenticate` challenge (RFC 9110), and 200 would state that the response is the page.
- **HY-59** The application declares a body limit, the largest request body in bytes (8 MiB by default), and its form types, the media types of the request bodies that its actions and `/_hyper/keep` accept: one or both of `application/x-www-form-urlencoded` and `multipart/form-data`, by default `application/x-www-form-urlencoded`. Another limit or form type fails when the application opens. The server checks a request in this order, and runs no loader or action when a check fails:
  1. A body larger than the limit receives status 413 with the text `Content Too Large`, for every request and before HY-42. The size of a body is its length, or its `Content-Length` when that is larger, because PHP leaves the body empty when it is larger than `post_max_size`. The Node server stops reading a body when it passes the limit.
  2. After routing and HY-27, a `POST` request to an action or to `/_hyper/keep` whose `Content-Type` media type, without parameters and compared without case, is not a form type receives status 415 with the text `Unsupported Media Type`.
  3. Then the CSRF check of HY-24 answers 403.

  `App::run` of PHP fails before it answers when `post_max_size` is smaller than the limit, or when `multipart/form-data` is a form type and `enable_post_data_reading` is on (HY-57).
- **HY-60** The application may declare a response hook. The server calls it once for every response of the application with the request, the response and the elapsed time in milliseconds, including the responses that hyper answers itself: 400 (HY-42, HY-58), 403 (HY-24, HY-51), 404 and 405 (HY-27), 406 and the static shell (HY-62), 413 and 415 (HY-59), and 500 (HY-43, HY-66). The request is the request as received, with the base path. The response is the response of the application with its `Content-Security-Policy` (HY-45); the session cookie that the session adds afterwards is not part of it. The elapsed time counts on a monotonic clock from the start of the request: `App::run` and `handle` of PHP take the start from their caller as an `hrtime(true)` value, such as the value that the first statement of a front controller takes, or count from their own call; the Node server counts with `performance.now()` from the time when `node:http` gives the request. No server subtracts a wall clock time such as `REQUEST_TIME_FLOAT` or `microtime(true)`, because an adjustment of the system time moves the wall clock backwards and gives a negative elapsed time. The Node server also reports the 400 and 431 responses to requests that `node:http` cannot parse, with a request of the method and the target of the request line, or with no request when the packet has no request line. The hook also receives the reply of the request (HY-52), so that it reads the values that the loaders and actions of the request decided: the reply that they received, also when the request ended with a stop (HY-50, HY-51, HY-58), a failure of HY-27 or an error of HY-43, and a new empty reply when the server answered before routing (HY-42, HY-59, a path without a route, `/_hyper/keep` and the responses that `node:http` cannot give to the application) or without a loader or an action (the 405 and 406 responses and the shell of HY-62). A loader or an action records such a value with a note of the reply, a name and any value; a later note of the same name replaces the value and keeps its position. The server does not read the notes, and they are not part of the response. The hook also receives the failure of a 500 of HY-43 or HY-66, so that an application writes the cause with its own line: the message of the error of HY-43 (the message of a PHP `Throwable` or of a Node `Error`, or the text of another thrown value) or `the response to <method> <path> has <size> bytes, more than the response limit of <limit> bytes` of HY-66; for every other response it receives null. The files of the public directory of the Node server are not responses of the application. An error that the hook throws is not handled by HY-43; it reaches the caller of `handle`.
  - An error that escapes the answer of a request, because HY-43 does not handle it, is a failed read of the body, a failed stat of a file of the public directory, a failed session open or close, a failed write of the response, an error that the response hook throws, or an error that `around` raises outside `answer` (HY-97). The server logs it with the message of HY-43 and answers a plain 500 that hyper writes itself, identical in every adapter: status 500, the text `Internal Server Error`, `Cache-Control: no-store` (HY-65) and `Content-Security-Policy: frame-ancestors <policy>` (HY-45). No server reports that 500 to the response hook. The write hook (HY-99) receives it once, with the request as the server received it. The request as received has the target, the headers and the cookies of the request; a body that was not read is empty, and its size is the Content-Length that the client declared. A request whose target the transport does not give (a WSGI environ without `RAW_URI` and `REQUEST_URI`, or an ASGI scope without `raw_path`) has no request to report, so no hook receives its 500. The 500 is written only when the response has not started. When the response has started, or the write of the 500 fails, the server closes the connection; a write that fails is reported to the write hook once, so no hook is called twice for a request. The WSGI and ASGI callables (HY-100) write the same 500 before their `start_response` or their first send. `App::run` writes the same 500 for an uncaught exception, through `set_exception_handler`, and for a fatal error of the request, which the shutdown function reads from `error_get_last()` as E_ERROR, E_CORE_ERROR, E_COMPILE_ERROR or E_USER_ERROR (a memory or time limit is an E_ERROR), when headers have not been sent.
  - The plain 500 of an escaped error keeps the response headers that the caller of hyper set before hyper received the request, and no other header. PHP keeps the headers of `headers_list()` at the call of `App::run`, and `sendReplacing` removes every other header and adds them again before the headers of the 500. Node writes the 500 with `writeHead` on the `node:http` response, which keeps a header that the caller set with `setHeader` before the listener of hyper ran. The WSGI and ASGI callables (HY-100) pass the 500 to the `start_response` or the `send` of their caller as any response.
- **HY-65** Every response with a status of 400 or more has `Cache-Control: no-store`, so that no cache stores a failure: the plain text responses of HY-24, HY-27, HY-40, HY-42, HY-43, HY-51, HY-58, HY-59, HY-62 and HY-66, the plain 500 of an escaped error (HY-60), the 400 and 431 responses of the Node server to requests that `node:http` cannot parse (HY-60), the pages with status 409 or 422 (HY-58) and the pages with status 403 (HY-69). A reply does not change it (HY-52). Without the header, a cache may store a 404 or 405 response by its heuristic freshness (RFC 9111).
- **HY-66** The application declares a response limit, the largest response body in bytes (8 MiB by default); a limit that is not a positive integer fails when the application opens. The limit bounds the body that the server holds for sending one response, which a slow client keeps in the memory of the server process and of a web server that buffers the response. A response whose body is larger than the limit is not sent: the server writes `hyper: the response to <method> <path> has <size> bytes, more than the response limit of <limit> bytes` to its log, answers status 500 with the text `Internal Server Error` as HY-43 does, and reports that 500 to the response hook (HY-60) with the reply of the request. The size of a body is its length in bytes. The server renders a body completely before it compares its size, because the template programs render a document to one string.
- **HY-67** The application may declare a disconnect hook. The server calls it once, with the request as received, the elapsed milliseconds (HY-60) and the reply of the request, for a request whose client closed the connection before it received the complete response.
  - The Node server learns of the close when `node:http` reports that the connection closed before the response was written. It then runs no further loader, action or rendering of the request after the one that is running, writes no response, does not call the response hook and calls the disconnect hook.
  - PHP reports a closed connection only when a write to it fails, and a write of a small response to a closed connection can succeed. `App::run` turns `ignore_user_abort` off, so PHP ends the script at the first failed write of the response, and a shutdown function calls the disconnect hook when `connection_aborted()` is 1. The PHP server therefore renders the complete response and calls the response hook (HY-60) before it can detect the close, and it does not detect a close when every write of the response succeeds.
  - The Python server of `polyspec-hyper-server` (`create_server` of `polyspec.hyper.server`) learns of a closed connection only when a write of the response fails, as PHP does: `http.server` raises `BrokenPipeError`, `ConnectionResetError` or `ConnectionAbortedError` for a write to a connection that the client closed. The server renders the complete response and calls the response hook (HY-60) first, then writes the response; when a write fails with one of these errors, it writes no more of the response and calls the disconnect hook once with the request as received, the elapsed milliseconds and the reply of the request. It counts the elapsed time with `time.perf_counter_ns()`, a monotonic clock, from the time when its request handler starts the request, as it does for the response hook. It does not detect a close when every write of the response succeeds. `App.respond` answers a request as `App.handle` does and returns the response with the reply of the request, so that the server holds the reply that the disconnect hook receives; `App.handle` returns only the response.
- **HYC-9** An error in the browser code is thrown from the htmx response hook. htmx reports it with the `htmx:error` event and does not swap.
